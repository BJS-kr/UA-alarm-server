# mock 서버 동작 실측 기록

외부 발송 API 서버(`ghcr.io/us-all/backend-assignment-api:1.2`)의 세부 동작 특성을 확인하기 위해 수행한 실측 결과다. 계약 요약은 [external-api.md](./external-api.md)에 정리되어 있다.

## 측정 환경 구성

개별 특성을 분리 측정하기 위해 컨테이너 환경변수를 조정하여 실험을 수행했다.

| 측정 목적                                 | 컨테이너 환경변수 설정                                                     |
| ----------------------------------------- | -------------------------------------------------------------------------- |
| 처리량 제한 알고리즘 확인                 | `ERROR_RATE=0 TIMEOUT_RATE=0 SLOW_RATE=0 BLOCKED_PERCENT=0`                |
| 30초 지연 요청의 내역 기록 시점 확인      | `TIMEOUT_RATE=1 TIMEOUT_MS=10000 ERROR_RATE=0 SLOW_RATE=0 RATE_LIMIT=1000` |
| 지연 응답(Slow)의 기록 시점 및 소요 시간  | `SLOW_RATE=1 TIMEOUT_RATE=0 ERROR_RATE=0`                                  |
| 일시 오류(`500`, `503`) 시 내역 기록 여부 | `ERROR_RATE=1 TIMEOUT_RATE=0 SLOW_RATE=0 RATE_LIMIT=1000`                  |
| 기본 혼합 동작 분포                       | 기본값                                                                     |

## 처리량 제한: 토큰 버킷 (용량 50, 초당 50 충전)

- 50건을 동시에 전송하여 버킷을 소진시킨 직후 약 0.3초 뒤 20건을 전송하면 15~16건이 성공하고, 다시 약 0.6초 뒤 40건을 전송하면 30~31건이 성공했다. 이는 초당 50개 연속 충전 방식(토큰 버킷)과 일치하며, 1초 슬라이딩 윈도우나 고정 윈도우 방식이 아님을 확인했다.
- 벽시계 기준 초 경계(0.1초, 0.4초, 0.7초)와 무관하게 동일한 충전 동작을 보였다.
- 초당 45~50건을 균등 간격으로 3초간 전송했을 때 `429`는 0건이었다.
- 초당 100건을 3초간 전송했을 때 총 199건이 성공했다(초기 용량 50 + 3초간 충전 150). **`429`로 거절된 요청은 토큰을 차감하지 않는다.**
- `429` 응답의 `Retry-After` 헤더 값은 `1`(초)이다.
- `GET /v1/messages` 조회 엔드포인트는 발송 토큰이 소진된 상태에서도 `429` 없이 `200`을 반환한다.

## 메시지 기록 시점: 요청 접수 즉시

- **장기 지연(`TIMEOUT_MS`) 요청**: 요청 전송 후 0.35초 시점에 `GET /v1/messages?clientRef=`로 조회했을 때 이미 메시지 기록이 존재했다. HTTP 응답은 설정된 지연 시간(10초) 경과 후 `202`로 반환되었다.
- **클라이언트 측 연결 조기 종료**: 전송 후 1초 시점에 클라이언트 소켓을 강제 종료해도 서버 측 발송 기록은 정상 생성되었다.
- **지연 응답(`SLOW_MS`)**: 요청 후 0.21초 시점 조회에서 기록이 확인되었으며, 응답은 4.33초에 도착했다.

따라서 응답 지연이나 타임아웃 발생 시에도 요청 접수 직후 내역 조회 API를 통해 실제 발송 여부를 판별할 수 있다.

## 오류 응답 시 기록 생성 여부

| 응답 상태                         | 외부 기록 생성 여부                              |
| --------------------------------- | ------------------------------------------------ |
| `500`, `503`                      | 생성되지 않음                                    |
| `429`                             | 생성되지 않음 (거절된 18건 모두 미생성 확인)     |
| `400 RECIPIENT_BLOCKED`           | 생성되지 않음 (동일 수신자 재요청 시 항상 `400`) |
| 동일 `clientRef`로 2회 `202` 수신 | 2건 모두 개별 기록 생성                          |

## 응답 지연 분포

- **지연 응답(`SLOW_MS=3000` 기본값)**: 40건 측정 시 최소 3.0초, 중앙값 3.9초, 최대 4.5초가 소요되었다.
- **장기 지연(`TIMEOUT_MS=30000` 기본값)**: 설정값에 맞춰 30,000~30,003ms 구간에 응답한다.
- **기본 설정 혼합 전송(400건, 초당 40건)**:
  - 상태 코드 비율: `202` 93.8%, `500` 3.8%, `503` 1.8%, `400 RECIPIENT_BLOCKED` 0.75%
  - 지연 시간 백분위수: p50 64ms, p90 97ms, p95 3.2초, p99 30초
  - 지연 구간 분포: 200ms 미만 94.8%, 3~10초 4.3%, 30초 1.0%
- **조회 API 지연**: 발송 내역 조회(`GET /v1/messages`)와 사용자 목록 조회(`GET /v1/users`)에서도 간헐적으로 3~4초 지연 응답이 발생하므로 조회 요청에도 타임아웃 및 재시도 처리가 필요하다.

## 사용자 목록 API (`GET /v1/users`)

- 페이지당 최대 1,000명씩 총 100페이지(100,000명, `u_000001`~`u_100000`)를 반환한다.
- 전체 100페이지 순차 조회 시 약 31~33초가 소요되었으며(페이지당 p50 66ms, 최대 4.3초), 200페이지 조회 동안 5xx 오류나 30초 타임아웃은 발생하지 않았다.
- `cursor` 값은 다음 시작 인덱스의 base64url 인코딩 문자열이나, 클라이언트에서는 불투명(opaque) 토큰으로 취급한다.
- 유효하지 않은 커서는 `400 INVALID_CURSOR`, `limit > 1000` 요청은 `400 INVALID_REQUEST`를 반환한다.

## 기타 관측 사항

- 수신 거부(`RECIPIENT_BLOCKED`) 여부는 `SEED` 환경변수와 무관하게 사용자 ID 해시로 결정된다(예: `u_000089`, `u_000233`, `u_000322`).
- 존재하지 않는 사용자 ID 발송 요청 시 `400 UNKNOWN_RECIPIENT`를 반환한다.
- 필수 필드 누락 시 `400 INVALID_REQUEST`를 반환한다.
- `GET /health` 엔드포인트가 내장되어 있어 Docker Compose의 `service_healthy` 조건에 사용할 수 있다.
