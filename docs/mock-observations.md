# mock 서버 실측 관측 기록

API 문서만으로는 알 수 없어서 직접 측정한 mock 서버(`ghcr.io/us-all/backend-assignment-api:1.2`)의 동작이다. 계약 요약은 [external-api.md](./external-api.md)에 있다.

## 측정 방법

특성을 하나씩 분리하기 위해 환경변수를 다르게 준 컨테이너를 따로 띄워 측정했다.

| 목적 | 설정 |
| --- | --- |
| 처리량 제한만 보기 | `ERROR_RATE=0 TIMEOUT_RATE=0 SLOW_RATE=0 BLOCKED_PERCENT=0` |
| 30초 지연 요청의 기록 시점 | `TIMEOUT_RATE=1 TIMEOUT_MS=10000 ERROR_RATE=0 SLOW_RATE=0 RATE_LIMIT=1000` |
| 느린 응답의 기록 시점과 처리 시간 | `SLOW_RATE=1 TIMEOUT_RATE=0 ERROR_RATE=0` |
| 일시 오류의 기록 여부 | `ERROR_RATE=1 TIMEOUT_RATE=0 SLOW_RATE=0 RATE_LIMIT=1000` |
| 실제 혼합 동작 | 기본값 |

## 처리량 제한: 토큰 버킷 (용량 50, 초당 50 충전)

- 50건을 한 번에 보내 토큰을 소진하고 약 0.3초 뒤 20건을 보내면 15\~16건이 성공했다. 다시 약 0.6초 뒤 40건을 보내면 30\~31건이 성공했다. 초당 50 충전과 일치한다. 슬라이딩 윈도우였다면 0.3초 뒤에는 0건이어야 한다.
- 이 측정을 벽시계 초 안의 0.1초, 0.4초, 0.7초에 시작해도 결과가 같았다. 초 경계에 맞춘 고정 윈도우가 아니다.
- 초당 50건과 45건을 균등하게 3초간 보내면 429가 0건이었다.
- 초당 100건을 3초간 보내면 199건이 성공했다(초기 50 + 충전 150). **거절(429)된 요청은 토큰을 쓰지 않는다.** 그래서 429가 몰려도 상황이 스스로 악화되지 않는다.
- 429 응답의 `Retry-After`는 `1`(초)이다.
- `GET /v1/messages`는 발송이 포화된 중에도 200을 반환했다. 처리량 제한 대상이 아니다.

## 기록 시점: 접수 즉시

- **30초 지연 요청**: 0.35초 시점에 조회하면 이미 기록이 있었다. 응답은 설정한 지연(10초) 뒤에 202로 왔다.
- **클라이언트가 연결을 끊은 경우**: 1초 만에 요청을 중단해도 발송되고 기록됐다.
- **느린 응답**: 0.21초 시점에 조회하면 이미 기록이 있었다. 응답은 4.33초에 왔다.

정리하면, 응답이 늦거나 오지 않아도 발송 여부는 접수 직후 조회로 확인할 수 있다.

## 기록되지 않는 응답

| 응답 | 기록 |
| --- | --- |
| 500, 503 | 없음 |
| 429 | 없음 (거절된 18건 모두 기록 없음, 같은 순간 성공한 52건은 모두 기록) |
| 400 RECIPIENT_BLOCKED | 없음 (같은 사용자에게 다시 보내도 항상 400) |
| 같은 clientRef로 2번 성공 | 2건 기록 |

## 지연 분포

- **느린 응답** (`SLOW_MS=3000` 기본값): 40건이 최소 3.0초, 중앙값 3.9초, 최대 4.5초였다. 문서의 "3초 이상"은 실제로는 3~4.5초다.
- **30초 지연**: `TIMEOUT_MS`에 정확히 맞춰 온다(30,000~30,003ms).
- **기본 설정 혼합** (400건, 초당 40건):
  - 응답 비율: 202 93.8%, 500 3.8%, 503 1.8%, 400 RECIPIENT_BLOCKED 0.75%
  - 지연: p50 64ms, p90 97ms, p95 3.2초, p99 30초
  - 구간: 200ms 미만 94.8%, 3~10초 4.3%, 30초 1.0%
- **조회 API도 느릴 수 있다**: 발송 내역 조회와 사용자 조회에도 3~4초짜리 응답이 있었다. 그래서 조회에도 타임아웃과 재시도가 필요하다.

## 사용자 API

- 1000명씩 100페이지, 총 100,000명. id는 `u_000001`부터 `u_100000`까지이고 중복이 없다.
- 전체를 받는 데 31~33초가 걸렸다. 페이지당 p50은 66ms였고, 최대 4.3초였다.
- 두 번의 전체 조회(200페이지)에서 오류나 30초 지연은 한 번도 없었다. 발송 API와 달리 일시 오류는 주입되지 않는 것으로 보인다. 다만 이것은 관측일 뿐이므로 오류 처리는 그대로 둔다.
- 커서는 다음 시작 번호를 base64url로 인코딩한 값이다(`MTAwMQ` = `1001`, `MjAwMQ` = `2001`). 계약상으로는 불투명한 값이므로 내부 구조에 의존하지 않는다.
- 문서에 없는 에러 코드: 잘못된 커서는 `400 INVALID_CURSOR`, `limit=1001`은 `400 INVALID_REQUEST`를 반환한다.

## 그 밖의 관측

- 수신 거부 사용자는 `SEED`와 관계없이 사용자 ID로 정해진다. `SEED=42`와 `SEED=7`에서 앞쪽 400명 중 `u_000089`, `u_000233`, `u_000322`로 같았다. 테스트에서 영구 실패를 재현할 때 쓸 수 있다.
- 존재하지 않는 사용자는 `400 UNKNOWN_RECIPIENT`를 반환한다(`unknown recipient: u_999999`).
- 필수 필드가 없으면 `400 INVALID_REQUEST`를 반환한다(`alarmId, recipientId, body are required strings`). 조회에서 `clientRef`를 빠뜨려도 `400 INVALID_REQUEST`다.
- `messageId`는 컨테이너마다 `m_1`부터 순차적으로 매겨진다.
- 이미지에 `GET /health` 헬스체크가 포함되어 있어 compose의 `depends_on: condition: service_healthy`로 기동 순서를 맞출 수 있다.
