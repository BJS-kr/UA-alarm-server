# ADR-0015. alarms 리소스 및 동작 엔드포인트(send, cancel) 설계

## 배경

요구되는 API 기능은 알림 생성, 목록 조회, 단건 조회, 발송 시작, 발송 취소다. 발송 시작과 취소는 리소스의 상태를 전이시키는 작업이므로 REST 경로 설계 방식을 결정해야 한다.

## 결정

```
POST   /v1/alarms                      알림 생성
GET    /v1/alarms                      목록 조회 (상태·종류 필터, 커서 페이지네이션)
GET    /v1/alarms/{id}                 단건 조회 (상태별 건수 포함)
POST   /v1/alarms/{id}/send            발송 시작
POST   /v1/alarms/{id}/cancel          발송 취소
GET    /v1/alarms/{id}/deliveries      수신자별 발송 결과 조회 (상태 필터, 커서 페이지네이션)
```

## 근거

- **발송 시작과 취소는 별도 동작 엔드포인트로 분리한다**: 클라이언트가 상태 필드를 직접 수정하지 않도록 한다. 경로만으로 수행 동작이 명확히 드러나며, 허용되지 않는 임의 상태로의 변경 요청이 원천 차단된다.
- **`/deliveries` 하위 리소스를 제공한다**: 수신 거부만으로도 대량 알림 1건당 약 1,000명의 실패가 발생한다. 운영상 개별 수신자의 실패 사유를 조회할 수단이 필요하다.
- **`/v1` 경로 접두사로 버전을 명시한다**: 응답·요청 스키마 변경 시 기존 클라이언트의 하위 호환성을 깨지 않고 신규 버전을 병행 제공할 수 있다.
- 추가 엔드포인트가 필요한 경우에도 동일한 원칙(리소스 + 동작 엔드포인트)을 적용한다.

## 검토한 대안

- **`PATCH /alarms/{id}` + `{ "status": ... }`**: 상태 필드를 클라이언트에 직접 노출하게 되어 허용되지 않는 상태 전이를 차단하는 별도 검증이 필요하다. 또한 취소 요청의 결과 상태가 `CANCELING`인지 `CANCELED`인지 요청 본문만으로는 표현할 수 없다.
- **`POST /alarms/{id}/dispatches` (발송을 별도 하위 리소스로 생성)**: 리소스 중심 설계에는 부합하나, 알림 1건당 발송은 1회만 수행되므로 불필요한 리소스 계층만 추가된다.
