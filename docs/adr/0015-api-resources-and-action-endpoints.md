# ADR-0015. API는 alarms 리소스와 동작 경로(send, cancel)로 짠다

## 배경

필요한 기능은 알림 생성, 목록 조회, 단건 조회, 발송 시작, 발송 취소다. 발송 시작과 취소는 "상태를 바꾸는 일"이라, REST에서 어떻게 표현할지 고를 것이 있다.

## 결정

```
POST   /v1/alarms                      알림 생성
GET    /v1/alarms                      목록 (상태·종류 필터, 커서 페이지네이션)
GET    /v1/alarms/{id}                 단건 (상태별 건수 포함)
POST   /v1/alarms/{id}/send            발송 시작
POST   /v1/alarms/{id}/cancel          발송 취소
GET    /v1/alarms/{id}/deliveries      수신자별 결과 (상태 필터, 커서 페이지네이션)
```

## 이유

- **발송 시작과 취소는 동작 경로로 둔다.** 클라이언트가 상태 필드를 직접 쓰게 하지 않는다. 경로만 보고 하는 일을 알 수 있고, 허용되지 않는 상태로 바꾸는 요청이 애초에 생기지 않는다.
- **`/deliveries`를 더한다.** 수신 거부만 해도 대량 알림마다 약 1000명이 실패한다. 누가 왜 실패했는지 볼 수단이 운영에 필요하다.
- **`/v1` 접두사로 버전을 둔다.** 형식을 바꿔야 할 때, 기존 클라이언트를 깨지 않고 새 버전을 나란히 둘 수 있다.
- 구현 중 필요한 경로가 생기면 같은 원칙(리소스 + 동작 경로)으로 더한다.

## 검토한 후보

- **`PATCH /alarms/{id}` + `{ "status": ... }`**: 상태 필드를 클라이언트에게 열어 두는 셈이다. 허용되지 않는 전이를 막는 검증이 따로 필요하다. 취소한 결과가 CANCELING인지 CANCELED인지도 요청만 보고는 알 수 없다.
- **`POST /alarms/{id}/dispatches`(발송을 별도 리소스로 생성)**: REST 원칙에 가장 충실하지만, 알림 하나에 발송은 한 번뿐이라 리소스만 는다.
