# ADR-0005. 외부 의존성은 최소한으로 유지한다

## 배경

시스템 구성 요소(외부 인프라, 서드파티 라이브러리, 추상화 계층)가 추가될 때마다 장애 지점과 운영 비용이 증가한다. 또한 상태 저장소가 둘 이상으로 분리되면 시스템 간 상태 불일치가 발생할 수 있으며, 본 과제의 핵심 요구사항인 중복 발송 방지와 누락 방지는 상태 불일치가 발생하는 순간 보장할 수 없게 된다.

## 결정

기존 핵심 구성 요소(OS, PostgreSQL, Node.js 표준 내장 기능, NestJS)만으로 요구사항을 충족할 수 없는 경우에만 새로운 의존성을 추가한다.

상용 도구 및 라이브러리가 제공하는 세부 기능을 분석하고, 이를 기존 기술 스택으로 온전히 대체할 수 있는지 검증한 뒤 제외 여부를 결정한다.

## 근거

- 인프라 구성 요소가 추가될 때마다 장애 지점, 운영 부담(설정, 백업, 모니터링, 장애 조치), 시스템 간 상태 불일치 가능성이 함께 증가한다.
- 동시성 제어와 장애 복구의 정확성은 단일 진실 공급원(Single Source of Truth) 여부에 좌우된다. 기준 저장소가 하나면 상태 판정이 충돌하지 않는다.
- 이미 검증된 단일 시스템(PostgreSQL)의 원자적 연산과 격리 수준을 활용하면 별도의 분산 동기화 증명이 불필요하다. 예를 들어 PostgreSQL은 동일 행에 대한 조건부 `UPDATE`를 행 잠금으로 직렬화하고, `FOR UPDATE SKIP LOCKED`로 동일 행의 중복 점유를 방지한다.

## 상세: 적용 원칙 및 채택 의존성

### 적용 원칙

- 일반적인 외부 도구를 제외할 때는 해당 도구가 제공하는 기능과 프로젝트 내 대체 구현 수단을 명시적으로 대조한다(예: ADR-0003의 BullMQ 기능 대체 표).
- 각 아키텍처 결정마다 재검토 조건을 명시한다. 의존성 최소화는 현재 처리량 규모와 요구사항에 맞춘 엔지니어링 선택이며, 트래픽이나 요구 조건이 임계치를 넘으면 전용 구성 요소를 도입한다.

### 채택한 외부 의존성

| 의존성                                                   | 채택 사유                                                    |
| -------------------------------------------------------- | ------------------------------------------------------------ |
| `drizzle-orm`, `pg` (개발: `drizzle-kit`)                | DB 접근 및 스키마 마이그레이션(ADR-0036)                     |
| `@nestjs/config`, `class-validator`, `class-transformer` | 환경변수 설정 및 요청 입력 검증(ADR-0030, ADR-0037)          |
| `@nestjs/swagger`                                        | OpenAPI 문서 자동 생성(ADR-0037)                             |
| `prom-client`                                            | Prometheus 메트릭 수집 및 노출(ADR-0027)                     |
| 개발 의존성: Jest, Stryker, ESLint, Prettier             | 테스트, 변이 테스팅(ADR-0034, ADR-0035), 정적 분석 및 포매팅 |

## 검토한 대안

- **기능별 전용 도구 도입(BullMQ, Redis 기반 Rate Limiter 등)**: 애플리케이션 코드 작성량은 줄어들지만 발송 상태와 제어 정보가 여러 저장소에 분산된다. 결과적으로 중복 및 누락 방지 문제가 이기종 시스템 간 분산 상태 동기화 문제로 전환된다.
