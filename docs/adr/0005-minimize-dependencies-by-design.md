# 의존성은 의도적으로 최소화한다

이 프로젝트의 설계 원칙이다. 새 구성 요소(인프라, 라이브러리, 간접 계층)는 이미 의존하는 시스템(OS, PostgreSQL, Node.js 표준 기능, NestJS)이 보장하는 성질로 해결할 수 없을 때만 추가한다. 흔히 쓰는 도구를 몰라서 빼는 것이 아니다. 그 도구가 주는 기능을 하나씩 확인하고, 각각을 이미 가진 것으로 대체할 수 있을 때 뺀다.

## 이유

- 구성 요소가 하나 늘 때마다 장애 지점, 운영 대상(설정·백업·모니터링·장애 조치), 그리고 시스템끼리 상태가 엇갈릴 가능성이 함께 는다.
- 동시성과 장애 처리의 정합성은 "무엇을 끝까지 믿는가"로 결정된다. 믿는 대상이 하나면 판단이 경합하지 않는다.
- 이미 쓰는 시스템의 기저 원리(커널이 죽은 프로세스의 소켓을 닫는다, Postgres가 끝난 세션의 잠금을 푼다)에 기댄 설계는 따로 증명할 것이 적다.

## 적용 방법

- 흔한 대안을 기각할 때는 ADR에 그 도구가 주는 기능과 우리가 대신 쓰는 수단을 나란히 적는다(예: ADR-0003의 BullMQ 대응표).
- 각 결정에 "다시 볼 조건"을 적는다. 최소화는 고집이 아니라 현재 규모에 맞춘 선택이며, 조건이 바뀌면 구성 요소를 추가한다.

## 검토한 후보

- **각 기능마다 검증된 전용 도구 채택(BullMQ, Redis 기반 rate limiter 등)**: 직접 짤 코드는 줄지만 상태가 여러 시스템에 흩어진다. 이 과제의 핵심인 중복·누락 방지가 시스템 간 동기화 문제로 바뀐다.
