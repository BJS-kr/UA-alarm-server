# PostgreSQL 하나로 발송 상태·작업 큐·처리량 제한을 처리 (Redis, BullMQ 미사용)

수신자별 발송 상태는 조회 요구사항 때문에 영속 DB에 있어야 한다. 그 행 자체를 작업 큐로 쓰면 남은 일이 한 곳에만 존재한다. 외부 API 상한이 초당 50건이라 DB 부하도 작다. 그래서 별도 큐나 Redis를 두지 않는다. 워커는 `FOR UPDATE SKIP LOCKED`로 Delivery를 작게(10건 내외) 묶어 꺼내고, 긴급 알림은 꺼내는 정렬 순서로 앞에 선다.

BullMQ와 Redis가 주는 기능을 검토한 뒤 의도적으로 뺐다(ADR-0005).

## BullMQ가 주는 기능과 대체 수단

| 기능 | BullMQ | 이 프로젝트 |
| --- | --- | --- |
| 우선순위 | `priority` 옵션 | 꺼내는 쿼리의 `ORDER BY priority` |
| 재시도와 백오프 | `attempts`, `backoff` | Delivery의 다음 시도 시각 컬럼 |
| 여러 워커 분배 | 내장 | `FOR UPDATE SKIP LOCKED` |
| 크래시 복구 | 시간 기반 잠금 갱신(stalled job을 그대로 재실행) | 건마다 적은 기한(리스). 넘겨받은 건은 조회한 뒤에만 다시 보내고, 늦은 쓰기는 펜싱으로 막는다(ADR-0004) |
| 전역 처리량 제한 | 큐 단위 limiter | PG 기반 카운터 (처리량 제한 결정에서 정함) |

## 외부 저장소를 두지 않은 이유

1. **원본이 하나다.** 큐와 DB를 함께 쓰면 발송 시작(행 삽입과 작업 적재), 완료(DB 기록과 큐 완료 처리), 취소(DB와 큐에 남은 작업) 각각에서 둘이 어긋날 수 있고, 이를 맞추는 코드가 따로 필요하다. 결국 워커가 작업마다 DB를 확인하게 되어 큐는 중복 정보가 된다.
2. **부하가 작다.** 외부 상한 초당 50건이 전체 처리량의 상한이다. 실측(초당 49건 발송)에서 커밋은 워커 2대 초당 280회, 3대 340회였고 처리량에 영향이 없었다. 처음에는 묶어서 꺼내므로 초당 수십 건으로 봤지만, 토큰이 한 개 남짓씩 나가서 꺼내기도 거의 한 건씩이다(ADR-0009).
3. **판정자가 하나다.** 워커 생존 판정(ADR-0004)을 DB 하나가 하므로 두 시스템의 판단이 엇갈릴 일이 없다.
4. **운영 대상이 하나 줄어든다.** Redis의 영속성 설정, 백업, 장애 조치, 모니터링이 필요 없다.
5. **처리량 카운터는 PG로 충분하다.** 잃어도 잠깐의 429로 끝나는 가벼운 상태이다. 갱신은 워커 수에 비례해 실측 초당 160~210회(워커 2~3대)였고, 행 하나의 HOT 갱신이라 처리량에 영향이 없었다. 구체 방식은 처리량 제한 결정에서 정한다.

## 검토한 후보

- **BullMQ(Redis) 큐 + PG 상태**: 우선순위·재시도·크래시 복구가 내장돼 있다. 그러나 1번의 이중 기록 문제가 생기고, 크래시 복구가 시간 기반 잠금이라 이벤트 루프가 막히면 같은 작업이 두 번 실행될 수 있다(공식 문서의 stalled job 경고). ADR-0004에서 기각한 방식과 같다.
- **워커 메모리 큐 + 장애 시 재적재**: 워커가 죽으면 큐가 사라지고, 재적재하려면 어디까지 보냈는지 DB를 봐야 하므로 결국 DB가 원본이다.
- **PG 큐 확장(pgmq)**: 디스크 기반이지만 메시지가 확장의 자체 테이블에 있어, 수신자별 상태와 남은 일이 다시 두 곳에 나뉜다. 크래시 복구가 visibility timeout(시간 기반 리스)이며, 공식 postgres 이미지에 들어 있지 않다.
- **PG 큐 + 처리량 제한만 Redis**: 처리량 카운터도 PG로 충분해 구성 요소를 하나 더 둘 이유가 없다.

DB를 작업 큐로 쓰는 방식은 Rails 8 기본 큐(Solid Queue), pg-boss(Node), Oban(Elixir)과 같은 계열이다.

## 다시 볼 조건

외부 처리량이 초당 수천 건 단위로 커지거나 DB 조회 자체가 병목이 되면, 처리량 제한부터 Redis로 분리한다.
