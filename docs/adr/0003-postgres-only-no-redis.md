# ADR-0003. PostgreSQL 단일 저장소로 발송 상태, 작업 대기열, 처리량 제한을 처리한다 (Redis, BullMQ 미사용)

## 배경

발송 시스템은 흔히 상태 저장용 DB, 작업 대기열(BullMQ·Redis 등), 처리량 제한 카운터(Redis)를 별도 인프라로 분리한다.

그러나 수신자별 발송 결과를 조회해야 하는 요구사항상 수신자별 상태(`Delivery`)는 반드시 DB에 저장되어야 한다.

## 결정

`Delivery` 테이블 행을 작업 대기열로 직접 사용한다. 별도 큐나 Redis는 도입하지 않는다.

- 워커는 `FOR UPDATE SKIP LOCKED`로 `Delivery` 행을 점유(claim)한다. 다른 워커가 이미 잠근 행을 건너뛰고 선택하므로 여러 워커가 동시에 점유를 시도해도 동일 행을 중복 점유하지 않는다.
- 1회 점유 건수는 획득한 토큰 수만큼이며, 평시 1건 내외, 최대 10건이다(ADR-0009).
- 긴급 알림은 점유 쿼리의 정렬 순서(`ORDER BY`)를 통해 우선 처리된다(ADR-0011).

BullMQ와 Redis가 제공하는 기능을 검토한 결과 모두 PostgreSQL로 대체 가능하여 의존성에서 제외했다(ADR-0005).

## 상세: BullMQ 기능과 대체 수단

| 기능                | BullMQ                                    | 본 프로젝트 (PostgreSQL)                                                                                                        |
| ------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 우선순위            | `priority` 옵션                           | 점유 쿼리의 `ORDER BY priority`                                                                                                 |
| 재시도 및 백오프    | `attempts`, `backoff`                     | `Delivery`의 다음 시도 시각 컬럼                                                                                                |
| 다중 워커 작업 분배 | 내장                                      | `FOR UPDATE SKIP LOCKED`                                                                                                        |
| 워커 장애 복구      | 시간 기반 잠금(멈춘 작업을 그대로 재실행) | 건별 리스 만료 시각(`lease_until`). 인계(Takeover)한 건은 발송 내역 조회 후에만 재발송하고, 지연 쓰기는 펜싱으로 차단(ADR-0004) |
| 전역 처리량 제한    | 큐 단위 limiter                           | PG 단일 행 토큰 버킷(ADR-0009)                                                                                                  |

## 근거

1. **단일 원본(Single Source of Truth) 유지**: 큐와 DB를 병행하면 발송 시작, 완료, 취소 시점마다 두 저장소의 상태가 어긋날 수 있다. 예를 들어 DB에는 취소로 기록되었으나 큐에는 작업이 남아 있는 경우 이를 동기화하는 코드가 별도로 필요하며, 결국 워커가 작업마다 DB를 다시 확인하게 되어 큐는 중복 정보가 된다.
2. **낮은 DB 부하**: 전역 처리량은 외부 API 상한인 초당 50건을 넘지 않는다. 초당 49건 발송 기준 DB 커밋은 워커 2대에서 초당 185회, 3대에서 초당 221회로 측정되었으며 처리량 저하가 없었다.
3. **단일 판단 기준**: 리스 만료, 우선순위 순서, 처리량 제한을 모두 DB 행과 DB 시계 하나로 판단하므로 시스템 간 판단 불일치가 발생하지 않는다.
4. **운영 요소 감소**: Redis의 영속성 설정, 백업, 장애 조치, 모니터링이 불필요하다.
5. **PG 기반 처리량 카운터의 충분성**: 토큰 버킷 행 갱신은 초당 72~94회(워커 2~3대) 수준이며, 인덱스를 수정하지 않는 HOT(Heap-Only Tuple) 갱신으로 처리되어 성능 영향이 없다.

DB를 작업 대기열로 사용하는 방식은 Solid Queue(Rails 8 기본 큐), pg-boss(Node.js), Oban(Elixir)과 동일한 아키텍처 계열이다.

## 검토한 대안

- **BullMQ(Redis) 큐 + PG 상태 저장**: 우선순위, 재시도, 복구 기능을 내장하고 있으나 이중 기록 문제가 발생한다. 복구 메커니즘도 시간 기반 잠금 방식이라 이벤트 루프가 블로킹되면 동일 작업이 중복 실행될 수 있다(공식 문서의 stalled job 경고). 리스 만료 방식을 쓰더라도 중복 발송을 막기 위한 발송 내역 조회와 펜싱 장치는 직접 구현해야 한다.
- **워커 메모리 큐 + 장애 시 재적재**: 워커 종료 시 메모리 큐가 소실되며, 재적재를 위해 어디까지 발송했는지 DB를 조회해야 하므로 결국 DB가 원본이 된다.
- **PG 큐 확장(`pgmq`)**: 메시지가 확장 모듈 자체 테이블에 저장되어 수신자별 상태와 대기 작업이 다시 두 곳으로 분리된다. 공식 `postgres` 이미지에도 기본 포함되지 않는다.
- **PG 큐 + 처리량 제한만 Redis 사용**: 처리량 카운터 역시 PG로 충분하므로 인프라 구성 요소를 추가할 이유가 없다.

## 재검토 조건

외부 처리량 상한이 초당 수천 건 단위로 증가하거나 DB가 병목이 되면 처리량 제한기부터 Redis로 분리한다.
