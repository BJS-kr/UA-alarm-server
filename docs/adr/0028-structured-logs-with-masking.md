# ADR-0028. 표준 출력 JSON 구조화 로깅 및 민감정보 마스킹

## 배경

로그는 장애 원인 분석 시 가장 먼저 확인하는 자료다. 그러나 알림 본문에는 인증번호나 카드번호 같은 민감한 숫자가 포함될 수 있고, DB 오류 메시지에는 실패한 SQL 문장의 파라미터 값이 그대로 노출된다. 디버깅에 필요한 맥락을 유지하면서 민감정보 유출을 차단해야 한다.

## 결정

- NestJS 기본 로거(`ConsoleLogger`)의 JSON 모드를 사용하여 표준 출력(stdout)에 기록한다. NestJS 11부터 기본 제공되므로 `pino` 같은 별도 의존성을 추가하지 않는다(ADR-0005).
- 기본 로거를 얇게 래핑하여 `AsyncLocalStorage`에 저장된 `traceId`, `alarmId`, `deliveryId`를 모든 로그 줄에 자동으로 포함시킨다.
- 로그 파일은 생성하지 않으며, 로그 수집 및 보관은 실행 플랫폼에 위임한다.
- 민감정보 마스킹(masking)은 로거 계층 한 곳에서 일괄 처리하여 호출부에서의 누락을 방지한다.
- 로그 메시지와 오류 메시지(예외, API 오류 응답, 입력 검증 사유)는 영어로 작성한다. 로그 수집·검색 도구 및 외부 연동에서 다루기 쉽고 운영자가 원문 그대로 검색어로 사용할 수 있기 때문이다. 코드 주석과 문서는 한국어로 작성한다.

## 상세

### 로그 레벨별 기록 내용

| 레벨    | 기록 내용                                                                                                                                       |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `info`  | API 요청 요약 1줄(메서드, 경로, 상태 코드, 소요 시간), 알림의 주요 상태 변화(발송 시작, 수신자 확장 완료, 취소, 완료)                           |
| `warn`  | 일시적 오류 후 재시도, 결과 미확정(`UNCONFIRMED`) 전환, 429 응답 수신, 리스 만료 인계(Takeover)                                                 |
| `error` | 재시도 소진에 따른 최종 실패, 중복 발송 탐지, 서킷 브레이커 발동, 수신자 확장(Expansion) 중단                                                   |
| `debug` | 발송 시도마다 1줄: `alarmId`, `deliveryId`, `recipientId`, 시도 번호, 요청 본문(마스킹 적용), 응답 상태 코드, `messageId`, 소요 시간, 판정 결과 |

- **`info` 이상에서는 개별 성공 건을 기록하지 않는다.** 성공 여부, 시각, `messageId`는 Delivery 테이블에 저장되므로 대량 알림 1건당 10만 줄의 중복 로그가 발생하는 것을 방지한다.
- **`debug` 레벨은 Delivery 테이블과 중복되는 정보라도 생략 없이 모두 기록한다.** `LOG_LEVEL=debug`로 활성화한다.

### 마스킹(Masking) 규칙

민감정보는 필드를 통째로 제거하지 않고 마스킹하여 디버깅에 필요한 맥락을 보존한다.

| 대상                                                       | 마스킹 방식                                                                                                                                            |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 알림 본문                                                  | 4자리 이상 연속된 숫자를 동일 길이의 `*`로 치환한다(인증번호, 카드번호 등)                                                                             |
| 전화번호                                                   | 중간 자리를 마스킹한다(`010-****-2749`)                                                                                                                |
| 비밀 키(`password`, `token`, `authorization`, `apiKey` 등) | 값 전체를 마스킹한다                                                                                                                                   |
| 접속 주소의 비밀번호(`user:pw@host`)                       | 필드 이름과 무관하게 모든 문자열에서 비밀번호 구간만 마스킹한다                                                                                        |
| 오류 문자열(`message`, `stack`, `detail`, `cause`)         | 필드 이름과 무관하게 4자리 이상 연속된 숫자와 접속 주소의 비밀번호를 마스킹한다. 스택의 호출 위치 줄과 오류 코드(`code`, `errno` 등)는 그대로 유지한다 |

- **오류 객체는 문자열 내용을 기준으로 마스킹한다.** 오류 문자열(`message`, `stack`, `detail`, `cause`)은 외부 라이브러리와 드라이버가 생성한다. DB 드라이버와 Drizzle은 실패한 쿼리의 파라미터 값을 `message`나 `detail`에 포함시키므로(예: `params: …`, `Failing row contains (…)`), 본문과 수신자 정보가 필드 이름 없이 섞여 들어온다.
- **로그 메시지 문자열도 동일한 방식으로 마스킹한다.** 애플리케이션 자체 문장은 숫자가 없는 고정 문자열이므로 변경되지 않으며, 오류 객체를 첫 인자로 넘겨 오류 문자열이 곧 로그 메시지가 되는 경우를 처리하기 위함이다.
- 전화번호는 발송에 필요하지 않으므로 DB에 저장하지 않는다.

### 로그 수집 연동

애플리케이션은 표준 출력 JSON 기록까지만 담당한다. Docker 로그 드라이버, Fluent Bit, Loki, CloudWatch 등이 이 형식을 공통으로 지원하므로 코드 변경 없이 수집 파이프라인을 연결할 수 있다. 평가 및 개발 환경에서는 `docker compose logs`로 확인하고 `deliveryId` 등으로 검색한다.

## 검토한 대안

- **pino(`nestjs-pino`)**: 처리 성능은 더 높지만, 본 시스템의 로그 발생량은 초당 수백 줄 수준이므로 기본 로거로 충분하다.
- **민감정보 포함 필드 전체 생략**: 디버깅에 필요한 주변 맥락까지 함께 소실된다.
- **성공 건도 `info` 레벨로 기록**: Delivery 테이블과 동일한 내용이 알림당 10만 줄씩 중복 출력된다.
