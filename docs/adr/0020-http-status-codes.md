# ADR-0020. HTTP 상태 코드 매핑 규칙

## 배경

클라이언트가 HTTP 상태 코드만으로 오류 원인과 재시도 가능 여부를 판단할 수 있어야 한다. 특히 발송 시작과 취소는 응답 시점에 비동기 후속 작업이 진행 중일 수 있으므로 상태 완료 여부에 따른 응답 코드를 명확히 구분해야 한다.

## 결정

| 상황                                                                                                   | 상태 코드                               |
| ------------------------------------------------------------------------------------------------------ | --------------------------------------- |
| 알림 생성 성공                                                                                         | `201 Created` + `Location` 헤더         |
| 조회 성공                                                                                              | `200 OK`                                |
| 발송 시작 또는 취소 요청 후 비동기 처리 진행 중(`SENDING`, `CANCELING`)                                | `202 Accepted`                          |
| 발송 시작 또는 취소 요청 시점에 이미 종료 상태 도달(`COMPLETED`, `CANCELED`)                           | `200 OK`                                |
| 요청 형식·값 검증 실패(JSON 파싱 실패, 필수 필드 누락, 길이 초과, 긴급 수신자 규칙 위반, ID 형식 오류) | `400 Bad Request`                       |
| 인증 실패(ADR-0033)                                                                                    | `401 Unauthorized`                      |
| 존재하지 않는 알림 ID 또는 미정의 경로                                                                 | `404 Not Found`                         |
| 정의된 경로에 허용되지 않은 HTTP 메서드 호출(예: `DELETE /v1/alarms`)                                  | `405 Method Not Allowed` + `Allow` 헤더 |
| 현재 알림 상태에서 허용되지 않는 전이 요청(취소된 알림 시작, 완료된 알림 취소)                         | `409 Conflict`                          |
| 요청 본문 크기 제한 초과                                                                               | `413 Content Too Large`                 |
| `Content-Type`이 JSON이 아님                                                                           | `415 Unsupported Media Type`            |
| 예기치 않은 서버 내부 오류                                                                             | `500 Internal Server Error`             |
| DB 연결 불가 등 일시적 처리 불가 상태                                                                  | `503 Service Unavailable`               |

## 근거

- **`202`와 `200`은 응답 시점의 작업 종결 여부로 구분한다**: 발송 시작(`SENDING`)과 발송 중 취소(`CANCELING`)는 비동기 작업이 남아 있으므로 `202`를 반환한다. `CREATED` 상태에서의 즉시 취소(`CANCELED`)나 이미 `COMPLETED`된 알림에 대한 멱등 재시작 요청은 후속 작업이 없으므로 `200`을 반환한다.
- **요청 검증 실패는 `400`으로 통일한다**: 개별 필드의 검증 실패 사유는 Problem Details 응답의 `errors` 배열에 명시한다(ADR-0019).
- **미허용 메서드는 `405`로 응답한다**: 경로가 존재할 때 `404`를 반환하면 클라이언트가 URL 오타로 오인할 수 있다. `405`와 `Allow` 헤더로 허용 메서드를 명시하며, 허용 메서드 목록은 OpenAPI 정의에서 자동 추출하여 경로 추가 시 별도 수정이 필요 없도록 한다.
- **비 JSON 본문은 `415`로 구분한다**: 서버는 JSON 본문만 파싱한다. 다른 미디어 타입을 `415`로 차단하지 않으면 본문이 빈 객체로 처리되어 필수 필드 누락(`400`)이라는 부정확한 오류가 반환된다.

## 검토한 대안

- **문법 오류는 `400`, 도메인 규칙 위반은 `422`로 분리**: 제목 길이 초과 등 두 범주의 경계가 모호하며, 상세 원인은 `errors` 필드로 전달되므로 상태 코드를 세분화할 실익이 없다.
