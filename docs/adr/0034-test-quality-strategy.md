# ADR-0034. ADR 보장 기반의 테스트 품질 기준 및 다중 검증 체계

## 배경

단순 라인 커버리지 기준만으로는 코드는 실행되지만 핵심 불변식을 실제로 검증하지 않는 테스트를 걸러내기 어렵다. 특히 분산 동시성 제어와 장애 복구 로직은 각 설계 결정(ADR)이 보장하는 불변식이 깨졌을 때 테스트가 확실히 실패하는지 확인해야 한다.

## 결정

유효한 테스트의 기준을 명시하고, 이를 객관적으로 검증하는 다중 검증 체계를 둔다.

## 상세

### 유효한 테스트의 기준

1. **ADR의 보장 사항 1개를 검증한다.** 테스트 이름이 곧 해당 보장 문장이다.
2. **해당 보장이 깨지면 반드시 실패한다.** 실패를 확인하지 않은 테스트는 신뢰하지 않는다.
3. **외부에서 관측 가능한 결과로 검증한다.** API 응답, DB 상태, 외부 API가 실제로 수신한 요청으로 검증한다. 애플리케이션 내부 구현을 대역(mock)으로 대체하여 호출 여부만 확인하는 테스트는 인정하지 않는다.
4. **실행 결과가 항상 동일해야 한다.** 시간과 무작위 값(지터)은 주입할 수 있게 설계하고, 시간 임계값은 설정으로 단축하여 실제 시간으로 빠르게 실행한다.

### 검증 체계

| 단계                            | 대상                                                                                                      | 검증 방법                                                                                                                                                                                                                                        |
| ------------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1. 결정 → 보장 → 테스트 대응표  | 모든 ADR                                                                                                  | ADR마다 보장 사항을 도출하고, 보장이 깨질 때 실패하는 테스트를 연결한다. 보장이 없는 테스트와 테스트가 누락된 보장이 드러난다([requirements.md](../requirements.md))                                                                             |
| 2. 변이 테스팅(Stryker)         | TypeScript 순수 로직: 재시도 간격, 응답 분류, 서킷 브레이커 판정, 상태 전이표, 마스킹(masking), 입력 검증 | 변이 도구가 코드를 미세하게 변경(변이)했을 때 테스트가 이를 감지하여 실패하는지 확인한다. 변이 점수 기준(90%)을 두고 생존한 변이를 전수 검토한다                                                                                                 |
| 3. ADR 기반 결함 주입(Sabotage) | SQL 및 동시성 제어                                                                                        | ADR마다 주입할 결함(예: 완료 판정의 알림 행 잠금 제거, 발송 결과 기록의 담당 워커 조건 제거, 점유(claim)의 알림 상태 조인 제거)과 그때 실패해야 할 테스트를 지정한다. 스크립트가 결함을 하나씩 주입하고 대상 테스트가 실제로 실패하는지 확인한다 |
| 4. 요구사항 기준 교차 검증      | 전체 구현 및 문서                                                                                         | 요구사항 대응표의 누락 여부, 생존 변이의 타당성, 결함 주입 검출 여부 및 실제 E2E 동작을 교차 검증한다(ADR-0038)                                                                                                                                  |

검증 결과는 [testing.md](../testing.md)에 기록한다.

### 3단계(결함 주입 검증)가 필요한 근거

본 시스템의 정확성은 대부분 SQL 문장(조건부 상태 전이, `SKIP LOCKED`, 알림 행 잠금과 `NOT EXISTS`, 담당 워커 펜싱 조건)에 의존한다. TypeScript 변이 도구는 SQL을 일반 문자열로 취급하여 빈 문자열로 치환하는 수준의 변이만 수행하며, `SKIP LOCKED` 제거나 조건 누락 같은 의미 있는 결함을 생성하지 못한다. 따라서 변이 점수가 높아도 중복과 누락을 방지하는 핵심 쿼리는 검증되지 않을 수 있다. SQL과 동시성 영역은 ADR에서 도출한 결함 주입 목록을 통해 동일한 수준의 검증을 수행한다.

### 의존성

Stryker(`@stryker-mutator/core` 및 Jest 러너 플러그인)를 개발 의존성으로 추가한다.

## 검토한 대안

- **코드 커버리지 단일 기준**: 실행만 하고 결과를 검증하지 않는 테스트도 커버리지 수치를 채운다.
- **변이 테스팅 단독 적용**: SQL과 동시성 제어라는 시스템의 핵심 영역을 검증하지 못한다.
