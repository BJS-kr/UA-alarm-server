# ADR-0034. 테스트의 품질은 커버리지가 아니라 "ADR의 보장을 지키는가"로 판정하고, 네 층으로 검증한다

## 결정

구현은 에이전트가 하고, 결과물은 맥락을 모르는 별도 에이전트가 심사한다. 테스트를 쓰라고만 하면 의미 없는 테스트가 나오기 쉽다. 그래서 좋은 테스트의 기준과, 그것을 객관적으로 확인하는 장치를 함께 둔다.

## 좋은 테스트의 기준

1. **ADR의 보장 하나를 지킨다.** 테스트 이름이 곧 그 보장 문장이다.
2. **그 보장을 깨면 실패한다.** 실패하는 것을 본 적 없는 테스트는 믿지 않는다.
3. **밖에서 보이는 결과로 확인한다.** API 응답, DB 상태, 외부 API가 실제로 받은 요청으로 확인한다. 우리 코드 내부를 모킹해서 호출 여부를 보는 테스트는 인정하지 않는다.
4. **결과가 매번 같다.** 시간과 무작위 값(지터)은 주입할 수 있게 하고, 시간 기준값은 설정으로 짧게 줄여 실제 시간으로 빠르게 돌린다.

## 네 층의 검증

| 층 | 대상 | 방법 |
| --- | --- | --- |
| 1. 결정 → 보장 → 테스트 대응표 | 모든 ADR | ADR마다 보장을 한 줄씩 뽑고, 깨지면 실패하는 테스트를 잇는다. 보장 없는 테스트와 테스트 없는 보장이 드러난다([requirements.md](../requirements.md)) |
| 2. 변이 테스팅(Stryker) | TS 순수 로직: 재시도 간격, 응답 분류, 서킷 브레이커 판정, 상태 전이표, 마스킹, 입력 검증 | 코드를 자동으로 조금씩 바꿔(변이) 테스트가 잡는지 본다. 점수 기준(90%)을 두고, 살아남은 변이를 하나씩 검토한다 |
| 3. ADR에서 뽑은 고의 결함 목록 | SQL과 동시성 | ADR마다 깨뜨려 볼 결함(예: 완료 판정의 알림 행 잠금 제거, 결과 기록의 owner 조건 제거, 꺼내기의 알림 상태 조인 제거)과 그때 실패해야 할 테스트를 정해 둔다. 스크립트가 결함을 하나씩 넣고 그 테스트가 실제로 실패하는지 확인한다 |
| 4. 독립 심사 에이전트 | 위 결과 전체 | 구현 맥락 없이 명세, ADR, 코드, 테스트만 보고 대응표의 빈칸, 살아남은 변이의 정당성, 고의 결함의 검출 여부를 판정한다(ADR-0038) |

결과는 [testing.md](../testing.md)에 있다.

## 3층이 필요한 이유

이 시스템의 정확성은 대부분 SQL 문장(조건부 전이, `SKIP LOCKED`, 알림 행 잠금과 `NOT EXISTS`, owner 조건)에 있다. TS 변이 도구는 SQL을 문자열로만 다뤄서 빈 문자열로 바꾸는 정도이고, `SKIP LOCKED` 제거나 조건 누락 같은 의미 있는 결함을 만들지 못한다. 변이 점수가 높아도 중복과 누락을 막는 핵심이 검증되지 않았을 수 있다. 그래서 SQL과 동시성은 ADR에서 뽑은 결함 목록으로, 사람이 고른 범위에서 같은 검증을 한다.

## 의존성

Stryker(`@stryker-mutator/core`와 Jest 러너 플러그인)를 개발 의존성으로 더한다.

## 검토한 후보

- **커버리지 기준**: 실행만 하고 확인하지 않는 테스트도 커버리지를 채운다.
- **변이 테스팅만으로 판정**: SQL과 동시성이라는 이 시스템의 핵심을 보지 못한다.
