# ADR-0021. 알림 생성은 엄격하게 검증하고, 제목은 보내지 않고 관리용 이름으로 쓴다

```json
POST /v1/alarms
{ "type": "URGENT", "title": "결제 안내", "body": "결제가 완료되었습니다.", "recipientIds": ["u_000001"] }
```

## 결정 1: 실수 한 번으로 전체 사용자에게 나가는 것을 막는다

- **`type`은 필수이고 기본값이 없다.** 기본값이 BULK면 필드를 빠뜨리는 것만으로 10만 명에게 나간다.
- **모르는 필드는 400으로 거절한다.** `recipientIDs` 같은 오타를 조용히 무시하면, 클라이언트는 수신자를 지정했다고 믿는데 서버는 지정이 없는 요청으로 처리한다.
- **BULK에 `recipientIds`가 있으면 거절한다.** 지정한 사람에게만 보내려다 전체로 나가는 사고를 막는다.

## 결정 2: 나머지 검증

| 필드 | 규칙 |
| --- | --- |
| `title` | 1~100자, 공백만 있으면 거절 |
| `body` | 1~1000자, 공백만 있으면 거절 |
| `recipientIds` (URGENT 전용, 필수) | 1~100개, 각 1~64자, 중복이 있으면 거절 |

- **글자 수는 코드 포인트로 센다.** DB의 CHECK(`char_length`)와 같은 기준이어야, 검증을 통과한 값이 저장할 때 거절되지 않는다. class-validator의 `Length`는 이모지 변형 선택자(U+FE0F)를 빼고 세서 `❤️` 51개(코드 포인트 102개)를 100자로 통과시켰고, DB가 거절해 500이 났다.
- **NUL(U+0000)이 든 문자열은 거절한다.** Postgres의 text에 담을 수 없어 저장할 때 500이 된다. 수신자 목록의 커서도 같다.
- **중복 수신자는 합치지 않고 거절한다.** 중복은 클라이언트 쪽 버그의 신호다.
- **수신자가 실제로 있는지는 생성할 때 확인하지 않는다.** 사용자 API에 단건 조회가 없어서, 확인하려면 전체를 넘겨 봐야 한다. 없는 수신자는 발송할 때 `UNKNOWN_RECIPIENT`로 실패하고 Delivery에 남는다.

## 결정 3: 제목은 보내지 않는다 (모호한 부분의 해석)

외부 발송 API에는 `body`만 있고 `title` 필드가 없다. 그래서 본문만 보내고, 제목은 목록과 조회에서 알림을 구별하는 관리용 이름으로 쓴다. 외부 계약에 없는 필드를 서버가 마음대로 본문에 섞지 않는다. 이 해석은 README에도 적었다.

## 검토한 후보

- **제목과 본문을 합쳐 발송(`[제목] 본문`)**: 메시지 형식을 서버가 마음대로 정하는 셈이고, 제목이 필요 없는 알림(인증번호 등)에도 붙는다.
- **`type` 기본값 BULK**: 필드 하나를 빠뜨리면 전체 발송이 된다.
- **중복 수신자 자동 제거**: 클라이언트 버그를 숨긴다.
