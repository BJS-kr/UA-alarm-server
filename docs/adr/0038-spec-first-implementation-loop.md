# ADR-0038. 원본 명세 기준의 구현-독립 심사 반복 루프

## 배경

구현은 에이전트가 수행한다. 작업이 길어질수록 대화 맥락이 누적되고, 자체 해석으로 인해 최초 요구 명세에서 벗어나기 쉽다. 동일한 에이전트가 스스로 검증하면 동일한 해석을 반복하여 누락이나 오류를 놓치게 된다.

## 결정

판정 기준점을 고정하고, 매 회차 새로운 컨텍스트에서 원본 명세부터 대조하는 독립 심사를 반복한다.

```
구현 에이전트: 구현 → 1차 완료
  → 심사 에이전트(새 컨텍스트)를 기동해 심사 기준 전달
  → 지적 사항 반영 → 재심사 … 최대 N회, 차단(blocking) 지적이 0건이면 조기 종료
  → 완료 보고
```

- 심사 에이전트는 구현 과정의 대화 이력 없이 코드, 문서, 실행 결과만 입력받는다. 회차마다 새로운 컨텍스트로 시작하므로 구현 에이전트에 누적된 해석이 심사에 섞이지 않는다.
- 심사 기준은 [review-criteria.md](../review-criteria.md)에 정의한다.
- 심사에서 ADR 자체의 결함이 드러나면 구현 에이전트는 임의로 수정하지 않고 작업을 중단한 뒤 사용자에게 보고한다. 아키텍처 결정은 사람이 내린다.
- 작업 흐름과 중단·보고 조건은 저장소의 에이전트 지침(`CLAUDE.md`)에 명시한다.

## 상세

### 문서 우선순위

```
원본 과제 명세 > ADR > CONTEXT.md > 구현 계획
```

ADR이 원본 명세와 충돌하면 ADR이 잘못된 것이다. 에이전트는 작업을 중단하고 보고하며, ADR로 명세를 덮어쓰지 않는다.

### 요구사항부터 테스트까지의 추적 대응

```
명세의 요구사항(R·O·S ID) → ADR → 보장 → 테스트
```

[requirements.md](../requirements.md)가 요구사항, ADR, 테스트를 연결한다. ADR-0034의 "결정 → 보장 → 테스트" 대응표 앞에 요구사항 ID를 결합한 구조다. 심사 에이전트는 요구사항에서 출발해 추적하므로 누락된 요구사항과 범위를 벗어난 구현이 함께 식별된다.

### 원본 명세의 분리 보관

과제 명세는 외부 공개 및 제3자 공유가 금지된 자료이고, 제출물은 공개 저장소다. 따라서 원본 명세는 Git 추적에서 제외한 로컬 파일(`.local/assignment.md`)로 두어 에이전트만 읽게 한다. 저장소에는 자체 문장으로 요약한 요구사항 대응표만 커밋하며, 원본 명세의 문장을 커밋 대상 파일에 그대로 옮겨 적지 않는다.
