# 구현은 "구현 → 독립 심사 → 개선"을 반복하며, 원본 과제 명세를 기준점으로 삼는다

구현은 에이전트가 하고, 작업이 길어질수록 컨텍스트가 쌓여 요구된 명세에서 멀어지기 쉽다. 그래서 무엇이 기준인지를 고정하고, 매번 새 컨텍스트에서 명세부터 확인하는 심사를 반복한다.

## 작업 흐름

```
구현 에이전트: 구현 → 1차 완료
  → 심사 에이전트(새 컨텍스트)를 띄워 심사 기준 전달
  → 지적 반영 → 다시 심사 … 최대 N회, 차단 지적 0건이면 조기 종료
  → 완료 보고
```

- 심사 에이전트는 구현 과정의 대화 없이 코드, 문서, 실행 결과만 받는다. 매 회차 새로 시작하므로 구현 에이전트의 컨텍스트에 쌓인 해석이 심사에 섞이지 않는다.
- 심사 기준은 [review-criteria.md](../review-criteria.md)에 둔다.
- 심사에서 ADR 자체의 문제가 드러나면 구현 에이전트는 고치지 않고 멈춘 뒤 사용자에게 보고한다.

## 우선순위

```
원본 과제 명세 > ADR > CONTEXT.md > 구현 계획
```

ADR이 명세와 부딪히면 ADR이 틀린 것이다. 에이전트는 작업을 멈추고 보고하며, ADR로 명세를 덮어쓰지 않는다.

## 요구사항부터 테스트까지의 대응

```
명세 요구사항(R·O·S ID) → ADR → 보장 → 테스트
```

[requirements.md](../requirements.md)에 요구사항과 ADR을 잇고, 테스트 열은 구현하면서 채운다. ADR-0034의 "결정 → 보장 → 테스트" 대응표 앞에 요구사항을 붙인 것이다. 심사 에이전트는 요구사항에서 출발해 따라가므로, 빠뜨린 요구사항과 범위를 넘은 구현이 함께 드러난다.

작업 흐름과 멈추고 보고할 조건은 저장소의 에이전트 지침(`CLAUDE.md`)에 둔다.

## 원본 명세의 보관

과제는 외부 공개와 제3자 공유가 금지된 자료인데, 제출물은 공개 저장소다. 그래서 원본 명세는 git에서 제외한 로컬 파일(`.local/assignment.md`)로 두어 에이전트만 읽게 하고, 저장소에는 우리 말로 요약한 요구사항 대응표만 커밋한다.
