# ADR-0038. 구현은 "구현 → 독립 심사 → 개선"을 되풀이하며, 원본 과제 명세를 기준점으로 삼는다

## 결정

구현은 에이전트가 한다. 작업이 길어질수록 컨텍스트가 쌓여 요구된 명세에서 멀어지기 쉽다. 그래서 무엇이 기준인지를 고정하고, 매번 새 컨텍스트에서 명세부터 확인하는 심사를 되풀이한다.

```
구현 에이전트: 구현 → 1차 완료
  → 심사 에이전트(새 컨텍스트)를 띄워 심사 기준을 넘김
  → 지적 반영 → 다시 심사 … 최대 N회, 막는 지적이 0건이면 일찍 끝냄
  → 완료 보고
```

- 심사 에이전트는 구현 과정의 대화 없이 코드, 문서, 실행 결과만 받는다. 회차마다 새로 시작하므로, 구현 에이전트의 컨텍스트에 쌓인 해석이 심사에 섞이지 않는다.
- 심사 기준은 [review-criteria.md](../review-criteria.md)에 있다.
- 심사에서 ADR 자체의 문제가 드러나면, 구현 에이전트는 고치지 않고 멈춘 뒤 사람에게 보고한다. 결정은 사람이 내린다.
- 작업 흐름과 멈추고 보고할 조건은 저장소의 에이전트 지침(`CLAUDE.md`)에 있다.

## 우선순위

```
원본 과제 명세 > ADR > CONTEXT.md > 구현 계획
```

ADR이 명세와 부딪히면 ADR이 틀린 것이다. 에이전트는 멈추고 보고하며, ADR로 명세를 덮어쓰지 않는다.

## 요구사항부터 테스트까지의 대응

```
명세의 요구사항(R·O·S ID) → ADR → 보장 → 테스트
```

[requirements.md](../requirements.md)가 요구사항과 ADR과 테스트를 잇는다. ADR-0034의 "결정 → 보장 → 테스트" 대응표 앞에 요구사항을 붙인 것이다. 심사 에이전트는 요구사항에서 출발해 따라가므로, 빠뜨린 요구사항과 범위를 넘은 구현이 함께 드러난다.

## 원본 명세의 보관

과제는 외부 공개와 제3자 공유가 금지된 자료이고, 제출물은 공개 저장소다. 그래서 원본 명세는 git에서 뺀 로컬 파일(`.local/assignment.md`)로 두어 에이전트만 읽게 하고, 저장소에는 우리 말로 요약한 요구사항 대응표만 커밋한다. 명세의 문장을 커밋되는 파일에 옮겨 적지 않는다.
