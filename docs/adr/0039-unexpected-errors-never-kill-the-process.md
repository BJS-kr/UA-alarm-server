# ADR-0039. 최상위 경계 기반의 예외 격리 및 DB 타임아웃을 통한 요청 종료 보장

## 배경

프로세스가 예기치 않은 오류로 인해 아무 기록 없이 종료되면 장애 원인을 파악할 수 없다. 반대로 오류 처리를 모듈마다 개별 작성하면 한 곳만 누락되어도 프로세스가 종료된다. 또한 DB가 응답하지 않을 때 쿼리가 무한 대기하면 클라이언트는 응답을 받지 못한다.

## 결정

예기치 않은 오류는 최상위 경계(진입점)에서 포착하여 로그와 메트릭으로 기록하고 프로세스 실행을 유지한다. 의도적으로 프로세스를 종료하는 경우는 기동 단계에서 초기화에 실패했을 때뿐이다.

## 상세

### 최상위 경계(진입점)에서의 일괄 오류 포착

개별 모듈 곳곳에 중복 `try/catch`를 두지 않고, 오류가 전파되는 최상위 경계(진입점)마다 한 번씩 동일한 방식으로 포착한다.

| 최상위 경계(진입점)              | 처리 방식                                                                                                                                                                                                                                 |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 프로세스                         | `api`와 `worker` 기동 시 `unhandledRejection`, `uncaughtException` 핸들러를 등록한다. `error` 로그를 남기고 `alarm_unhandled_errors_total`을 증가시킨 뒤 실행을 유지한다                                                                  |
| HTTP 요청                        | 전역 예외 필터가 모든 오류를 Problem Details로 변환한다(ADR-0019). 예기치 않은 오류는 `500`, DB 사용 불가는 `503`으로 응답한다                                                                                                            |
| `worker`의 작업 루프             | 5개 루프(발송, 발송 내역 조회, 수신자 확장, 취소 정리, 리스 만료 인계)가 공통 `PollingLoop`를 사용한다. 한 폴링 주기(사이클)가 오류로 종료되면 로그와 `alarm_loop_errors_total`을 남기고, 짧게 대기(sleep)한 뒤 다음 폴링 주기를 실행한다 |
| 루프 외부에서 실행되는 단건 발송 | 발송 작업을 등록하는 단일 진입점에서 예외를 포착한다. 단건 오류가 폴링 루프나 다른 처리 중인 건으로 전파되지 않는다                                                                                                                       |
| 관리 포트                        | 응답 본문을 끝까지 생성한 뒤 한 번에 전송한다. 생성 도중 실패하면 `503`으로 응답하고 로그를 남긴다                                                                                                                                        |

### DB 타임아웃을 통한 요청 종료 보장

- **`api`의 DB 풀에는 타임아웃 한도를 둔다.** 연결 대기 한도(`DB_ACQUIRE_TIMEOUT_MS`, 기본 5초)와 쿼리 응답 한도(`DB_QUERY_TIMEOUT_MS`, 기본 10초)다. 한도가 없으면 커넥션이 고갈되었을 때 요청이 응답 없이 무한 대기한다. 한도를 초과하면 `503`으로 응답한다. Drizzle은 드라이버 오류를 래핑하여 `cause`에 두므로, `503` 해당 여부는 `cause` 체인을 따라가며 판별한다.
- **쿼리 응답 한도를 10초로 설정한 근거**: API의 일반 쿼리는 모두 수십 ms 안에 완료된다. 다만 발송 시작과 취소는 알림 행을 갱신한다. 트랜잭션 도중 멈춘 워커가 해당 행 잠금을 점유 중이면, PostgreSQL이 해당 세션을 강제 종료할 때까지(트랜잭션 유휴 한도 5초) 대기해야 한다. 따라서 쿼리 응답 한도를 트랜잭션 유휴 한도보다 길게 두며, 이 대소 관계는 기동 시 검증한다(ADR-0030).
- **`worker`의 풀에는 클라이언트 측 타임아웃 한도를 두지 않는다.** 멈춘 워커가 점유 중인 알림 행 잠금이 해제되기를 대기하는 것은 정상 동작이며, 해당 잠금은 DB 서버 측 한도(트랜잭션 유휴 한도 5초)가 해제한다(ADR-0004).

### 의도적 프로세스 종료 조건

- **기동에 실패했을 때만 종료한다**(설정 검증 오류, 2분 내 DB 연결 실패 등). `fatal` 로그에 사유를 남기고 종료 코드 `1`로 종료한다. 작업을 시작할 수 없는 상태이며, 기동 단계이므로 처리 중이던 건이 없다.
- **처리 결과를 DB에 기록하지 못해도 프로세스를 종료하지 않는다.** DB 쓰기는 대기 간격을 늘려 가며 수회 재시도하고, 최종 실패하면 해당 오류를 루프의 최상위 경계가 포착하여 로그와 `alarm_loop_errors_total`로 기록한다. 결과를 기록하지 못한 건은 리스 만료 시각(`lease_until`)이 지나 다른 워커가 인계(Takeover)받는다(ADR-0004). 수신자 확장(Expansion)은 동일 커서부터 재개하고, 취소 정리는 리스 만료 후 다시 점유(claim)된다.
- `migrate`는 1회 실행 후 종료되는 작업이므로 실패 시 종료 코드 `1`로 종료한다.

### 미처리 예외 발생 후 실행을 유지하는 근거

Node.js는 `uncaughtException` 이후의 상태 정합성을 보장하지 않으나, 본 시스템은 실행을 유지하는 방식을 선택했다.

- 시스템의 데이터 정합성은 프로세스 메모리가 아니라 DB(조건부 쓰기, 펜싱)에 있다.
- 비정상 상태에 빠진 프로세스는 생존 확인(liveness check)이 감지한다. `worker`는 작업 루프가 30초 동안 실행되지 않으면 생존 확인이 실패하여 재시작 대상이 된다(ADR-0026).
- 기록 없이 즉시 종료되는 것보다, 오류 로그를 남기고 생존 확인에 재시작을 위임하는 편이 원인 분석에 유리하다.

## 한계

`worker`의 DB 연결이 응답 패킷 없이 유실되면(예: 장애 조치로 기존 DB 서버가 사라진 경우), 해당 연결의 쿼리는 운영체제가 TCP 재전송을 포기할 때까지 장시간 대기할 수 있다. 그 기간 동안 해당 워커는 작업을 진행하지 못하고 생존 확인이 `unhealthy`로 표시한다. 데이터 정확성은 리스와 펜싱이 보장하므로, 해당 워커가 점유 중이던 건은 리스 만료 후 다른 워커가 인계(Takeover)받는다. 이 시나리오를 직접 재현 테스트하지는 않았다.

## 검토한 대안

- **예외 발생 즉시 프로세스 종료(Node.js 권장)**: 인메모리 상태를 신뢰할 수 없을 때는 안전하나, 단일 요청의 버그가 프로세스 전체를 중단시키고 원인 로그가 기록되기 전에 종료될 수 있다.
- **모듈별 개별 `try/catch`**: 예외 처리 방식이 파편화되고 한 곳만 누락되어도 프로세스가 종료된다.
- **DB 결과 기록 최종 실패 시 워커 종료**: 리스 방식에서는 프로세스를 종료할 이유가 없다. 기록하지 못한 건은 리스가 만료되면 다른 워커에 인계(Takeover)된다. 워커를 종료시키면 DB가 수 초간 일시 응답하지 않을 때 모든 워커가 동시에 재시작한다.
- **`api` 쿼리 응답 한도 30초**: 수십 ms짜리 쿼리에 비해 과도하게 길다. 앞단 게이트웨이의 응답 한도와 비슷하거나 길면, DB 장애 시 클라이언트가 애플리케이션의 `503` 응답 대신 게이트웨이 오류를 받게 된다.
