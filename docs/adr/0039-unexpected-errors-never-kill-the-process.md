# ADR-0039. 예상하지 못한 오류로 프로세스가 죽지 않게 하고, 요청에는 반드시 응답한다

## 배경

서버가 아무 기록 없이 툭 끝나면, 무엇이 잘못됐는지 알 수 없다. 반대로 오류 처리를 모듈마다 제각각 하면, 한 곳만 빠뜨려도 프로세스가 죽는다. 또 DB가 응답하지 않을 때 요청이 끝없이 기다리면, 클라이언트는 답을 받지 못한다.

## 결정

예상하지 못한 오류는 받아서 로그와 메트릭으로 남기고 계속 돈다. 일부러 끝내는 경우는 시작하지 못했을 때 하나뿐이다.

## 오류는 꼭대기 몇 곳에서만 받는다

try/catch를 곳곳에 바르지 않는다. 오류가 올라오는 꼭대기마다 한 번씩, 같은 방식으로 받는다.

| 꼭대기 | 받는 방식 |
| --- | --- |
| 프로세스 | api와 worker가 시작할 때 `unhandledRejection`, `uncaughtException`을 받는 안전망을 단다. error 로그를 남기고 `alarm_unhandled_errors_total`을 올린 뒤 계속 돈다 |
| HTTP 요청 | 전역 예외 필터가 모든 오류를 Problem Details로 바꾼다(ADR-0019). 예상하지 못한 오류는 500, DB를 쓸 수 없으면 503이다 |
| worker의 작업 루프 | 다섯 루프(발송, 결과 확인, 펼치기, 취소 정리, 넘겨받기)가 같은 `PollingLoop`를 쓴다. 한 바퀴가 오류로 끝나면 로그와 `alarm_loop_errors_total`을 남기고, 잠깐 쉰 뒤 다음 바퀴를 돈다 |
| 루프 밖에서 도는 발송 한 건 | 발송 작업을 등록하는 한 곳에서 받는다. 한 건의 오류가 루프와 다른 건에 번지지 않는다 |
| 관리 포트 | 응답을 끝까지 만든 뒤 한 번에 보낸다. 만드는 도중 실패하면 503으로 답하고 로그를 남긴다 |

## 요청은 반드시 끝난다

- **api의 DB 풀에는 한도를 둔다.** 연결 대기 한도(`DB_ACQUIRE_TIMEOUT_MS`, 기본 5초)와 쿼리 응답 한도(`DB_QUERY_TIMEOUT_MS`, 기본 10초)다. 한도가 없으면 연결이 바닥났을 때 요청이 응답 없이 끝없이 기다린다. 한도를 넘으면 503으로 답한다. Drizzle은 드라이버 오류를 감싸 `cause`에 두므로, 503인지는 `cause`를 따라가며 판단한다.
- **쿼리 한도가 10초인 이유**: API의 쿼리는 모두 몇십 ms 안에 끝난다. 다만 발송 시작과 취소는 알림 행을 바꾼다. 트랜잭션 도중 멈춘 워커가 그 행 잠금을 쥐고 있으면, Postgres가 그 세션을 끝낼 때까지(트랜잭션 유휴 한도 5초) 기다린다. 그래서 그보다 길게 둔다. 이 관계는 기동할 때 검사한다(ADR-0030).
- **worker의 풀에는 클라이언트 쪽 한도를 두지 않는다.** 멈춘 워커가 쥔 알림 행 잠금이 풀리기를 기다리는 것은 정상이다. 그 잠금은 서버 쪽 한도(트랜잭션 유휴 한도 5초)가 풀어 준다(ADR-0004).

## 일부러 끝내는 경우

- **시작하지 못했을 때만 끝낸다**(설정 오류, 2분 안에 DB에 연결하지 못함 등). fatal 로그에 사유를 남기고 종료 코드 1로 끝난다. 일을 시작할 수 없고, 기동 단계라 처리 중인 일이 없다.
- **결과를 DB에 적지 못해도 끝내지 않는다.** DB 쓰기는 간격을 늘려 가며 몇 번 재시도하고, 끝내 실패하면 그 오류를 루프 꼭대기가 받아 로그와 `alarm_loop_errors_total`로 남긴다. 적지 못한 건은 기한이 지나 다른 워커가 넘겨받는다(ADR-0004). 펼치기는 같은 커서부터 다시 받고, 취소 정리는 기한 뒤 다시 집힌다.
- migrate는 한 번 돌고 끝나는 작업이라, 실패하면 종료 코드 1로 끝나는 것이 약속이다.

## 처리되지 않은 예외 뒤에도 계속 도는 위험

Node는 `uncaughtException` 뒤의 상태를 보장하지 않는다. 그래도 계속 도는 쪽을 택했다.

- 이 시스템의 정확성은 메모리가 아니라 DB에 있다(조건부 쓰기, 펜싱).
- 망가진 프로세스는 생존 확인이 잡는다. worker는 작업 루프가 30초 동안 돌지 않으면 생존 확인이 실패해 재시작 대상이 된다(ADR-0026).
- 아무 기록 없이 죽는 것보다, 기록을 남기고 생존 확인에 맡기는 편이 원인을 찾기 쉽다.

## 한계

worker의 DB 연결이 아무 응답 없이 사라지면(예: 장애 조치로 옛 DB 서버가 사라짐), 그 연결의 쿼리는 운영체제가 TCP 연결을 포기할 때까지 오래 기다릴 수 있다. 그동안 그 워커는 일하지 못하고, 생존 확인이 unhealthy로 표시한다. 정확성은 기한과 펜싱이 지킨다. 그 워커가 쥔 건은 기한이 지나 다른 워커가 넘겨받는다. 이 경우를 직접 재현해 보지는 않았다.

## 검토한 후보

- **예외 뒤 바로 종료(Node 권장)**: 상태를 믿을 수 없을 때는 안전하다. 하지만 요청 하나의 버그가 프로세스 전체를 내리고, 원인 로그가 남기 전에 죽을 수 있다.
- **모듈마다 try/catch**: 받는 방식이 곳곳에서 달라지고, 하나만 빠뜨려도 프로세스가 죽는다.

## 바뀐 경위

- 처음에는 worker가 결과를 끝내 DB에 적지 못하면 스스로 끝났다. 점유를 DB 세션으로 판정하던 때라, 끝내야 잠금이 풀려 다른 워커가 넘겨받았기 때문이다. 기한 방식(ADR-0004)으로 바꾼 뒤에는 끝낼 이유가 없어졌다. 오히려 끝내면 DB가 몇 초만 응답하지 않아도 모든 워커가 한꺼번에 재시작했다.
- api의 쿼리 한도는 처음에 30초였다. 몇십 ms짜리 쿼리에 비해 너무 길었다. 앞단 게이트웨이의 응답 한도와 비슷하거나 길면, DB가 멈췄을 때 클라이언트가 503 대신 게이트웨이 오류를 받는다. 심사(4회차)의 지적으로 10초로 줄였다.
