# ADR-0013. 워커당 동시 발송 상한은 50개로 제한하고 HTTP 연결 풀 크기도 50개로 맞춘다

## 배경

외부 API의 응답 시간은 편차가 크다. 대부분 0.06초이나 일부는 4초, 일부는 10초(HTTP 타임아웃)까지 소요된다. 응답을 대기하는 인플라이트(in-flight) 요청을 동시에 몇 개까지 허용할지 정해야 한다. 상한이 너무 작으면 지연 응답이 슬롯을 점유해 초당 50건을 채우지 못하고, 상한이 없으면 외부 지연 시 미완료 요청이 무한정 누적된다.

## 결정

- 워커 1대가 동시에 응답을 대기할 수 있는 발송 요청은 최대 50개로 제한한다.
- 외부 발송 API용 HTTP 연결 풀(`keepAlive`, 연결 재사용 방식)의 최대 소켓 수도 50개로 동일하게 설정한다.
- 발송 요청과 조회 요청(발송 내역 조회, 사용자 목록 조회)은 HTTP 연결 풀을 분리한다. 동일한 풀을 사용하면 상태 확정(Reconciliation)을 위한 발송 내역 조회가 몰릴 때 발송 소켓이 부족해져 "토큰을 할당받은 요청은 즉시 전송된다"는 전제가 깨진다.

## 근거

- **동시 진행 중인 요청 수 = 초당 건수 × 평균 응답 시간**: 실측 응답 시간의 평균은 약 0.33초다. 초당 50건 기준 평시 동시 요청은 약 17개이며, 지연 응답이 겹치면 일시적으로 30~40개까지 증가한다.
- **단일 워커 생존 시 초당 50건 단독 처리 보장**: 워커가 1대만 남아도 단독으로 초당 50건을 처리해야 하므로 워커당 상한을 50개로 설정한다. 작게 잡으면 지연 응답이 슬롯을 점유해 추가 토큰을 요청하지 못하고 초당 50건을 채우지 못한다.
- **외부 지연 시 배압(Backpressure) 역할**: 외부 서비스 전체가 느려져 모든 요청이 10초씩 소요되면 동시 요청이 최대 500개까지 누적될 수 있다. 상한이 있으면 워커당 50개에서 멈추고 토큰도 덜 할당받는다.
- **소켓 수를 동시 발송 상한과 동일하게 두는 이유**: 소켓 수가 상한보다 적으면 토큰을 할당받은 요청이 소켓을 기다리며 대기하다가 한꺼번에 전송된다. 결과적으로 외부 API에 요청이 몰려 도착하여 `429`가 발생한다.

## 결과 및 한계

동시 발송 슬롯이 모두 차면 긴급 알림도 빈 슬롯을 기다린다. 이 상황은 외부 서비스 전체가 느려졌을 때만 발생하며, 해당 상황에서는 긴급과 대량 모두 동일하게 지연된다.

## 상세: 작업 루프 전용 DB 연결 풀 분리

워커는 DB 연결 풀을 둘로 분리한다. 토큰 할당과 점유(claim)는 연결 2개짜리 전용 풀을 사용하고, 결과 기록과 나머지 작업은 연결 10개짜리 풀을 사용한다. 워커 1대가 사용하는 DB 연결은 총 12개다.

- 결과 기록 트랜잭션은 동일 알림의 행 잠금을 순차적으로 대기한다(ADR-0018). 동일한 풀을 공유하면 잠금을 기다리는 트랜잭션들이 연결을 점유하는 동안 작업 루프가 연결을 얻지 못한다. 그 사이 토큰 버킷이 용량(10)을 초과하여 넘친 토큰이 버려진다.
- 실측(mock 사용자 2000명, 워커 2대): 단일 풀일 때 초당 46.9건, 풀을 분리한 뒤 초당 49.1건이었다. 두 경우 모두 `429`는 0건이었다.
