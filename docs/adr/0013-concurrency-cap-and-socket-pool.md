# 워커당 동시 발송 한도 50, HTTP 연결 풀도 50

워커 한 대가 동시에 응답을 기다릴 수 있는 발송 요청은 최대 50개이고, 외부 API용 HTTP 연결 풀(keepAlive)의 소켓 수도 50으로 같게 둔다.

## 근거

- 동시에 진행 중인 요청 수는 초당 건수 × 평균 응답 시간이다. 실측 응답 시간(대부분 0.06초, 약 4%가 4초, 약 1%가 10초 타임아웃)의 평균은 약 0.33초이므로, 초당 50건이면 평소 17개 정도이고 느린 응답이 겹치면 순간적으로 30~40개다.
- 워커가 한 대만 남아도 혼자 초당 50건을 내야 하므로 워커당 50으로 잡는다. 작게 잡으면 느린 응답이 자리를 차지해 토큰을 받으러 가지 못하고 초당 50건을 채우지 못한다.
- 한도는 브레이크 역할도 한다. 외부 서비스 전체가 느려져 모든 요청이 10초씩 걸리면 동시 요청이 500개까지 쌓일 수 있는데, 한도가 있으면 워커당 50개에서 멈추고 토큰도 덜 받아 간다.
- 소켓 수를 한도보다 적게 두면, 토큰을 받은 요청이 소켓을 기다리며 쌓였다가 한꺼번에 나가 외부에 몰려 도착한다(429). 토큰을 받은 요청은 바로 나가야 하므로 소켓 수를 한도와 같게 둔다.
- 한도가 꽉 차면 긴급 알림도 자리를 기다린다. 이 상황은 외부 서비스 전체가 느려졌을 때만 생기며, 그때는 긴급과 대량이 똑같이 느리다.

## 작업 루프 전용 DB 연결 (구현 중 측정으로 추가)

워커는 DB 커넥션 풀을 둘로 나눈다. 토큰 받기와 꺼내기는 연결 2개짜리 전용 풀을 쓰고, 결과 기록과 나머지는 연결 10개짜리 풀을 쓴다.

- 결과 기록 트랜잭션은 알림 행 잠금을 차례로 기다린다(ADR-0018). 같은 풀을 쓰면, 잠금을 기다리는 트랜잭션들이 연결을 붙잡는 동안 작업 루프가 연결을 얻지 못한다. 그 사이 토큰 버킷이 용량(10)을 넘겨 넘친 토큰이 버려진다.
- 실측(mock 2000명, 워커 2대): 같은 풀일 때 초당 46.9건이었고, 풀을 나눈 뒤 초당 49.1건이 됐다. 두 경우 모두 429는 0건이었다.
