# ADR-0013. 워커 한 대가 동시에 기다리는 발송은 50개까지이고, HTTP 연결 풀도 50이다

## 배경

외부 API의 응답 시간은 들쭉날쭉하다. 대부분 0.06초지만 일부는 4초, 일부는 10초(우리 타임아웃)까지 걸린다. 응답을 기다리는 요청을 한 번에 몇 개까지 둘지 정해야 한다. 너무 적으면 느린 응답이 자리를 차지해 초당 50건을 못 채우고, 제한이 없으면 외부가 느려질 때 요청이 끝없이 쌓인다.

## 결정

- 워커 한 대가 동시에 응답을 기다릴 수 있는 발송 요청은 최대 50개다.
- 외부 API용 HTTP 연결 풀(keepAlive, 연결을 끊지 않고 다시 쓰는 방식)의 소켓 수도 50으로 같게 둔다.
- 발송과 조회(발송 내역, 사용자)는 연결 풀을 따로 쓴다. 같은 풀을 쓰면 결과 확인 조회가 몰릴 때 발송 소켓이 모자라서, "토큰을 받은 요청은 바로 나간다"는 전제가 깨진다.

## 이유

- **동시에 진행 중인 요청 수 = 초당 건수 × 평균 응답 시간이다.** 실측 응답 시간의 평균은 약 0.33초다. 초당 50건이면 평소 17개 정도이고, 느린 응답이 겹치면 잠깐 30~40개다.
- **워커가 한 대만 남아도 혼자 초당 50건을 내야 한다.** 그래서 워커당 50으로 잡는다. 작게 잡으면 느린 응답이 자리를 차지해 토큰을 받으러 가지 못하고, 초당 50건을 채우지 못한다.
- **한도는 브레이크 역할도 한다.** 외부 서비스 전체가 느려져 모든 요청이 10초씩 걸리면, 동시 요청이 500개까지 쌓일 수 있다. 한도가 있으면 워커당 50개에서 멈추고 토큰도 덜 받아 간다.
- **소켓 수를 한도와 같게 두는 이유**: 소켓이 한도보다 적으면, 토큰을 받은 요청이 소켓을 기다리며 쌓였다가 한꺼번에 나간다. 그러면 외부에 몰려 도착해 429가 난다.

## 대가

한도가 꽉 차면 긴급 알림도 자리를 기다린다. 이 상황은 외부 서비스 전체가 느려졌을 때만 생기며, 그때는 긴급과 대량이 똑같이 느리다.

## 작업 루프 전용 DB 연결 풀

워커는 DB 연결 풀을 둘로 나눈다. 토큰 받기와 꺼내기는 연결 2개짜리 전용 풀을 쓰고, 결과 기록과 나머지는 연결 10개짜리 풀을 쓴다. 워커 하나가 쓰는 연결은 12개다.

- 결과 기록 트랜잭션은 같은 알림의 행 잠금을 차례로 기다린다(ADR-0018). 같은 풀을 쓰면, 잠금을 기다리는 트랜잭션들이 연결을 붙잡는 동안 작업 루프가 연결을 얻지 못한다. 그 사이 토큰 버킷이 용량(10)을 넘겨, 넘친 토큰이 버려진다.
- 실측(mock 사용자 2000명, 워커 2대): 같은 풀일 때 초당 46.9건, 풀을 나눈 뒤 초당 49.1건이었다. 두 경우 모두 429는 0건이었다.
