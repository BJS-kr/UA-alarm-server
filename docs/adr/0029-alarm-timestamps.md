# 알림 시각은 created_at, started_at, finished_at 세 개를 상태 전이와 같은 문장에서 기록한다

| 값 | 쓰는 곳 | 읽는 곳 |
| --- | --- | --- |
| `created_at` | 알림 생성 API의 INSERT (DB 기본값) | 목록·단건 조회 |
| `started_at` | 발송 시작 API의 조건부 UPDATE(CREATED → SENDING, ADR-0016) | 단건 조회, 워커의 긴급 알림 "시작→발송" 지연 메트릭 |
| `finished_at` | 종료 상태로 바꾸는 문장: 완료 판정(워커, ADR-0018), 시작 전 취소(API, ADR-0016), 취소 정리 후 판정(워커, ADR-0017) | 목록·단건 조회 |

- 시각은 상태를 바꾸는 바로 그 문장에서 함께 쓴다. 시각만 따로 기록하는 단계가 없으므로 상태와 시각이 어긋나지 않는다.
- 읽는 곳은 조회 API와 메트릭뿐이며, 이 값을 보고 동작하는 백그라운드 로직은 없다.
- 워커는 건을 꺼낼 때 알림 상태를 확인하는 조인(ADR-0017)에서 `started_at`을 함께 가져온다.
- 이 값들은 다른 데이터로 다시 계산할 수 없는 사건 기록이라 저장한다. 다시 계산할 수 있는 값(첫 발송 시각, 상태별 건수)은 저장하지 않는다(ADR-0018).

## 검토한 후보

- **예상 완료 시각**: 명세에 없고, 먼저 시작한 알림부터 처리하는 순서(ADR-0012) 때문에 앞에 남은 알림의 건까지 세야 해서 계산에 비해 얻는 것이 적다. 남은 양은 상태별 건수의 대기 건수로 충분하다.
- **펼치기 완료 시각, 취소 요청 시각**: 운영자의 질문에 꼭 필요하지 않다. 취소 여부와 종료 시각은 상태와 `finished_at`으로 충분하다.
