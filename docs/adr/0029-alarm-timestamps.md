# ADR-0029. 알림 생명주기 시각 컬럼 구성 및 상태 전이 시 원자적 기록

## 배경

운영 및 조회 시 알림의 생성 시각, 발송 시작 시각, 종료 시각을 확인해야 한다. 시각을 상태 변경과 별도 쿼리로 기록하면, 두 작업 사이에 프로세스가 비정상 종료될 때 상태와 시각이 불일치할 수 있다.

## 결정

알림 시각은 `created_at`, `started_at`, `finished_at` 세 컬럼으로 두며, 상태를 변경하는 SQL 문장에서 함께 기록한다.

| 컬럼          | 기록 시점                                                                                                                                 | 조회 시점                                                           |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `created_at`  | 알림 생성 API의 `INSERT`(DB 기본값)                                                                                                       | 알림 목록 및 단건 조회                                              |
| `started_at`  | 발송 시작 API의 조건부 `UPDATE`(`CREATED` → `SENDING`, ADR-0016)                                                                          | 단건 조회, 긴급 알림의 발송 시작부터 접수 완료까지 소요 시간 메트릭 |
| `finished_at` | 종료 상태로 변경하는 조건부 `UPDATE`: 완료 판정(워커, ADR-0018), 발송 시작 전 취소(API, ADR-0016), 취소 정리 후 종료 판정(워커, ADR-0017) | 알림 목록 및 단건 조회                                              |

## 근거

- **시각은 상태를 변경하는 동일 SQL 문장에서 원자적으로 기록한다.** 시각만 별도로 기록하는 단계가 없으므로 상태와 시각이 어긋나지 않는다.
- **시각 컬럼을 읽는 경로는 조회 API와 메트릭뿐이다.** 이 값을 기준으로 동작하는 백그라운드 제어 로직은 없다. 워커는 Delivery 점유(claim) 시 알림 상태를 확인하는 조인 쿼리(ADR-0017)에서 `started_at`을 함께 조회한다.
- **사후 재계산이 불가능한 사건 시각만 저장한다.** 사후 계산이 가능한 값(첫 발송 시각, 상태별 건수 등)은 별도로 저장하지 않는다(ADR-0018).

## 검토한 대안

- **예상 완료 시각 제공**: 선착순 처리(ADR-0012) 구조상 선행 알림의 잔여 건수까지 합산해야 하므로 계산 비용 대비 효용이 낮다. 잔여 작업량은 상태별 건수의 대기 건수로 확인한다.
- **수신자 확장 완료 시각 및 취소 요청 시각 추가**: 운영 조회에 필수적이지 않으며, 취소 여부와 종료 시각은 알림 상태와 `finished_at`으로 충분하다.
