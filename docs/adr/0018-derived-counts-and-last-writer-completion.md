# 건수는 저장하지 않고 조회 시 세며, 완료는 마지막 기록이 같은 트랜잭션에서 판정한다

## 건수: 조회할 때 센다

- 알림 단건 조회에서 Delivery를 `GROUP BY status`로 그 자리에서 센다. (알림, 상태) 인덱스로 10만 건도 수십 ms다.
- 목록 조회는 상태만 보여 주고 건수는 보여 주지 않는다.
- 집계 결과를 저장하면 같은 사실이 두 곳에 있게 되어, Delivery 상태를 바꾸는 경로 하나만 갱신을 빠뜨려도 영원히 어긋난다(ADR-0003의 "원본은 하나"). 집계값 저장은 성능 이득이 명확한 경우에만 제한적으로 쓴다.

## 완료: 마지막 기록이 판정한다

Delivery가 최종 상태(SENT, FAILED, CANCELED)가 되는 트랜잭션은 모두 같은 함수를 거친다. 이 함수는 다음 순서로 동작한다.

1. 알림 행을 잠근다.
2. Delivery 결과를 기록한다.
3. 같은 트랜잭션에서 아래 조건부 UPDATE를 실행한다.

```sql
UPDATE alarms SET status = 'COMPLETED'          -- CANCELING이면 'CANCELED'
WHERE id = $1 AND status = 'SENDING'
  AND 펼치기_끝남
  AND NOT EXISTS (끝나지 않은 Delivery: 대기, 보내는 중, 결과 미확정)
```

- 잠금이 없으면 마지막 두 건을 동시에 기록할 때 서로 상대 건을 진행 중으로 보고 둘 다 지나쳐, 아무도 완료로 바꾸지 않는다. 알림 행을 잠그면 같은 알림의 기록이 한 줄로 서고, 뒤의 트랜잭션은 앞의 커밋을 본 뒤 확인하므로(READ COMMITTED는 문장마다 새 스냅숏을 쓴다) 진짜 마지막 기록만 "남은 건 없음"을 본다.
- 판정이 마지막 기록과 한 트랜잭션이라 기록과 판정 사이에 죽는 틈이 없다. 그래서 안전망으로 쓸 반복 쿼리가 필요 없다.
- 숫자를 세서 전체 수와 맞춰 보지 않고 존재 여부만 본다. 펼치기 중에는 전체 수가 정해지지 않기 때문이다. `NOT EXISTS`는 하나를 찾으면 멈추고, 끝나지 않은 건만 담은 부분 인덱스를 쓰므로 발송이 끝나 갈수록 비용이 0에 가까워진다.
- Delivery가 최종 상태가 되는 경로는 발송 결과 기록, 조회 결과 기록, 취소 정리, 펼치기 종료이며, 모두 이 함수를 거친다.
- 대가로 같은 알림의 결과 기록이 줄을 선다. 초당 50건이고 묶어서 기록하므로 경합은 작다. 저장되는 집계값은 없고 잠금만 쓴다.

## 검토한 후보

- **워커가 1초마다 완료 조건을 확인**: 정확하지만 반복 쿼리가 상시 돌고, 완료 반영이 최대 1초 늦다.
- **알림 행에 건수 카운터**: 건수 조회가 즉시 되고 완료도 바로 잡히지만, 같은 사실이 두 곳에 저장되어 어긋날 수 있다.
- **커밋한 뒤 별도 문장으로 확인**: 마지막 커밋자는 전부를 보므로 판정은 정확하지만, 커밋과 확인 사이에 죽으면 판정을 놓쳐 안전망이 따로 필요하다.
