# ADR-0018. 건수는 저장하지 않고 조회할 때 세며, 완료는 마지막 결과 기록이 같은 트랜잭션에서 판정한다

## 결정

- **건수**: 알림 단건 조회에서 Delivery를 `GROUP BY status`로 그 자리에서 센다. 저장해 두지 않는다.
- **완료**: Delivery가 끝 상태(SENT, FAILED, CANCELED)가 되는 트랜잭션이 알림 행을 잠그고, 같은 트랜잭션 안에서 "남은 건이 없으면 알림을 완료로"라는 조건부 UPDATE를 실행한다.

## 건수: 조회할 때 센다

- (알림, 상태) 인덱스로 10만 건도 수십 ms다.
- 목록 조회는 상태만 보여 주고 건수는 보여 주지 않는다.
- 집계를 저장하면 같은 사실이 두 곳에 있게 된다. Delivery 상태를 바꾸는 경로 하나만 갱신을 빠뜨려도 영원히 어긋난다(ADR-0003의 "원본은 하나"). 집계 저장은 이득이 분명한 경우에만 쓴다(예외는 ADR-0031).

## 완료: 마지막 기록이 판정한다

Delivery가 끝 상태가 되는 트랜잭션은 모두 같은 함수를 거친다.

1. 알림 행을 잠근다.
2. Delivery 결과를 기록한다.
3. 같은 트랜잭션에서 아래 조건부 UPDATE를 실행한다.

```sql
UPDATE alarms SET status = 'COMPLETED'          -- CANCELING이면 'CANCELED'
WHERE id = $1 AND status = 'SENDING'
  AND 펼치기_끝남
  AND NOT EXISTS (끝나지 않은 Delivery: 대기, 보내는 중, 결과 미확정)
```

- **잠그는 이유**: 잠금이 없으면 마지막 두 건을 동시에 기록할 때 서로 상대 건을 진행 중으로 보고 둘 다 지나쳐, 아무도 완료로 바꾸지 않는다. 알림 행을 잠그면 같은 알림의 기록이 한 줄로 서고, 뒤 트랜잭션은 앞 트랜잭션의 커밋을 본 뒤 확인한다(READ COMMITTED는 문장마다 새 스냅숏을 쓴다). 그래서 진짜 마지막 기록만 "남은 건 없음"을 본다.
- **같은 트랜잭션인 이유**: 기록과 판정 사이에 죽는 틈이 없다. 그래서 놓친 판정을 주울 반복 쿼리가 필요 없다.
- **세지 않고 존재만 본다**: 펼치기 중에는 전체 수가 정해지지 않기 때문이다. `NOT EXISTS`는 하나를 찾으면 멈추고, 끝나지 않은 건만 담은 부분 인덱스를 써서 발송이 끝나 갈수록 비용이 0에 가까워진다.
- **이 함수를 거치는 경로**: 발송 결과 기록, 조회 결과 기록, 취소 정리, 펼치기 종료.

## 대가

같은 알림의 결과 기록이 줄을 선다. 기록은 건마다 한 트랜잭션이라 초당 50번 줄을 서지만, 한 번이 짧아서(행 하나 갱신과 남은 건 확인) 처리량은 상한 가까이 나온다(실측 초당 49건). 기다리는 동안 DB 연결을 붙잡으므로, 작업 루프에는 전용 연결 풀을 둔다(ADR-0013).

## 검토한 후보

- **워커가 1초마다 완료 조건을 확인**: 정확하지만 반복 쿼리가 늘 돌고, 완료 반영이 최대 1초 늦다.
- **알림 행에 건수 카운터**: 건수 조회가 바로 되고 완료도 바로 잡히지만, 같은 사실이 두 곳에 저장되어 어긋날 수 있다.
- **커밋한 뒤 별도 문장으로 확인**: 마지막 커밋자는 전부를 보므로 판정은 정확하지만, 커밋과 확인 사이에 죽으면 판정을 놓쳐 안전망이 따로 필요하다.
