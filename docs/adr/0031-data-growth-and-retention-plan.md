# ADR-0031. 데이터 증가에 따른 성능 영향 분석 및 보존 정책 설계

## 배경

대량 알림 1건당 Delivery가 10만 행 생성된다. 매일 발송하면 월 300만 행이 누적된다. 장기 운영 시 오래된 데이터를 정리해야 하지만, 삭제 장치를 현재 범위에 구현할지 여부를 결정해야 한다.

## 결정

현재는 데이터를 삭제하지 않는다. 데이터가 누적되었을 때의 보존 대책은 아래 설계로만 남긴다.

## 근거

- 발송 경로의 쿼리(점유(claim), 완료 판정)는 대기 중이거나 미종료 상태인 건만 포함하는 부분 인덱스(partial index)를 사용한다(ADR-0011, 0018). 종료된 건이 누적되어도 부분 인덱스는 작게 유지되므로 발송 속도에 영향이 없다.
- 조회 쿼리는 알림 ID로 범위를 좁혀 읽으므로 다른 알림의 행이 늘어나도 조회 성능이 저하되지 않는다.

## 상세

### 데이터 누적 시 보존 대책 (설계)

1. **보존 기간 설정**: 종료된 지 일정 기간(예: 90일)이 지난 알림의 Delivery를 삭제한다.
2. **월 단위 파티션**: Delivery 테이블을 생성 시각 기준 월별 파티션으로 분할한다. 보존 기간이 지난 월은 행 단위 `DELETE` 대신 파티션을 통째로 분리(detach/drop)한다. 대량 `DELETE`는 실행 시간이 길고 테이블에 빈 공간(bloat)을 남기지만, 파티션 분리는 즉시 완료된다.
3. **종료된 알림의 건수 저장**: 알림이 종료 상태로 전이하는 SQL 문장(ADR-0018)에서 상태별 건수를 알림 행에 기록한다. Delivery를 삭제하면 원본 행 기반 집계값도 사라지기 때문이다. 집계를 별도 저장하지 않는다는 원칙(ADR-0018)의 예외이나, 종료된 알림의 건수는 더 이상 변경되지 않아 원본과 불일치할 수 없고 보존 정책 적용이라는 명확한 이점이 있다.

### 현재 구현하지 않는 이유

파티션 운영에는 다음 달 파티션을 사전 생성하는 작업(`pg_partman` 같은 확장이나 애플리케이션 내부 스케줄러)이 필요하다. 과제 실행 범위에서는 데이터가 장기 누적될 일이 없으므로 불필요한 장치를 추가하지 않는다.
