# 헬스체크는 생존(live)과 준비(ready)를 나눈다

| 프로세스 | 경로 | 확인 | 실패 시 |
| --- | --- | --- | --- |
| api | `/health/live` | 프로세스가 응답한다 | 재시작 대상 |
| api | `/health/ready` | DB `SELECT 1`이 1초 안에 성공한다 | 요청을 보내지 않음, 재시작하지 않음 |
| worker | `/health/live` | 작업 루프가 최근 30초 안에 한 바퀴 이상 돌았다 | 재시작 대상 |

- 생존 확인에 DB를 넣지 않는다. DB가 잠깐 죽었을 때 생존 확인까지 실패하면 플랫폼이 api를 모두 재시작하는데, DB는 여전히 죽어 있어 얻는 것 없이 재시작만 연달아 일어난다. DB 상태는 "지금은 요청을 보내지 말라"는 준비 확인에만 넣는다.
- worker의 생존 기준은 HTTP 응답이 아니라 작업 루프의 회전이다. HTTP 응답은 이벤트 루프가 살아 있다는 것만 보여 주며, 작업 루프가 끝나지 않는 쿼리에서 기다려도 200이 나간다. 작업 루프는 할 일이 없어도 0.5초마다 돌기 때문에(ADR-0011) 30초 동안 돌지 않았다면 멈춘 것이다.
- worker는 헬스체크와 메트릭을 위해 외부에 공개하지 않는 내부 HTTP 포트를 연다.
- compose healthcheck는 api에 `/health/ready`, worker에 `/health/live`를 쓴다.

## DB 장애 시 worker

- 일하던 중 멈췄다 깨어나도 종료하지 않는다. 기한이 지난 건은 보내지 않고, 늦은 쓰기는 펜싱이 막는다(ADR-0004).
- 새로 기동할 때는 DB에 연결될 때까지 간격을 늘려 가며 재시도하며 기다린다. 연결 실패로 바로 죽지 않으므로 DB가 복구되는 동안 재시작을 반복하지 않는다.
