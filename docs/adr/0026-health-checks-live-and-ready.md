# ADR-0026. 헬스체크는 생존(live)과 준비(ready)를 나눈다

## 결정

| 프로세스 | 경로 | 확인하는 것 | 실패하면 |
| --- | --- | --- | --- |
| api | `/health/live` | 프로세스가 응답한다 | 재시작 대상 |
| api | `/health/ready` | DB `SELECT 1`이 1초 안에 성공한다 | 요청을 보내지 않는다. 재시작하지 않는다 |
| worker | `/health/live`, `/health/ready` | 작업 루프가 최근 30초 안에 한 바퀴 이상 돌았다(둘 다 같은 기준) | 재시작 대상 |

- 경로는 모두 관리 포트에 있다(ADR-0033).
- compose healthcheck는 api에 `/health/ready`, worker에 `/health/live`를 쓴다.

## 이유

- **생존 확인에 DB를 넣지 않는다.** DB가 잠깐 죽었을 때 생존 확인까지 실패하면 플랫폼이 api를 모두 재시작한다. DB는 여전히 죽어 있으므로 얻는 것 없이 재시작만 이어진다. DB 상태는 "지금은 요청을 보내지 말라"는 준비 확인에만 넣는다.
- **worker의 생존 기준은 HTTP 응답이 아니라 작업 루프가 도는가다.** HTTP 응답은 이벤트 루프가 살아 있다는 것만 보여 준다. 작업 루프가 끝나지 않는 쿼리에서 기다려도 200이 나간다. 작업 루프는 할 일이 없어도 0.5초마다 돌기 때문에(ADR-0011), 30초 동안 돌지 않았다면 멈춘 것이다.

## DB 장애 때 worker

- 일하던 중 DB가 끊겨도 종료하지 않는다. 결과를 기록하지 못한 건은 기한이 지나 넘겨받히고, 늦은 쓰기는 펜싱이 막는다(ADR-0004, 0039).
- 새로 기동할 때는 DB에 연결될 때까지 간격을 늘려 가며(0.25초에서 두 배씩, 최대 5초) 최대 2분 기다린다. 연결 실패로 바로 죽지 않으므로 DB가 복구되는 동안 재시작을 되풀이하지 않는다. 2분이 지나면 시작 실패로 끝나고 restart 정책이 다시 띄운다.
