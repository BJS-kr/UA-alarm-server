# ADR-0026. 생존(Liveness)과 준비(Readiness) 헬스체크 분리

## 배경

컨테이너 오케스트레이션 환경(Docker Compose, Kubernetes)은 헬스체크 결과를 기준으로 컨테이너 재시작 여부와 트래픽 라우팅 여부를 결정한다. 점검 항목을 구분하지 않으면 일시적인 외부 의존성 장애 시 정상 컨테이너를 연쇄 재시작하거나, 반대로 작업 루프가 교착(hang)된 컨테이너를 정상으로 판정할 수 있다.

## 결정

| 프로세스 | 경로                            | 점검 기준                                                                          | 실패 시 동작                  |
| -------- | ------------------------------- | ---------------------------------------------------------------------------------- | ----------------------------- |
| `api`    | `/health/live`                  | HTTP 요청에 프로세스가 응답함                                                      | 컨테이너 재시작 대상          |
| `api`    | `/health/ready`                 | DB `SELECT 1` 쿼리가 1초 이내 성공함                                               | 트래픽 차단 (재시작하지 않음) |
| `worker` | `/health/live`, `/health/ready` | 작업 폴링 루프가 최근 30초 이내 1폴링 주기(사이클) 이상 완료됨 (두 경로 동일 기준) | 컨테이너 재시작 대상          |

- 모든 헬스체크 경로는 관리 전용 포트에서 제공한다(ADR-0033).
- Docker Compose `healthcheck`는 `api`에 `/health/ready`, `worker`에 `/health/live`를 설정한다.

## 근거

- **생존 확인(`live`)에서 DB 점검 제외**: 일시적인 DB 장애 시 생존 확인까지 실패로 처리하면 플랫폼이 모든 `api` 컨테이너를 재시작한다. DB가 복구되지 않은 상태에서의 재시작은 무의미한 기동 부하만 유발하므로, DB 연결 상태는 트래픽 유입만 제어하는 준비 확인(`ready`)에만 반영한다.
- **`worker`의 생존 확인은 작업 루프 진행 여부로 판정**: 단순 HTTP 응답 성공은 Node.js 이벤트 루프의 동작 여부만 나타낼 뿐, 작업 루프가 무한 대기 쿼리 등에서 멈춘 상태를 감지하지 못한다. 워커 작업 루프는 유휴 상태에서도 0.5초 주기로 실행되므로(ADR-0011), 30초 동안 한 폴링 주기(사이클)도 완료하지 못했다면 작업 루프가 정지된 것으로 판단한다.

## 상세: DB 장애 시 워커 동작

- **런타임 중 DB 연결 단절**: 프로세스를 종료하지 않고 다음 폴링 주기에 재시도한다. 결과를 기록하지 못한 처리 중이던 건은 리스 만료 시각(`lease_until`) 경과 후 다른 워커에 의해 리스 만료 회수(인계, Takeover)되며, 지연된 쓰기는 펜싱 토큰으로 차단된다(ADR-0004, ADR-0039).
- **신규 기동 시 DB 연결 대기**: 기동 시점에는 DB 연결이 성공할 때까지 지수 백오프(0.25초부터 2배씩 증가, 상한 5초)로 최대 2분간 대기한다. 연결 실패 시 즉시 종료하지 않으므로 DB 복구 중 불필요한 컨테이너 재시작 반복을 방지한다. 2분 경과 후에도 연결되지 않으면 기동 실패로 종료하고 컨테이너 `restart` 정책에 의해 재기동한다.
