# ADR-0002. 결과 미확정(UNCONFIRMED) 건은 clientRef로 발송 내역을 조회한 후 재발송한다

## 배경

외부 발송 API는 멱등성을 보장하지 않으므로 동일 요청을 두 번 전송하면 수신자에게 중복 발송된다.

요청 전송 후 타임아웃(10초) 내에 응답을 받지 못하는 등 외부 API의 접수 여부를 알 수 없는 전송 여부 미확정 상황이 발생할 수 있다. 예를 들어 mock 서버는 일부 요청(약 2%)을 접수한 뒤 30초 동안 응답하지 않는다. 이러한 건을 즉시 재발송하면 중복이 발생하고, 발송 성공으로 간주하면 누락이 발생할 수 있다.

## 결정

전송 여부 미확정 건은 결과 미확정(`UNCONFIRMED`) 상태로 두고, 외부 발송 내역 API(`GET /v1/messages?clientRef=`)를 조회하여 상태를 확정(Reconciliation)한다.

- 발송 기록이 존재하면 발송 완료(`SENT`)로 확정한다.
- 발송 기록이 없다는 응답을 확인한 경우에만 재발송한다.
- 발송 내역 조회 자체가 실패하면 재발송하지 않고 조회만 재시도한다.

`clientRef`는 각 발송 요청에 부여하는 식별자이며, 외부 API는 이 값을 저장하고 발송 내역 조회를 지원한다.

## 상세

### 전송 여부 미확정 판정 기준

| 상황                                                                      | 판정 및 처리                                                                  |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `202`                                                                     | 전송 완료. `SENT` 확정                                                        |
| `400`                                                                     | 외부 API 거절. 실패(`FAILED`) 확정                                            |
| `429`, `500`, `503`, 요청 전송 전 연결 오류                               | 미전송 확정. 재발송해도 중복이 아님(처리는 ADR-0014 참조)                     |
| 타임아웃(10초), 요청 전송 후 연결 끊김, `502`·`504`, 해석할 수 없는 `2xx` | 전송 여부 미확정. 결과 미확정(`UNCONFIRMED`)으로 전환                         |
| 워커가 결과를 기록하지 못한 채 리스 만료(ADR-0004)                        | 전송 여부 미확정. 인계(Takeover)한 워커가 결과 미확정(`UNCONFIRMED`)으로 전환 |

요청이 실제로 전송되었는지 가르는 세부 기준은 ADR-0037을 따른다.

### 동작 규칙

- **`clientRef`는 `{alarmId}:{recipientId}`로 고정한다.** 재발송 시에도 동일한 값을 사용하므로 단 한 번의 조회로 이전 시도의 접수 여부를 모두 확인할 수 있다.
- **발송 내역 조회는 이전 시도가 더 이상 전송될 수 없는 시점부터 5초 후에 수행한다.** 기준 시점은 타임아웃을 처리한 시각 또는 다른 워커가 리스 만료 건을 인계(Takeover)한 시각이다. 시도 시작 시각을 기준으로 삼지 않는 이유는 일시 정지되었다가 재개된 워커가 뒤늦게 요청을 전송할 수 있기 때문이다(ADR-0004). 너무 일찍 조회하면 아직 외부 기록이 생성되지 않아 미접수로 판단하고 중복 재발송할 위험이 있다.
- **재발송 대상 건은 대기(`PENDING`) 상태로 되돌린다.** 조회 직후 즉시 발송하지 않고 `PENDING`으로 전환하여 토큰 버킷(ADR-0009)과 우선순위 점유 순서(ADR-0011)를 동일하게 적용받도록 한다.
- **HTTP 타임아웃은 10초로 설정한다.** mock의 지연 응답(실측 3~4.5초)은 대기하여 수신하고, 30초 무응답 요청은 연결을 끊는다. 발송 내역 조회 요청에도 별도로 10초 타임아웃을 둔다.

## 근거: 5초 지연(`RECONCILE_DELAY_MS`)

- mock 서버 실측 결과([mock-observations.md](../mock-observations.md)), 30초 무응답 요청과 지연 응답 요청 모두 접수 즉시 발송 내역에 기록된다.
- 5초의 대기 시간은 타임아웃 직전에 전송된 요청이 네트워크를 거쳐 외부 API에 도달하기까지의 여유 시간이다.
- 또한 ADR-0004의 경합 구간(소켓 쓰기 직전 리스 검증을 통과한 직후 워커가 일시 정지하는 현상)에 대한 완충 역할을 한다. 해당 구간에서 중복 발송이 발생하려면 워커가 15초 이상 멈춰 있어야 한다.
- 이 값은 설정값(`RECONCILE_DELAY_MS`)으로 관리하며, 외부 서비스가 변경되면 해당 서비스의 내역 기록 지연 시간을 측정하여 재조정한다.

## 검토한 대안

- **응답을 끝까지 대기(타임아웃을 30초보다 길게 설정)**: 단순하지만 워커 비정상 종료 건은 여전히 발송 내역 조회가 필요하므로 복구 경로가 이원화된다. 실제 외부 서비스의 최대 응답 지연 시간도 사전에 단정할 수 없다.
- **타임아웃 시 즉시 재시도**: 이미 접수된 요청에 대해 중복 발송이 발생한다.
- **타임아웃 시 발송 성공으로 간주**: 요청이 도달하지 않은 경우 누락이 발생한다.
- **시도마다 `clientRef`에 일련번호 부여**: 시도 횟수만큼 조회해야 할 대상 값이 늘어난다.
- **조회 전 30초 대기**: 외부 서비스가 기록을 늦게 남기는 경우까지 포괄할 수 있으나, mock 서버는 접수 즉시 기록하므로 상태 확정만 25초 지연된다.
