# 결과가 확정되지 않은 발송은 clientRef 조회로 확인한 뒤에만 재발송

외부 API는 중복 제거를 하지 않으므로, 보냈는지 모르는 건을 그대로 재시도하면 중복이 된다. 발송 여부가 응답으로 확정되는 경우는 그대로 처리하고, 확정되지 않은 Delivery(우리 쪽 타임아웃, 워커 사망으로 회수된 건)는 `GET /v1/messages?clientRef=`로 조회해 기록이 있으면 발송 완료로 확정하고, 없을 때만 같은 clientRef로 재발송한다.

## 세부

- 응답별 처리: 202 → 완료. 400 → 영구 실패, 재시도 안 함. 429·500·503 → 발송 안 됨이 확정이므로 재시도.
- HTTP 타임아웃 10초. 느린 응답(실측 3.0~4.5초)은 성공으로 받고, 30초 지연 응답은 끊는다.
- clientRef는 `{alarmId}:{recipientId}`로 고정한다. 재시도해도 값이 바뀌지 않으므로 조회 한 번으로 이전 시도가 모두 확인된다.
- 조회 시각은 "이전 시도가 더는 보낼 수 없게 된 시점(타임아웃 처리 시각 또는 넘겨받은 시각) + 5초"다. 너무 이른 조회는 빈 결과를 내고, 그 재발송이 중복이 된다. 기준을 시도 시작이 아니라 끝으로 잡는 이유는 멈췄다 깨어난 워커가 늦게 보낼 수 있기 때문이다(ADR-0004).
- 대기 시간 5초의 근거: 처음에는 외부 서비스가 기록을 늦게 남길 수 있다고 보고 30초로 잡았다. 실측해 보니 mock은 30초 지연 요청과 느린 요청 모두 접수 즉시 기록했다([mock-observations.md](../mock-observations.md)). 남긴 5초는 끊기 직전에 보낸 요청이 네트워크를 건너 도착하는 여유다. 이 대기는 ADR-0004의 "확인 직후 멈춤" 경우의 완충도 겸한다. 그 경우 중복은 15 + 대기 시간(20초) 넘게 멈춰야 생기는데, 확률이 매우 낮아 기록을 빨리 확정하는 쪽을 택했다. 설정값으로 두며, 외부 서비스가 바뀌면 그 서비스의 기록 지연을 실측해 다시 정한다.
- 재발송은 조회가 성공해서 "기록 없음"을 답했을 때만 한다. 조회 자체가 실패하거나 타임아웃이면 다시 보내지 않고, 조회를 다시 시도한다. 조회 API도 느린 응답이 있으므로 별도의 타임아웃을 둔다.

## 검토한 후보

- 타임아웃을 30초보다 길게 잡고 응답을 끝까지 기다림: 단순하지만 워커 사망 건은 어차피 조회가 필요해 처리 경로가 둘이 된다. 실제 외부 서비스의 최대 지연은 알 수 없다.
- 타임아웃 시 즉시 재시도: 중복 발송.
- 타임아웃 시 발송된 것으로 간주: 요청이 도달하지 못한 경우 누락.
- 시도마다 clientRef에 접미사 부여: 조회 키가 시도 수만큼 흩어진다.
