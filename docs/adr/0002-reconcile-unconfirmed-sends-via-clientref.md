# ADR-0002. 보냈는지 모르는 건은 clientRef로 조회한 뒤에만 다시 보낸다

## 결정

외부 API는 중복 발송을 막아 주지 않는다. 보냈는지 모르는 건을 그냥 다시 보내면 같은 사람이 두 번 받는다. 그래서 그런 건은 결과 미확정(UNCONFIRMED)으로 두고, 외부의 발송 내역을 `GET /v1/messages?clientRef=`로 조회한다. 기록이 있으면 발송 완료로 확정하고, "기록 없음"이라는 답을 받았을 때만 다시 보낸다.

## 언제 "보냈는지 모른다"인가

| 상황 | 판단 |
| --- | --- |
| 202 | 보냈다. 완료 |
| 400 | 외부가 거절했다. 실패 확정 |
| 429, 500, 503, 요청이 나가기 전의 연결 오류 | 보내지 않았다. 다시 보내도 중복이 아니다. 처리는 ADR-0014 |
| 타임아웃(10초), 요청을 보낸 뒤 끊김, 502·504, 해석할 수 없는 2xx | 모른다. 결과 미확정 |
| 워커가 결과를 기록하지 못한 채 기한이 지남(ADR-0004) | 모른다. 넘겨받은 워커가 결과 미확정으로 둔다 |

요청이 나갔는지를 가르는 기준은 ADR-0037에 있다.

## 방식

- **clientRef는 `{alarmId}:{recipientId}`로 고정한다.** 재시도해도 값이 같아서, 조회 한 번으로 이전 시도가 모두 보인다.
- **조회는 이전 시도가 더는 보낼 수 없게 된 때부터 5초 뒤에 한다.** 그 시점은 타임아웃을 처리한 시각이거나 넘겨받은 시각이다. 시도를 시작한 시각을 기준으로 삼지 않는 이유는, 멈췄다 깨어난 워커가 늦게 보낼 수 있기 때문이다(ADR-0004). 너무 이르게 조회하면 아직 기록이 없어 "없음"이 나오고, 그 재발송이 중복이 된다.
- **재발송은 조회가 성공해서 "기록 없음"을 답했을 때만 한다.** 조회가 실패하거나 타임아웃이면 보내지 않고 조회만 다시 한다(간격은 ADR-0014). 조회에도 따로 타임아웃(10초)을 둔다.
- **재발송은 대기(PENDING)로 돌려 보낸다.** 그 자리에서 바로 보내지 않는다. 토큰(ADR-0009)과 우선순위 순서(ADR-0011)를 똑같이 지키기 위해서다.
- HTTP 타임아웃은 10초다. mock의 느린 응답(실측 3~4.5초)은 기다려서 성공으로 받고, 응답 없이 30초를 끄는 요청은 끊는다.

## 5초의 근거

- 처음에는 외부 서비스가 기록을 늦게 남길 수 있다고 보고 30초로 잡았다. mock을 재 보니 30초 지연 요청도, 느린 요청도 접수하는 즉시 기록했다([mock-observations.md](../mock-observations.md)).
- 남긴 5초는 끊기 직전에 보낸 요청이 네트워크를 건너 도착하는 여유다.
- 이 5초는 ADR-0004의 드문 틈(발송 직전 확인을 통과한 직후 워커가 멈춤)에 대한 완충도 된다. 그 틈에서 중복이 나려면 워커가 "남은 기한(10초 넘음) + 5초", 즉 15초 넘게 멈춰야 한다.
- 설정값(`RECONCILE_DELAY_MS`)이다. 외부 서비스가 바뀌면 그 서비스의 기록 지연을 재서 다시 정한다.

## 검토한 후보

- **응답을 끝까지 기다림(타임아웃을 30초보다 길게)**: 단순하지만, 워커가 죽은 건은 어차피 조회가 필요해 처리 경로가 둘이 된다. 실제 외부 서비스의 최대 지연도 알 수 없다.
- **타임아웃이면 바로 재시도**: 중복 발송이 된다.
- **타임아웃이면 보낸 것으로 간주**: 요청이 닿지 않은 경우 누락이 된다.
- **시도마다 clientRef에 접미사를 붙임**: 조회할 키가 시도 수만큼 흩어진다.
