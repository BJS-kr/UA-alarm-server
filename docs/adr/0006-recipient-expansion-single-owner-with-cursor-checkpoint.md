# ADR-0006. 수신자 확장(Expansion)은 알림당 단일 워커가 전담하고 페이지 단위로 커서를 체크포인트한다

## 배경

대량 알림의 수신 대상은 전체 사용자(약 10만 명)다. 외부 사용자 조회 API는 1회 호출당 최대 1000명씩 페이지 단위로 반환하며, 다음 페이지를 조회하려면 이전 페이지 응답에 포함된 커서(`nextCursor`)를 전달해야 한다.

외부 사용자 목록을 순회하며 수신자별 `Delivery` 행을 생성하는 작업을 수신자 확장(Expansion)이라 정의한다. 약 100페이지를 조회하는 도중 워커 장애가 발생할 수 있으므로 처음부터 재실행하지 않고 중단 지점부터 이어서 진행할 수 있어야 한다.

## 결정

- **단일 알림의 수신자 확장은 단일 워커만 전담하여 수행한다.** 작업 점유(claim), 리스(lease), 펜싱 방식은 발송 점유와 동일한 규칙을 따른다(ADR-0004).
- **매 페이지마다 `Delivery` 일괄 삽입과 다음 커서(`expansion_cursor`) 저장을 단일 트랜잭션으로 커밋한다.** 워커가 비정상 종료되면 리스 만료 후 인계(Takeover)한 워커가 마지막으로 커밋된 커서부터 이어서 진행한다.
- **`(alarm_id, recipient_id)` 복합 유일 제약(Unique Constraint)을 설정한다.** 동일 페이지를 재처리하더라도 중복 `Delivery` 행이 생성되지 않는다.

## 상세

### 동작 규칙

- **커밋된 `Delivery`는 즉시 발송 대상이 된다.** 발송 워커들은 수신자 확장이 모두 완료될 때까지 대기하지 않고 커밋된 페이지의 `Delivery`부터 즉시 점유하여 발송한다.
- **외부 사용자 API 호출 직전마다 리스를 연장한다.** 리스 연장 쿼리는 알림 상태가 `SENDING`이고 담당 워커(`owner`)가 자신일 때만 반영된다. 갱신 건수가 0건이면 알림이 취소되었거나 다른 워커에 인계된 상태이므로 즉시 확장 작업을 중단한다. 이를 통해 사용자 API 조회가 반복 실패하는 상황에서도 다음 조회 시도 전에 알림 취소를 감지할 수 있다.
- **페이지 저장 트랜잭션은 담당 워커(`owner`)와 현재 저장된 커서 값이 모두 일치할 때만 반영한다.** `owner` 조건은 작업 주체를, 커서 조건은 진행 위치를 검증하는 이중 펜싱이다. 일시 정지되었다가 뒤늦게 재개된 이전 담당 워커가 페이지를 중복 삽입하거나 진행 커서를 과거로 되돌리는 현상을 차단한다.
- **자신이 이미 점유 중인 확장 작업도 재점유 대상에 포함한다.** 워커는 미할당 또는 리스 만료 작업뿐만 아니라 자신의 워커 ID가 기록된 작업도 다시 점유한다. 페이지 커밋은 성공했으나 네트워크 오류 등으로 응답만 유실된 경우, 재시도 로직이 커서 불일치(이미 처리된 페이지)를 감지하고 루프를 탈출하더라도 해당 워커가 리스 만료(30초)까지 작업을 방치하지 않고 즉시 최신 커서 기준으로 재점유하여 이어갈 수 있다.
- **커서는 불투명(opaque) 문자열로 취급한다.** 응답 커서가 base64 인코딩된 순번 형태를 띠더라도 애플리케이션이 임의로 커서를 합성하여 다중 워커 병렬 조회를 시도하지 않는다. API 명세에 보장되지 않은 내부 구현에 의존하면 외부 서비스 변경 시 장애가 발생하기 때문이다.
- **수신자 확장과 발송은 코드 모듈을 완전히 분리한다.** 두 모듈은 DB 테이블만 공유하며, 런타임에는 동일한 워커 프로세스 내에서 함께 구동된다.

### 사용자 조회 실패 처리

| 실패 유형                                                    | 처리 방식                                                                                                                                                                                                       |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `5xx`, `429`, `408`, 타임아웃, 연결 오류, 응답 스키마 불일치 | 일시적 오류(재시도 가능). 발송 재시도와 동일한 지수 백오프(1초 시작, 2배씩 증가, 상한 60초, 지터 ±20%)를 적용하여 동일 커서를 재조회한다. 백오프 간격이 상한(60초)에 도달하면 확장 정체 `error` 로그를 기록한다 |
| `400`, `401`, `403`, `404`                                   | 영구 오류(비재시도성 오류, 요청 또는 서버 설정 오류). 수신자 확장을 즉시 중단하고 알림 상태를 취소 진행 중(`CANCELING`)으로 전환한다. 알림 행에 취소 사유 `EXPANSION_FAILED`와 마지막 오류를 기록한다           |

- 조회 실패 횟수는 `alarm_expansion_fetch_failures_total{kind}` 메트릭으로 집계한다.
- 영구 오류 발생 시 일부 수신자만 생성된 상태에서 `COMPLETED`로 종료하지 않는다. 정상 완료로 처리하면 일부 수신자 누락이 은폐되기 때문이다. 이미 발송된 건은 일반 발송 중 취소와 동일하게 `SENT`로 유지되고, 미발송 대기 건은 2단계 취소 정리를 통해 `CANCELED`로 전환된다(ADR-0017). 재발송 여부는 운영자가 판단한다.
- `400` 오류 중 커서 만료 오류는 첫 페이지부터 재조회하면 복합 유일 제약(`ON CONFLICT DO NOTHING`)을 통해 중복 없이 복구할 수 있으나, mock 서버에는 커서 만료 동작이 없으므로 구현하지 않았다.

## 결과 및 한계

수신자 확장이 완료되기 전에는 해당 알림의 전체 수신자 수를 확정할 수 없다.

### 대규모 트래픽 시 확장 방향

시스템 규모가 대폭 커질 경우 수신자 확장은 알림 생성 시마다 독립 작업(Kubernetes Job 등)을 실행하고 완료 시 종료하는 온디맨드 구조로 분리하는 것이 적합하다. 발송 작업은 처리량이 외부 상한(초당 50건)에 묶여 있어 고정된 수의 상시 워커로 충분하지만, 수신자 확장은 대량 알림이 집중될 때만 리소스가 필요하고 평소에는 유휴 상태로 남기 때문이다. 별도 Job으로 분리하면 확장 작업의 메모리 사용량 급증이나 크래시가 발송 워커에 영향을 주지 않으며 작업별 리소스 한도를 독립 설정할 수 있다.

현재 시점에 분리하지 않는 근거는 다음과 같다.

- 외부 사용자 API의 최대 허용 처리량이 명시되어 있지 않다.
- 단일 호스트(Docker Compose) 환경에서는 확장 작업을 늘리면 발송 워커와 CPU·메모리 자원을 경합하게 된다.
- 외부 사용자 API가 순차 커서 방식만 제공하므로 단일 알림 내에서는 병렬 확장이 불가능하다. 워커를 늘려 얻을 수 있는 이점은 다수의 대량 알림을 동시에 확장할 때뿐이며, 단일 알림의 확장 속도를 높이려면 ID 범위(range) 분할 조회 API가 선행되어야 한다.

향후 분리는 용이하다. 수신자 확장 모듈은 발송 모듈과 DB 테이블만 공유하고 리스 및 펜싱으로 소유권을 제어하므로, 별도 Job 컨테이너에서 동일 모듈만 단독 실행하면 된다.

## 검토한 대안

- **다중 워커의 페이지 분할 확장**: 커서 기반 페이지네이션 특성상 이전 페이지의 응답을 받아야 다음 페이지 요청이 가능하다. 또한 사용자 조회 API는 초당 50건 발송 제한의 적용 대상이 아니어서 100페이지 조회에 약 30초(실측)가 소요되므로, 전체 발송 시간(약 33분) 대비 병목 지점이 아니다.
- **수신자 확장 전담 상시 컨테이너 분리**: 전담 컨테이너 역시 장애 대비를 위해 다중화와 리스·펜싱 로직이 동일하게 필요하므로 관리 대상만 증가한다. 알림당 약 30초만 동작하고 나머지 시간은 유휴 상태로 남는다. 코드 레벨에서 모듈이 분리되어 있으므로 필요 시 기동 진입점 설정만 변경하여 분리할 수 있다.
- **오류 유형 구분 없이 무한 재시도**: `401` 등 영구 오류 발생 시에도 워커가 해당 알림 확장에 계속 묶이게 된다. 또한 페이지 저장 시점에만 알림 상태를 확인하면 조회가 연속 실패하는 동안 취소 요청을 감지하지 못한다.
