# ADR-0024. 목록은 커서 방식(keyset)으로 나눈다

## 배경

수신자별 결과 목록(`/deliveries`)은 알림 하나에 최대 10만 건이다. 이것을 페이지로 나눠 보여 줘야 한다. 게다가 발송 중에는 상태가 계속 바뀐다.

## 결정

알림 목록과 수신자별 결과 목록을 커서 방식으로 나눈다.

```
GET /v1/alarms/{id}/deliveries?status=FAILED&limit=100&cursor=...
→ { "items": [...], "nextCursor": "..." | null }
```

- 커서는 마지막으로 본 항목의 위치를 담는다. 다음 페이지는 "그 위치 다음부터 n개"(`WHERE 위치 > 마지막 위치 ORDER BY 위치 LIMIT n`)로 읽는다.
- 커서는 속을 감춘 값(base64)이다. 클라이언트가 형식에 기대지 않으므로, 서버가 형식을 바꿀 수 있다. mock 사용자 API의 커서를 다루는 방식(ADR-0006)과 같다.
- `limit`은 기본 20, 최대 100이다.
- 전체 개수는 응답에 넣지 않는다. 건수는 알림 단건 조회의 상태별 건수로 본다(ADR-0018).

## 이유

- **깊은 페이지도 빠르다.** 인덱스에서 그 위치로 바로 가므로, 마지막 페이지도 첫 페이지와 속도가 같다.
- **발송 중에도 빠지거나 겹치지 않는다.** 위치가 기준이라, 상태가 바뀌는 중에도 페이지를 넘기는 사이 항목이 빠지거나 두 번 나오지 않는다.

## 검토한 후보

- **페이지 번호 방식(`page`, `size`)**: `OFFSET`은 앞의 행을 모두 읽고 버리므로 깊어질수록 느리다. 발송 중에는 페이지 사이에 상태가 바뀐 건이 빠지면서 뒤 항목이 당겨진다. 그래서 어떤 건은 건너뛰고 어떤 건은 두 번 보인다.
