# ADR-0024. 커서 기반(Keyset) 페이지네이션 적용

## 배경

수신자별 발송 결과 목록(`/deliveries`)은 알림 1건당 최대 10만 건에 달하며, 발송 진행 중에는 각 Delivery의 상태가 실시간으로 변경된다. 대량 데이터의 깊은 페이지 조회 성능과 상태 변경 중의 조회 일관성을 보장하는 페이지네이션 방식이 필요하다.

## 결정

알림 목록(`GET /v1/alarms`)과 수신자별 결과 목록(`GET /v1/alarms/{id}/deliveries`) 모두 커서 기반(keyset) 페이지네이션을 적용한다.

```
GET /v1/alarms/{id}/deliveries?status=FAILED&limit=100&cursor=...
→ { "items": [...], "nextCursor": "..." | null }
```

- 커서는 직전 페이지 마지막 항목의 정렬 키 위치를 담으며, 다음 페이지는 `WHERE 키 > 마지막_위치 ORDER BY 키 LIMIT n` 조건으로 조회한다.
- 커서는 불투명(opaque) 문자열(Base64 인코딩)로 제공한다. 클라이언트가 내부 구조에 의존하지 않으므로 서버가 커서 형식을 변경할 수 있으며, 외부 mock 사용자 API의 커서 처리 방식(ADR-0006)과도 일관된다.
- `limit`의 기본값은 20, 최댓값은 100이다.
- 목록 응답에는 전체 건수(`totalCount`)를 포함하지 않는다. 상태별 건수는 알림 단건 조회 API를 통해 확인한다(ADR-0018).

## 근거

- **일정한 페이지 조회 성능**: 인덱스를 통해 커서 위치로 직접 탐색하므로 마지막 페이지 조회도 첫 페이지와 동일한 시간 복잡도로 처리된다.
- **데이터 변경 중 누락·중복 방지**: 고정된 정렬 키 위치를 기준으로 탐색하므로 발송 진행 중 앞선 항목의 상태가 변경되더라도 페이지 간 항목 누락이나 중복 노출이 발생하지 않는다.

## 검토한 대안

- **오프셋 기반 페이지네이션(`page`, `size`)**: `OFFSET`은 앞선 행을 모두 스캔한 뒤 버리므로 페이지가 깊어질수록 선형적으로 느려진다. 또한 발송 중 상태 필터(`?status=PENDING` 등) 조회 시 페이지 이동 사이에 앞선 행의 상태가 바뀌어 결과 집합에서 빠지면 뒤쪽 행이 당겨지면서 항목 누락 또는 중복 조회가 발생한다.
