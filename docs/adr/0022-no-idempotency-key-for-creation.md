# ADR-0022. 알림 생성 요청의 멱등키(Idempotency-Key) 미적용

## 배경

네트워크 오류 등으로 응답을 받지 못한 클라이언트가 알림 생성 요청을 재전송하면 동일한 내용의 알림이 중복 생성된다. 요청 1회가 즉시 외부 부수 효과를 일으키는 결제 API 등에서는 `Idempotency-Key` 헤더로 중복 생성을 방지하는 방식을 주로 사용한다.

## 결정

알림 생성(`POST /v1/alarms`)에 대해서는 별도의 중복 요청 방지 메커니즘을 두지 않는다.

## 근거

- **생성만으로는 외부 발송이 실행되지 않는다**: 실제 발송은 특정 알림 ID에 대한 발송 시작 요청(`POST /v1/alarms/{id}/send`)으로만 시작되며, 발송 시작 요청은 상태 전이 조건으로 중복 실행이 차단된다(ADR-0016). 생성 요청이 중복되더라도 미발송 상태(`CREATED`)의 알림 행이 하나 더 생성될 뿐이다.
- **중복 생성된 미발송 알림은 정리가 단순하다**: 클라이언트가 목록을 조회하여 불필요한 `CREATED` 알림을 취소(`CANCELED`)하면 된다.
- 알림 생성과 발송 시작을 분리한 2단계 설계로 인해 생성 단계의 멱등성 보장 필요성이 낮다.

## 검토한 대안

- **`Idempotency-Key` 헤더 도입**: 키 저장 테이블, TTL 만료 정리, 동일 키에 서로 다른 요청 본문이 유입될 때의 충돌 처리 규칙이 추가로 필요하며, 방지되는 부작용 대비 구현 복잡도가 과도하다.
