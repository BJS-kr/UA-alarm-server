# 모든 워커 종료는 "반납"과 "기한 만료" 두 출구로 수렴한다

워커가 내려가는 경우는 배포, 축소, 크래시, OOM, 멈춤, 네트워크 분리 등 여러 가지지만, 쥐고 있던 건을 처리하는 출구는 둘뿐이다. 정상 종료가 끝까지 성공하면 워커가 쥐고 있던 건을 직접 반납한다. 그 밖의 모든 경우는 기한이 지나 다른 워커가 넘겨받는다(ADR-0004).

넘겨받기는 "누가, 왜 끝냈는가"가 아니라 "기한이 지났다"는 사실로만 일어난다. 그래서 종료시키는 주체(워커 자신, 플랫폼, 운영자)와 복구 경로가 분리된다.

## 출구 1: 정상 종료 (SIGTERM)

배포, 워커 수 축소, 운영자 정지, 호스트 재부팅, 쿠버네티스 롤링 업데이트·drain처럼 종료를 요청받는 경우다.

```
SIGTERM
 → 새 Delivery를 꺼내지 않는다 (펼치기 중이면 현재 페이지를 커밋하고 멈춘다. 재시도를 기다리는 중이면 기다림을 끊는다)
 → 이미 보낸 요청의 응답을 기다려 결과를 기록한다 (최대 HTTP 타임아웃 10초)
 → 꺼냈지만 보내지 않은 Delivery는 대기 상태로 되돌린다 (확실히 안 보냈으므로 즉시 안전)
 → 펼치기 담당을 내려놓는다 (다른 워커가 기한을 기다리지 않고 이어 간다)
 → 연결을 닫고 종료한다
```

- 배포 때마다 일어나는 일이다. 이 경로가 없으면 배포할 때마다 쥐고 있던 건이 전부 기한을 기다린 뒤 결과 미확정이 되어 조회를 거친다.
- `stop_grace_period: 30s`로 둔다. Docker 기본값 10초는 HTTP 타임아웃과 같아 마무리가 잘릴 수 있다.
- 유예 시간을 넘기면 Docker가 SIGKILL을 보내고 출구 2로 합류한다.
- 루프가 쉬는 시간은 모두 멈추라는 요청에 바로 깬다. 처음에는 펼치기가 사용자 조회 실패 뒤 최대 60초를 그냥 쉬어서, 사용자 서비스 장애 중에 배포하면 유예 시간(30초)을 넘겨 강제 종료됐다.
- 신호가 Node 프로세스까지 도달해야 한다. `npm start`나 셸 형식 `CMD`는 신호를 전달하지 않으므로 exec 형식(`CMD ["node", "dist/main-worker.js"]`)과 compose의 `init: true`를 쓴다.

## 출구 2: 기한 만료 (그 밖의 모든 경우)

```
[워커가 결과를 기록하지 못함]
 ├ 크래시, OOM, docker kill                      → 프로세스가 없다
 ├ DB와 갈라짐                                    → 기록이 들어가지 않는다
 └ 이벤트 루프 막힘, 긴 GC, docker pause, SIGSTOP  → 멈춰 있다
        ↓
 그 워커가 쥔 건의 기한(30초)이 지남
        ↓
 다른 워커의 정리 루프가 결과 미확정으로 바꾸고 owner를 비움
        ↓
 넘겨받은 시각 + 5초 → clientRef 조회 → 완료 확정 또는 재발송 (ADR-0002)

 멈췄던 워커가 깨어나면 → 기한이 지난 건은 보내지 않고, 늦은 결과 기록은 펜싱에 걸린다. 종료하지 않고 계속 일한다
 종료된 컨테이너 → restart 정책이 새 ID로 새 워커를 띄움
```

## 관련 장치 정리

| 장치 | 누가 | 하는 일 |
| --- | --- | --- |
| 기한 (30초, claim 쿼리가 적음) | 워커 자신 | 이 시각까지 결과가 기록되지 않으면 남이 가져가도 된다고 DB에 적는다 |
| 넘겨받기 (2초마다) | 살아 있는 워커 누구나 | DB 시계로 기한이 지난 IN_FLIGHT 건을 결과 미확정으로 돌린다 |
| 발송 직전 확인 | 워커 자신 | 남은 기한이 응답 한도보다 짧으면 보내지 않고 반납한다 |
| 펜싱 (owner, 시도 번호) | DB | 넘겨받힌 뒤 늦게 온 결과 기록을 0건 갱신으로 거부한다 |
| 트랜잭션 유휴 한도 (5초) | Postgres | 트랜잭션 도중 멈춘 워커의 세션을 끝내 행 잠금을 푼다 |
| healthcheck / liveness probe | 플랫폼 | 얼어붙은 컨테이너를 재시작한다 (일손 보충, 정확성과 무관) |

## 얼어붙은 컨테이너의 재시작

정확성은 기한과 펜싱이 지키므로, 얼어붙은 컨테이너를 재시작하는 일은 일손을 되찾는 문제일 뿐이다. 애플리케이션은 판단 재료(healthcheck)만 제공하고 컨테이너를 죽일 권한은 갖지 않는다. healthcheck 방식은 운영 결정에서 정한다(ADR-0026).

- **docker compose (제출 환경)**: healthcheck는 컨테이너를 unhealthy로 표시만 하고 재시작하지 않는다. 운영자가 재시작할 때까지 워커 한 대만큼 일손이 줄어든 채로 계속 발송한다.
- **쿠버네티스 (운영 환경 가정)**: liveness probe가 실패하면 kubelet이 컨테이너를 재시작한다.

## 검토한 후보

- **compose 환경에 자동 재시작 도구(autoheal 등) 추가**: unhealthy 컨테이너를 재시작하려면 `docker.sock`이 필요하다. 호스트 root 권한을 가진 컨테이너와 의존성이 하나 늘어나므로(ADR-0005) 두지 않는다.
