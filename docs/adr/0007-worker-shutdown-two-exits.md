# ADR-0007. 워커 종료 시 점유 중인 건은 정상 반납과 리스 만료 두 경로로만 복구한다

## 배경

워커는 배포, 스케일 인(워커 수 축소), 프로세스 크래시, 메모리 부족(OOM), 이벤트 루프 블로킹, 네트워크 단절 등 다양한 원인으로 중단된다. 종료 원인마다 개별 복구 경로를 설계하면 예외 케이스가 복잡해지고 누락이 발생하기 쉽다.

## 결정

워커 중단 시 점유 중인 건의 복구 경로를 두 가지로 단일화한다.

1. **정상 반납(Graceful Release)**: 정상 종료 절차가 끝까지 완료되면 워커가 점유 중이던 건을 스스로 반환한다.
2. **리스 만료(Lease Expiration)**: 그 외 모든 비정상 종료 및 정지 상황에서는 리스 만료 시각(`lease_until`)이 경과한 뒤 다른 워커가 인계(Takeover)한다(ADR-0004).

인계 로직은 이전 워커의 종료 원인이나 주체를 구분하지 않고 오직 DB 시계 기준 리스 만료 여부만 확인한다. 따라서 워커 자체, 컨테이너 플랫폼, 운영자 중 누가 프로세스를 중단시켰든 동일한 경로로 복구된다.

## 상세

### 경로 1: 정상 종료 (`SIGTERM`)

배포, 스케일 인, 운영자 수동 정지, 호스트 재부팅, Kubernetes 롤링 업데이트 등 종료 시그널을 수신한 경우의 처리 흐름이다.

```
SIGTERM 수신
 → 신규 Delivery 점유(claim) 중단
   (수신자 확장 중이면 현재 처리 중인 페이지만 커밋하고 중단. 재시도 대기(sleep) 중이면 즉시 깨어남)
 → 이미 전송한 HTTP 요청의 응답을 대기하여 결과 기록 (응답 타임아웃 10초, 종료 대기 상한 20초)
 → 점유했으나 아직 전송하지 않은 Delivery를 대기(PENDING) 상태로 반납 (미전송이 확실하므로 즉시 재점유 가능)
 → 수신자 확장 담당(owner) 해제 (다른 워커가 리스 만료를 기다리지 않고 즉시 인계)
 → DB 및 HTTP 연결 종료 후 프로세스 종료
```

- 배포 시마다 실행되는 기본 경로다. 이 경로가 없으면 배포할 때마다 점유 중이던 건들이 모두 리스 만료(30초)를 기다린 뒤 결과 미확정(`UNCONFIRMED`)으로 전환되어 외부 발송 내역 조회를 거쳐야 한다.
- Docker Compose 설정에 `stop_grace_period: 30s`를 지정한다. Docker 기본값(10초)은 HTTP 응답 타임아웃(10초)과 동일하여 진행 중인 요청 처리가 강제 중단될 수 있다.
- 유예 시간(30초)을 초과하면 Docker가 `SIGKILL`을 전송하며, 남은 건은 경로 2(리스 만료)로 전환되어 복구된다.
- 모든 대기(sleep) 타이머는 종료 시그널 수신 즉시 해제된다. 그렇지 않으면 외부 사용자 서비스 장애 중에 배포할 때 수신자 확장 재시도 대기(최대 60초)로 인해 유예 시간을 초과하여 강제 종료된다.
- 종료 시그널이 Node.js 프로세스에 직접 전달되어야 한다. `npm start`나 셸 형식 `CMD`는 시그널을 전달하지 않으므로 exec 형식(`CMD ["node", "dist/main-worker.js"]`)과 Compose의 `init: true` 설정을 함께 사용한다.

### 경로 2: 리스 만료 (그 외 모든 비정상 상황)

```
[워커가 결과를 기록하지 못함]
 ├ 프로세스 크래시, OOM, docker kill                → 프로세스 소멸
 ├ DB 연결 단절                                     → 결과 기록 불가
 └ 이벤트 루프 블로킹, 긴 GC, docker pause, SIGSTOP → 프로세스 일시 정지
        ↓
 해당 워커가 점유한 건의 리스(30초) 만료
        ↓
 다른 워커의 정리 루프(2초 주기)가 결과 미확정(UNCONFIRMED)으로 전환하고 owner 초기화
        ↓
 인계 시각 + 5초 후 clientRef로 발송 내역 조회 → 완료(SENT) 확정 또는 대기(PENDING) 전환 후 재발송 (ADR-0002)

 일시 정지 후 재개된 워커: 리스가 만료된 건은 발송하지 않으며, 지연된 결과 기록은 펜싱으로 차단됨. 프로세스를 종료하지 않고 작업 재개
 종료된 컨테이너: 컨테이너 restart 정책에 의해 새로운 워커 ID로 재기동
```

### 복구 관여 장치 요약

| 장치                              | 수행 주체       | 역할                                                                                               |
| --------------------------------- | --------------- | -------------------------------------------------------------------------------------------------- |
| 리스 (30초, claim 쿼리 시 기록)   | 워커            | 지정된 만료 시각까지 결과 기록이 없으면 다른 워커가 인계해도 됨을 DB에 명시                        |
| 리스 만료 회수 및 인계 (2초 주기) | 모든 정상 워커  | DB 시계 기준으로 리스가 만료된 `IN_FLIGHT` 건을 `UNCONFIRMED`로 전환                               |
| 발송 직전 리스 확인               | 워커            | 잔여 리스 시간이 응답 타임아웃보다 짧으면 전송하지 않고 반납                                       |
| 펜싱 (`owner`, 시도 번호)         | DB              | 인계 이후 지연 도달한 이전 워커의 결과 기록을 0건 갱신으로 거부                                    |
| 트랜잭션 유휴 타임아웃 (5초)      | PostgreSQL      | 트랜잭션 도중 멈춘 워커의 세션을 강제 종료하여 행 잠금 해제                                        |
| `healthcheck`, `liveness probe`   | 컨테이너 플랫폼 | 응답 없는 컨테이너를 비정상으로 표시하거나 재시작 (처리 용량 확보 목적이며 데이터 정확성과는 무관) |

### 응답 없는 컨테이너의 재시작 책임

발송 정확성(중복·누락 방지)은 리스와 펜싱만으로 보장된다. 따라서 멈춘 컨테이너를 재시작하는 것은 줄어든 워커 처리 용량을 복구하는 운영상의 문제다. 애플리케이션은 상태 판별 지표(`healthcheck`, ADR-0026)만 노출하며 컨테이너를 강제 종료할 권한은 갖지 않는다.

- **Docker Compose (과제 제출 환경)**: `healthcheck` 실패 시 컨테이너 상태를 `unhealthy`로 표시만 하고 자동 재시작하지 않는다. 운영자가 수동 재시작할 때까지 워커 1대분의 처리 용량이 줄어든 상태로 나머지 워커가 발송을 계속한다.
- **Kubernetes (운영 환경 가정)**: `liveness probe` 실패 시 kubelet이 컨테이너를 자동 재시작한다.

## 검토한 대안

- **Docker Compose에 자동 재시작 컨테이너(`autoheal` 등) 추가**: `unhealthy` 컨테이너를 재시작하려면 `docker.sock` 마운트가 필요하다. 호스트 root 권한을 가진 컨테이너와 외부 의존성이 추가되므로(ADR-0005) 도입하지 않는다.
