# ADR-0016. 알림 상태 전이는 조건부 UPDATE 한 문장으로 하고, 응답은 "이미 목표 상태인가"로 정한다

## 배경

같은 알림에 발송 시작과 취소가 동시에 올 수 있다. 응답을 못 받은 클라이언트가 같은 요청을 다시 보낼 수도 있다. 이런 경우에도 상태가 한 번만, 올바르게 바뀌어야 한다.

"먼저 읽고, 확인한 뒤 쓰는" 방식(SELECT 후 UPDATE)은 읽고 쓰는 사이에 다른 요청이 끼어들 틈이 있다. 두 요청이 같은 CREATED를 읽고 둘 다 바꿀 수 있다.

## 결정

ADR-0008의 상태 그림에서 화살표 하나하나를, 확인과 변경을 한 문장으로 묶은 조건부 UPDATE로 실행한다.

```sql
UPDATE alarms SET status = 'SENDING', ... WHERE id = $1 AND status = 'CREATED'
```

"지금 CREATED일 때만 SENDING으로 바꾼다"는 뜻이다. 같은 전이가 동시에 여러 번 와도, 행 잠금 때문에 한쪽만 성공하고 나머지는 0건이 바뀐다.

## 전이표와 응답

| 요청 | 지금 상태 | 결과 |
| --- | --- | --- |
| 발송 시작 | CREATED | SENDING으로 바꿈 |
| 발송 시작 | SENDING, COMPLETED | 성공. 바꾸지 않고 지금 상태를 돌려준다 |
| 발송 시작 | CANCELING, CANCELED | 409 Conflict |
| 취소 | CREATED | CANCELED로 바꿈 |
| 취소 | SENDING | CANCELING으로 바꿈 |
| 취소 | CANCELING, CANCELED | 성공. 바꾸지 않고 지금 상태를 돌려준다 |
| 취소 | COMPLETED | 409 Conflict |

- **이미 목표 상태면 성공이다.** 응답을 못 받아 다시 보낸 클라이언트가 오류를 받지 않게 한다. 같은 요청을 여러 번 보내도 결과가 같다(멱등).
- **목표 상태로 갈 수 없을 때만 409다.** 409 응답에는 지금 상태를 담는다.
- **이 요청이 바꿨으면, `RETURNING`으로 받은 행으로 답한다.** 0건이 바뀌었을 때만 지금 상태를 다시 읽어, 위 표로 응답을 정한다.

## 검토한 후보

- **이미 시작된 알림에 대한 시작 요청에 409**: 다시 보낸 클라이언트가, 실제로는 성공했는데도 오류를 받는다.
- **`Idempotency-Key` 헤더로 요청 단위 중복 제거**: 키와 응답을 저장할 곳이 따로 필요하다. 시작과 취소처럼 결과가 상태로 남는 요청은 상태만으로 판단할 수 있다.
- **바꾼 뒤에도 상태를 다시 읽어 응답**: 발송 시작이 바꾼 직후 취소가 끼어들면, 실제로 발송을 시작한 요청이 CANCELING을 읽고 409를 받는다. 단위 테스트가 이 순서를 정해 놓고 확인한다(고의 결함 S27).
