# ADR-0016. 조건부 UPDATE를 통한 알림 상태 전이 및 목표 상태 기준 멱등 응답

## 배경

동일한 알림에 대해 발송 시작과 취소 요청이 동시에 유입되거나, 응답을 수신하지 못한 클라이언트가 동일 요청을 재전송할 수 있다. 이러한 동시 요청 및 재시도 상황에서도 상태 전이는 정확히 한 번만 수행되어야 한다.

조회 후 갱신하는 방식(`SELECT` 후 `UPDATE`)은 읽기와 쓰기 사이에 경쟁 상태(race condition)가 발생하여 두 요청이 모두 `CREATED`를 읽고 중복 처리될 수 있다.

## 결정

ADR-0008에 정의된 각 상태 전이를 조건 확인과 상태 변경이 결합된 단일 조건부 `UPDATE` 문으로 실행한다.

```sql
UPDATE alarms SET status = 'SENDING', ... WHERE id = $1 AND status = 'CREATED'
```

현재 상태가 `CREATED`일 때만 `SENDING`으로 변경한다. 동일 전이 요청이 동시에 여러 번 유입되더라도 행 잠금(row lock)에 의해 선행 요청만 성공하고 후행 요청은 변경 행 수가 0건이 된다.

## 상세: 상태 전이표 및 응답 규칙

| 요청      | 현재 상태               | 처리 결과                                        |
| --------- | ----------------------- | ------------------------------------------------ |
| 발송 시작 | `CREATED`               | `SENDING`으로 전이                               |
| 발송 시작 | `SENDING`, `COMPLETED`  | 성공 응답. 상태를 변경하지 않고 현재 상태를 반환 |
| 발송 시작 | `CANCELING`, `CANCELED` | `409 Conflict`                                   |
| 취소      | `CREATED`               | `CANCELED`로 전이                                |
| 취소      | `SENDING`               | `CANCELING`으로 전이                             |
| 취소      | `CANCELING`, `CANCELED` | 성공 응답. 상태를 변경하지 않고 현재 상태를 반환 |
| 취소      | `COMPLETED`             | `409 Conflict`                                   |

- **이미 목표 상태에 도달한 경우 성공으로 응답한다**: 네트워크 오류 등으로 응답을 받지 못해 재시도한 클라이언트가 오류를 받지 않도록 보장하여 멱등성(idempotency)을 제공한다.
- **목표 상태로 전이할 수 없는 상태일 때만 `409`를 반환한다**: `409` 응답 본문에는 현재 상태를 포함한다.
- **조건부 `UPDATE`가 행을 변경한 경우 `RETURNING` 절로 반환된 행을 사용해 즉시 응답한다**: 변경된 행이 0건일 때만 현재 상태를 다시 조회(`SELECT`)하여 위 표에 따라 응답을 결정한다.

## 검토한 대안

- **이미 시작된 알림에 대한 발송 시작 요청에 `409` 반환**: 실제로는 발송 시작에 성공했음에도 재전송한 클라이언트가 오류 응답을 받게 된다.
- **`Idempotency-Key` 헤더를 통한 요청 단위 중복 제거**: 키와 응답 스냅숏을 저장할 별도 테이블이 필요하다. 발송 시작과 취소처럼 결과가 리소스 상태로 남는 동작은 현재 상태만으로 멱등 응답을 판정할 수 있다.
- **`UPDATE` 성공 후에도 별도 `SELECT`로 상태를 재조회하여 응답**: 발송 시작 `UPDATE` 직후 취소 요청이 끼어들면 실제로 발송을 시작시킨 요청이 `CANCELING`을 읽고 `409`를 반환받게 된다. 단위 테스트에서 이 인터리빙 순서를 재현하여 검증한다(고의 결함 S27).
