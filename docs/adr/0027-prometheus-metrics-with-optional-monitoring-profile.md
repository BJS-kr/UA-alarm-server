# ADR-0027. Prometheus 메트릭 노출 및 선택적 모니터링 프로필 구성

## 배경

운영 환경에서는 초당 발송 처리량, 429 응답 및 외부 장애 발생 여부, 중복 발송 탐지 여부를 수치로 관측해야 한다. 반면 기본 실행 환경에 모니터링 컨테이너를 상시 포함하면 리소스 부담이 커진다.

## 결정

- `api`와 `worker`는 관리 포트의 `/metrics` 엔드포인트로 Prometheus 형식의 메트릭을 노출한다.
- 메트릭 수집 라이브러리로 `prom-client`를 사용한다. Node.js 기본 내장 기능에는 Prometheus 포맷 직렬화가 없으며, 히스토그램 버킷 집계와 텍스트 포맷을 직접 구현하면 오류가 발생하기 쉽다. 표준 기능만으로 대체할 수 없는 경우에 한해 의존성을 추가한다(ADR-0005).
- Prometheus 컨테이너는 Docker Compose의 `monitoring` 프로필로 분리한다. 기본 `docker compose up` 실행 시에는 기동하지 않으며, `docker compose --profile monitoring up` 실행 시에만 함께 기동한다.

## 상세

### 메트릭 출처 구분

| 출처     | 메트릭                                                                                                                                                                                                                                                                                                                                                                                                                    | 근거                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `worker` | 발송 요청 결과별 건수, 응답 지연 시간, 진행 중(in-flight) 요청 수, 긴급 알림의 발송 시작부터 접수 완료까지 소요 시간, 발송 내역 조회(Reconciliation) 결과별 건수, 중복 발송 탐지 건수, 펜싱(fencing) 차단 건수, 리스 만료 인계(Takeover) 건수, 서킷 브레이커 발동 및 프로브(probe, 단건 시험 발송) 결과, 429 일시 정지 건수, 토큰 버킷 획득 결과, 수신자 확장(Expansion) 페이지 수 및 조회 실패 건수, 폴링 루프 오류 건수 | 워커 프로세스 메모리 내부에서 발생하는 이벤트 지표다                                                         |
| `api`    | 우선순위별 대기 건수, 점유(claim) 가능 상태인 가장 오래된 대기 건의 경과 시간, 가장 오래된 전송 중(`IN_FLIGHT`) 건의 경과 시간, 결과 미확정(`UNCONFIRMED`) 건수, 상태별 알림 수                                                                                                                                                                                                                                           | DB 집계 기반 게이지 지표다. 워커마다 집계하면 동일한 값이 중복 노출되므로 단일 `api` 인스턴스에서만 집계한다 |

모든 메트릭 이름은 `alarm_` 접두사로 시작하며, 전체 목록과 설명(help)은 각 프로세스의 `/metrics` 엔드포인트에서 확인할 수 있다.

### 경보 규칙 예시

| 조건                                                  | 의미                                                                                                                                                  |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `alarm_duplicates_detected_total` 증가                | 동일 수신자에 대한 중복 발송이 확인됨(ADR-0004의 극단적 경합 구간). 즉시 원인을 확인한다                                                              |
| `alarm_rate_limit_pauses_total`이 5분 이상 지속 증가  | 처리량 제한 설정이 외부 발송 서비스의 실제 한도와 불일치한다                                                                                          |
| `alarm_breaker_trips_total`이 5분 이상 지속 증가      | 외부 발송 서비스 장애가 지속되고 있다                                                                                                                 |
| `alarm_oldest_in_flight_seconds` > 60                 | 리스 만료 회수 및 인계(Takeover)가 동작하지 않는다. 리스(30초)가 만료된 건은 2초 주기로 인계되어야 하므로, 활성 워커가 없거나 모든 워커가 멈춘 상태다 |
| `alarm_pending_oldest_due_seconds{priority="0"}` > 10 | 긴급 알림 처리가 지연되고 있다                                                                                                                        |

중복 탐지 메트릭은 중복 발송을 0에 수렴시키되, 발생 시 운영 단계에서 즉시 감지하기 위한 장치다.

### 수집 및 시각화 구성

기본 실행은 최소 컨테이너 구성을 유지하고, 필요 시 단일 명령(`--profile monitoring`)으로 메트릭 수집 및 그래프 조회를 활성화한다. Compose 기본 프로필 기능을 사용하므로 별도 도구가 추가되지 않는다. Grafana 대시보드 및 위 경보 규칙 설정 파일은 현재 구현 범위에 포함하지 않는다.

## 검토한 대안

- **`/metrics` 엔드포인트만 노출**: 메트릭 값을 `curl`로만 확인할 수 있어 시계열 추이를 즉시 파악하기 어렵다.
- **Prometheus와 Grafana를 기본 구성에 포함**: 매 실행마다 컨테이너 2개가 추가 기동되며 대시보드 설정을 상시 관리해야 한다.
- **메트릭 텍스트 포맷 직접 구현**: 히스토그램 버킷 집계 등에서 오류가 발생하기 쉬우며 표준 라이브러리를 배제할 이유가 없다.
