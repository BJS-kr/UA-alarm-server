# 메트릭은 Prometheus 형식으로 내보내고, 수집·화면은 선택 실행 프로필로 둔다

api와 worker는 `/metrics`를 Prometheus 형식으로 내보낸다. 라이브러리는 `prom-client`를 쓴다. Node에는 Prometheus 형식을 만드는 기본 기능이 없고, 히스토그램까지 직접 구현하면 버킷과 형식에서 실수하기 쉽다. ADR-0005의 "이미 가진 것으로 해결되지 않을 때만 추가"에 해당하는 의존성이다.

## 메트릭이 나오는 곳

| 출처 | 메트릭 | 이유 |
| --- | --- | --- |
| worker | 발송 요청 결과별 건수, 응답 시간 히스토그램, 진행 중 요청 수, 서킷 브레이커 발동·정지 여부, 조회 결과별 건수, 중복 탐지 건수, 넘겨받기·무효 선언 횟수 | 워커 메모리 안에서 일어나는 일 |
| api | 우선순위별 대기 건수, 가장 오래된 진행 중 건의 나이, 상태별 알림 수 | DB에서 세는 값이라, 워커마다 세면 같은 값이 여러 번 나오므로 한 곳에서만 센다 |

## 경보 규칙 예시 (README)

| 조건 | 의미 |
| --- | --- |
| 중복 탐지 ≥ 1 | ADR-0004의 드문 틈이 실제로 일어났다. 즉시 확인한다 |
| 429가 5분 넘게 지속 | 처리량 제한 설정이 외부 서비스와 맞지 않는다 |
| 서킷 브레이커 정지가 5분 넘게 지속 | 외부 발송 서비스 장애 |
| 진행 중인 건의 나이 > 1분 | 멈춘 워커가 있다 |
| 긴급 대기 건이 10초 넘게 남음 | 긴급 알림이 밀리고 있다 |

중복 탐지 메트릭은 "중복을 0에 가깝게 만들고, 생기면 반드시 알아챈다"는 약속을 운영에서 실제로 알아채게 하는 장치다.

## 수집과 화면

Prometheus는 compose의 `monitoring` 프로필로 넣는다. 기본 `docker compose up`에는 뜨지 않고, `docker compose --profile monitoring up`으로 실행할 때만 함께 뜬다. 기본 실행은 최소 구성을 지키면서, 원하면 명령 하나로 그래프를 볼 수 있다. 프로필은 compose의 기본 기능이라 도구가 늘지 않는다. Grafana 대시보드는 시간이 남으면 같은 프로필에 추가한다.

## 검토한 후보

- **`/metrics`만 열기**: 평가자가 숫자를 `curl`로만 볼 수 있다.
- **Prometheus와 Grafana를 기본 구성에 포함**: 매번 컨테이너 두 개가 더 뜨고 대시보드 설정을 관리해야 한다.
- **메트릭 형식을 직접 구현**: 히스토그램 구현에서 실수하기 쉽고, 표준 라이브러리를 피할 이유가 없다.
