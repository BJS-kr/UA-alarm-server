# ADR-0027. 메트릭은 Prometheus 형식으로 내보내고, 수집과 화면은 선택해서 켜는 프로필로 둔다

## 배경

운영자는 "지금 초당 몇 건을 보내는가", "429나 장애가 나고 있는가", "중복이 생겼는가"를 숫자로 봐야 한다. 그렇다고 기본 실행에 모니터링 컨테이너를 잔뜩 띄우면 무거워진다.

## 결정

- api와 worker는 관리 포트의 `/metrics`로 Prometheus 형식의 메트릭을 내보낸다.
- 라이브러리는 `prom-client`를 쓴다. Node에는 Prometheus 형식을 만드는 기본 기능이 없고, 히스토그램까지 직접 만들면 버킷과 형식에서 실수하기 쉽다. "이미 가진 것으로 안 될 때만 더한다"(ADR-0005)에 해당한다.
- Prometheus는 compose의 `monitoring` 프로필로 둔다. 기본 `docker compose up`에는 뜨지 않고, `docker compose --profile monitoring up`으로 실행할 때만 함께 뜬다.

## 메트릭이 나오는 곳

| 출처 | 메트릭 | 이유 |
| --- | --- | --- |
| worker | 발송 요청 결과별 건수, 응답 시간, 응답을 기다리는 요청 수, 긴급 알림의 시작부터 접수까지 걸린 시간, 조회 결과별 건수, 중복 탐지, 펜싱에 걸린 기록, 넘겨받기, 브레이커 발동과 시험 발송 결과, 429 정지, 토큰 요청 결과, 펼치기 페이지와 조회 실패, 루프 오류 | 워커 메모리 안에서 일어나는 일이다 |
| api | 우선순위별 대기 건수, 지금 꺼낼 수 있는데 남은 가장 오래된 대기 건의 나이, 가장 오래 전송 중인 건의 나이, 결과 미확정 건수, 상태별 알림 수 | DB에서 세는 값이다. 워커마다 세면 같은 값이 여러 번 나오므로, 한 곳에서만 센다 |

이름은 모두 `alarm_`으로 시작한다. 전체 목록은 각 `/metrics`에서 설명(help)과 함께 볼 수 있다.

## 경보 규칙 예시

| 조건 | 뜻 |
| --- | --- |
| `alarm_duplicates_detected_total` 증가 | 같은 수신자에게 두 번 나간 것이 확인됐다(ADR-0004의 드문 틈). 바로 확인한다 |
| `alarm_rate_limit_pauses_total`이 5분 넘게 계속 증가 | 처리량 제한 설정이 외부 서비스와 맞지 않는다 |
| `alarm_breaker_trips_total`이 5분 넘게 계속 증가 | 외부 발송 서비스 장애 |
| `alarm_oldest_in_flight_seconds` > 60 | 넘겨받기가 돌지 않는다. 기한(30초)이 지난 건은 2초 안에 넘겨받혀야 하므로, 살아 있는 워커가 없거나 모두 멈췄다 |
| `alarm_pending_oldest_due_seconds{priority="0"}` > 10 | 긴급 알림이 밀리고 있다 |

중복 탐지 메트릭은 "중복을 0에 가깝게 만들고, 생기면 반드시 알아챈다"는 약속을 운영에서 실제로 알아채게 하는 장치다.

## 수집과 화면

기본 실행은 최소 구성을 지키면서, 원하면 명령 하나로 그래프를 볼 수 있다. 프로필은 compose의 기본 기능이라 도구가 늘지 않는다. Grafana 대시보드와 위의 경보 규칙은 아직 넣지 않았다.

## 검토한 후보

- **`/metrics`만 열기**: 평가자가 숫자를 `curl`로만 볼 수 있다.
- **Prometheus와 Grafana를 기본 구성에 포함**: 매번 컨테이너 두 개가 더 뜨고, 대시보드 설정을 관리해야 한다.
- **메트릭 형식을 직접 구현**: 히스토그램에서 실수하기 쉽고, 표준 라이브러리를 피할 이유가 없다.
