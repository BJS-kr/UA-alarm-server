# ADR-0004. 워커가 점유한 건에는 리스(lease)를 부여하고, 지연된 워커의 쓰기는 펜싱으로 차단한다

## 배경

워커가 `Delivery` 건을 점유하여 발송하는 도중 비정상 종료되거나 일시 정지될 수 있다. 해당 건을 다른 워커가 인계(Takeover)하여 처리하지 않으면 수신자 누락이 발생한다.

분산 환경에서는 프로세스의 영구 종료와 일시 정지(긴 GC pause, 이벤트 루프 블로킹 등)를 외부에서 즉시 구별할 수 없다. 예를 들어 워커 A가 발송 직전 긴 GC로 40초간 멈춘 사이 워커 B가 해당 건을 인계받아 발송을 완료한 뒤, 뒤늦게 재개된 워커 A가 동일 건을 다시 발송하면 중복이 발생한다. 또한 워커 A가 뒤늦게 실패 상태를 기록하여 워커 B가 기록한 성공 상태를 덮어쓰는 문제도 방지해야 한다.

## 결정

세 가지 장치를 결합하여 사용한다.

1. **리스(lease)**: 워커가 건을 점유(claim)할 때 해당 행에 만료 시각(`lease_until`, 현재 시각 + 30초)을 기록한다. 만료 시각 내에 결과가 기록되지 않으면 다른 워커가 리스 만료 건을 회수하여 인계(Takeover)한다.
2. **인계 건의 발송 내역 조회 후 재발송**: 인계받은 워커는 즉시 재발송하지 않고 외부 발송 내역을 먼저 조회(Reconciliation)한다. 이미 전송된 기록이 있으면 완료(`SENT`)로 확정하고, 기록이 없을 때만 재발송한다(ADR-0002).
3. **펜싱(Fencing)**: 결과를 기록할 때 현재 담당 워커(`owner`)가 자신이고 시도 번호도 자신이 점유할 때의 번호와 일치하는 경우에만 조건부 `UPDATE`를 수행한다. 인계 과정에서 `owner`가 초기화되므로, 뒤늦게 재개된 워커 A의 쓰기는 0건 갱신으로 거부된다.

리스 만료 여부는 DB 시계 하나로만 판정하므로 워커 간 시계 오차로 인해 판단이 엇갈리지 않는다.

이 구조는 AWS SQS의 visibility timeout(점유된 메시지를 정해진 시간 동안 숨기고 만료 시간 내 미처리 시 재노출) 및 분산 잠금의 fencing token(지연된 이전 소유자의 쓰기 차단)과 동일한 방식이다.

## 상세

### 처리 흐름

1. 워커가 대기(`PENDING`) 건을 점유(claim)한다. 단일 `UPDATE` 쿼리(claim 쿼리)가 `status = IN_FLIGHT`, `owner = 워커 ID`, `lease_until = 현재 시각 + 30초`를 함께 기록한다.
2. 요청 바이트를 소켓에 쓰기 직전, 남은 리스 시간이 HTTP 응답 타임아웃(10초)보다 긴지 검증한다. 짧으면 발송하지 않고 반납한다.
3. 응답을 수신하면 펜싱 조건을 걸어 결과를 기록한다.
4. 워커가 종료되거나 멈춰 결과를 기록하지 못하면, 다른 워커의 정리 루프(2초 주기)가 만료 시각이 지난 건을 결과 미확정(`UNCONFIRMED`)으로 변경하고 `owner`를 비운다(리스 만료 회수 및 인계).
5. 인계된 건은 5초 후 발송 내역을 조회하여 기록이 있으면 완료로 확정하고, 없으면 재발송한다(ADR-0002).
6. 멈췄던 워커가 재개되어 결과를 기록하려 해도 `owner`가 비어 있으므로 0건 갱신으로 거부된다. 해당 워커는 프로세스를 종료하지 않고 계속 작업을 수행한다.

### 동작 규칙

- **워커 ID**: 프로세스가 기동될 때마다 새로 생성하는 무작위 양의 정수다. 재시작된 프로세스가 이전과 동일한 ID를 사용하면 이전 실행이 남긴 건과 현재 건을 쓰기 조건에서 구별할 수 없다.
- **리스 시간 30초**: 응답 타임아웃(10초)과 결과 기록 시간을 충분히 포괄한다. 정상 상태에서는 만료 시각 내에 결과가 기록되어 인계가 발생하지 않는다. 단건 발송은 응답 타임아웃 내에 종료되므로 리스를 연장하지 않는다.
- **소켓 쓰기 직전에 검증하는 이유**: 건을 점유한 뒤 실제 전송하기까지는 소켓을 배정받고 TCP 연결을 맺는 시간차가 존재한다. 그보다 앞서 검증하면, 검증 직후의 틈에서 멈췄다 재개된 워커가 이미 인계된 건을 전송할 수 있다. 소켓 쓰기 직전이 차단 가능한 마지막 시점이므로 1회 검증으로 충분하다.
- **워커 측 리스 판정의 보수성**: 워커는 claim 쿼리를 보내기 직전에 측정한 시각에 30초를 더해 로컬 만료 시각으로 삼는다. 시계는 역행하지 않는 단조 시계(monotonic clock)를 사용한다. 이 시각은 DB가 `lease_until`을 기록하는 시각보다 항상 이르므로 워커 측 판정이 늘 보수적이다.
- **사전 검증에서 차단된 건**: 전송하지 않았으므로 시도 횟수를 되돌리고 대기(`PENDING`)로 전환한다. 외부 장애가 아니므로 서킷 브레이커(ADR-0014) 실패 횟수에 반영하지 않는다.
- **리스 만료 회수(인계)**: 모든 워커가 2초마다 실행한다. 여러 워커가 동시에 실행해도 `SKIP LOCKED`와 조건부 `UPDATE`를 통해 한 번만 반영된다. 인계된 건에는 마지막 오류로 `LEASE_EXPIRED`가 기록된다.
- **펜싱에 차단된 결과의 사후 확인**: 펜싱으로 거부된 결과도 즉시 폐기하지 않고 `clientRef`로 발송 내역을 조회한다. 실제로 두 번 전송된 사실이 확인되면 `alarm_duplicates_detected_total` 메트릭과 `error` 로그를 남긴다.
- **알림 단위 작업(수신자 확장, 취소 정리)**: 동일한 방식으로 `owner`와 만료 시각(`lease_until`)을 기록하고, 만료 시 다른 워커가 인계받는다. 수신자 확장(Expansion)은 페이지를 반복 조회하는 장기 작업이므로 사용자 API를 호출하기 직전마다 리스를 연장한다. 연장 `UPDATE`가 0건이면 취소되었거나 인계된 것이므로 즉시 중단한다(ADR-0006).
- **일시 정지된 워커가 점유한 행 잠금**: 워커가 트랜잭션 도중 멈추면 알림 행 잠금을 점유한 채 유지되어 같은 알림의 결과 기록을 모두 블로킹한다. 이를 방지하기 위해 워커의 DB 연결에 `idle_in_transaction_session_timeout`(5초)을 설정한다. 트랜잭션 도중 5초 이상 후속 쿼리가 없으면 PostgreSQL이 해당 세션을 종료하고 잠금을 해제한다. 정상 트랜잭션은 수 ms 내에 완료되므로 영향이 없다.
- **시간 설정값의 불변식**: `응답 타임아웃(10초) < 발송 리스 시간(30초)`, `사용자 조회 타임아웃(10초) < 작업 리스 시간(30초)` 관계를 기동 시 검증하며, 위반 시 프로세스를 시작하지 않는다(ADR-0030).

## 결과 및 한계

### 장애 상황별 결과

| 상황                                                            | 동작 결과                                                                                                                                                      |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 크래시, OOM, `docker kill`                                      | 해당 워커가 처리 중이던 건(최대 50건)은 리스 만료 후(최대 30초 + 2초) 다른 워커가 인계받는다. 대기 건은 그 사이에도 다른 워커가 정상 발송한다                  |
| 일시 정지(이벤트 루프 블로킹, 긴 GC, `docker pause`, `SIGSTOP`) | 위와 동일하게 인계된다. 재개된 워커는 리스가 만료된 건을 발송하지 않으며, 지연된 결과 기록은 펜싱으로 차단된다                                                 |
| DB 네트워크 단절                                                | 신규 건을 점유하지 못한다. 이미 발송한 건의 결과는 기록되지 못한 채 남아 리스 만료 후 인계된다. 워커는 종료하지 않고 연결이 복구되면 작업을 재개한다(ADR-0039) |

DB 연결 세션 자체에 묶인 상태가 없으므로 PgBouncer 같은 커넥션 풀러를 경유할 수 있고, 다른 워커의 DB 세션을 강제 종료하는 권한도 필요 없다.

### 한계: 소켓 쓰기 직전 검증 통과 직후의 일시 정지

발송 직전 검증을 통과한 직후, 요청 바이트가 커널로 넘어가기 전의 짧은 순간에 워커가 멈출 수 있다. 리스 만료 시각은 DB에 기록된 값이므로 이를 검증하는 단계까지만 워커를 제어할 수 있으며, 이미 검증을 통과한 워커는 재개 시 재검증 없이 그대로 소켓에 기록한다.

- **중복 발생 조건**: 인계받은 워커는 인계 시점부터 5초 후에 발송 내역을 조회한다(ADR-0002). 그 전에 전송된 요청은 조회 결과에 잡혀 재발송되지 않는다. 사전 검증은 남은 리스가 10초보다 길 때만 통과하므로, 해당 지점에서 15초 이상 정지해야 중복이 발생한다.
- **실측 발생률**: 동일한 경합 구간이 존재하는 DB 세션 방식(아래 검토한 대안 참조)으로 측정한 결과, 초당 100건을 발송하는 워커를 임의 시점에 강제 정지시키고 장시간 방치하면 전체 실행의 1~3%에서 재개 직후 요청 1건이 전송되어 중복이 발생했다.
- **중복 발생 시 탐지**: 재개된 워커가 해당 요청의 응답을 받아 결과를 기록하려 하면 펜싱에 걸린다. 이어서 발송 내역을 조회해 기록이 2건이면 중복 메트릭과 `error` 로그로 남긴다. 탐지를 놓치는 경우는 재개 직후 요청을 보낸 뒤 응답을 받기 전에 프로세스가 즉시 종료되는 경우뿐이다.
- **완전 차단을 위한 조건(STONITH)**: 이 구간을 완전히 닫으려면 의심 워커의 프로세스나 네트워크를 외부에서 강제 차단하고 차단 완료를 확인한 뒤에만 인계하는 방식(STONITH)이 필요하다. 애플리케이션이 이를 직접 수행하려면 호스트 root에 준하는 권한(`docker.sock`)이 필요하므로 과도하다고 판단했다. 운영 환경에서는 오케스트레이션 플랫폼(Kubernetes의 Pod 삭제와 노드 펜싱, 클라우드 인스턴스 중지)이 담당하는 영역이다(ADR-0007).

## 검토한 대안

- **DB 세션(Advisory Lock) 기반 워커 생존 판정**: 워커마다 전용 연결로 자신의 ID에 대한 advisory lock(연결 종료 시 자동 해제되는 잠금)을 점유하고 2초마다 생존 신호를 보낸다. 15초 이상 무응답인 워커가 있으면 다른 워커가 해당 워커의 DB 세션을 `pg_terminate_backend`로 강제 종료하며, 잠금을 잃은 워커는 스스로 종료한다. 크래시 시 리스 만료를 기다리지 않고 즉시 인계하는 장점(최대 50건을 최대 30초 조기 복구)이 있으나 단점이 크다.
  - 일시 정지는 결국 시간(15초)으로 판정하므로 워커 단위 리스와 동일하며, 소켓 쓰기 직전 검증 직후에 멈추는 경합 구간도 동일하게 남는다.
  - TCP 연결이라는 애플리케이션 외부 동작에 의존한다. 다른 세션을 끊는 권한이 필요하고, PgBouncer 같은 커넥션 풀러를 거칠 수 없으며, 워커마다 전용 연결이 2개씩 더 필요하다.
  - 잠금을 잃은 워커가 즉시 종료해야 하므로, 경합 구간에서 중복을 일으킨 워커가 응답을 받아 펜싱에 걸리기 전에 프로세스가 종료되어 중복 탐지 메커니즘이 작동하지 않는다.
  - 업계에서도 일시 정지된 프로세스는 대부분 시간 기반 리스로 처리한다(ZooKeeper 세션 만료, etcd와 Kubernetes의 Lease, Chubby). 연결에 묶인 잠금은 크래시 감지에 흔히 쓰이지만(Ruby의 Que·GoodJob, 마이그레이션 잠금), 다른 워커의 연결을 강제 종료해 무효화하는 것은 ZooKeeper 서버가 제공하는 세션 만료를 수동으로 구현하는 셈이다.
- **워커 단위 리스(워커 행 + 만료 시각 + 생존 신호)**: 건마다 만료 시각을 기록하지 않아도 되지만 생존 신호 갱신과 워커 테이블 관리가 별도로 필요하다. claim 쿼리가 만료 시각을 한 번 기록하면 끝나는 건 단위 리스가 더 단순하다.
- **프로세스 종료가 확실할 때만 인계**: 경합 구간은 좁아지지만, 일시 정지된 워커가 점유한 건은 외부에서 해당 워커를 종료시킬 때까지 처리되지 않는다. Docker Compose에는 이를 자동으로 강제 종료할 주체가 없어, 중단된 워커의 건을 다른 워커가 이어서 발송해야 한다는 요구사항을 충족하지 못한다.
- **HTTP 호출 동안 트랜잭션을 열고 행 잠금 유지**: 동시 발송 수만큼 DB 연결을 점유하여 커넥션이 고갈되고, 롤백 시 시도 기록이 소실된다.
- **별도 감시 프로세스**: 감시 프로세스가 죽는 경우를 다시 고려해야 한다. 리스 방식은 살아 있는 워커 누구나 DB를 보고 대등하게 판단한다.
- **다수결 합의(etcd 등)**: 외부 의존 시스템이 늘어난다.
- **애플리케이션의 직접 외부 펜싱(`docker.sock` 마운트)**: 앱 컨테이너에 호스트 root에 해당하는 권한을 부여하게 된다.
