# 워커 점유는 건마다 기한(리스)을 두고, 늦게 깨어난 워커의 쓰기는 펜싱으로 막는다

워커가 가져간 Delivery를 다른 워커가 넘겨받으려면 원래 주인이 더는 보내지 않아야 한다. 꺼낸 건에 "이 시각까지 내 것"이라는 기한을 적고, 기한이 지나면 다른 워커가 넘겨받는다. 넘겨받은 쪽은 바로 다시 보내지 않고 외부 발송 내역을 조회한 뒤에만 보낸다(ADR-0002). 늦게 깨어난 원래 주인의 쓰기는 owner와 시도 번호로 막는다. 기한 판단은 DB 시계 하나로 한다.

AWS SQS의 visibility timeout과 같은 개념이다. 받아 간 메시지는 일정 시간 남에게 보이지 않고, 그 안에 처리를 끝내지 못하면 다시 보인다. 늦게 깨어난 보유자를 펜싱으로 막는 것은 분산 잠금에서 널리 쓰는 답이다(fencing token).

## 방식

- **워커 ID**: 프로세스가 뜰 때마다 새로 뽑는 무작위 양의 정수. Delivery와 알림 단위 작업의 owner 칸에 적어 펜싱에 쓴다. 재시작한 프로세스가 이전 생과 같은 ID를 쓰면, 이전 생이 남긴 건과 지금의 건을 쓰기 조건으로 구별할 수 없다.
- **발송 기한**: claim 쿼리(대기 건을 IN_FLIGHT로 바꾸는 UPDATE)가 `lease_until = 지금 + 30초`를 함께 적는다. 30초는 응답 한도(10초)와 결과 기록을 넉넉히 덮는 길이라, 정상이면 기한 안에 결과가 기록되어 넘겨받기가 일어나지 않는다. 기한은 연장하지 않는다. 발송 한 번은 응답 한도 안에 끝나기 때문이다.
- **발송 직전 확인**: 남은 기한이 응답 한도보다 길 때만 보낸다. 요청이 응답 한도까지 걸려도 기한 안에 끝나게 하기 위해서다. 남은 기한은 claim 쿼리를 보내기 직전에 잰 단조 시계로 계산한다. 그 시각은 DB가 기한을 적은 시각보다 이르므로, 워커가 보는 기한은 DB의 기한보다 늘 짧다. 확인은 요청 바이트를 소켓에 쓰기 바로 앞에서 한다. 꺼낸 건을 보내기까지는 소켓 배정과 TCP 연결이라는 비동기 틈이 있어서, 그보다 앞에서 확인하면 그 틈에서 멈췄다 깨어난 워커가 이미 넘겨받힌 건을 보낼 수 있다. 쓰기 직전이 마지막 기회라 한 번이면 된다. 확인에 걸린 건은 보내지 않고 반납한다(시도 횟수를 되돌리고 대기로). 외부 장애가 아니므로 서킷 브레이커(ADR-0014)에 세지 않는다.
- **넘겨받기**: 워커마다 2초마다 도는 정리 루프가 기한이 지난 IN_FLIGHT 건을 결과 미확정으로 바꾸고 owner를 비운다. 그 건은 ADR-0002의 조회 경로로 간다. 여러 워커가 동시에 시도해도 행 잠금으로 하나만 성공한다.
- **소유 기반 쓰기 펜싱**: Delivery 결과, 펼치기 커서처럼 owner가 있는 모든 쓰기는 owner(와 시도 번호)가 일치할 때만 반영한다. 넘겨받기가 owner를 비우므로, 늦게 깨어난 워커의 쓰기는 0건 갱신으로 거부된다. Delivery 결과가 거부되면 clientRef 조회로 실제 중복 여부를 확인해 로그와 메트릭에 남긴다.
- **알림 단위 작업(펼치기, 취소 정리)**: 같은 방식이다. 담당(owner)과 기한을 적고, 기한이 지나면 다른 워커가 맡는다. 펼치기는 페이지를 여러 번 받는 긴 작업이라, 사용자 API를 부르기 전마다 기한을 연장한다. 연장은 "아직 SENDING이고 내가 담당일 때만" 반영되므로, 연장이 0건이면 취소됐거나 넘겨받힌 것으로 보고 멈춘다. 페이지 저장은 담당과 저장된 커서가 맞을 때만 반영한다(ADR-0006).
- **멈춘 워커가 쥔 행 잠금**: 트랜잭션 도중 멈춘 워커는 알림 행 잠금을 쥔 채 남아, 같은 알림의 결과 기록을 모두 막는다. 워커의 DB 연결에 `idle_in_transaction_session_timeout`(5초)을 걸어, 트랜잭션 도중 클라이언트가 응답하지 않으면 Postgres가 그 세션을 끝내고 잠금을 풀게 한다. 정상 트랜잭션은 몇 ms 안에 끝나므로 걸리지 않는다.
- **시간 값의 관계**: 응답 한도 10초 < 발송 기한 30초. 사용자 조회 한도 10초 < 작업 기한 30초. 기동 시 설정값을 검증해 어기면 시작하지 않는다.

## 결과

- 크래시하면 그 워커가 보내던 건(동시 발송 한도 50건 이내)은 기한이 지난 뒤(최대 30초) 넘겨받는다. 대기 중인 건은 다른 워커가 그동안에도 보낸다. 펼치기와 취소 정리도 기한이 지나면 다른 워커가 이어 간다.
- 멈춘 워커(이벤트 루프 막힘, 긴 GC, docker pause, SIGSTOP)의 건도 기한이 지나면 넘겨받는다. 깨어난 워커는 기한이 지난 건을 보내지 않고, 이미 보낸 건의 결과 기록은 펜싱에 걸린다. 프로세스는 종료하지 않고 계속 일한다. 기한이 지난 건은 이미 남의 것이고, 남의 것에 쓰려는 시도는 펜싱이 막기 때문이다.
- DB와 네트워크가 갈라진 워커는 새 건을 꺼내지 못한다. 보낸 건의 결과를 기록하지 못하면 재시도하다 종료하고(ADR-0007), 그 건은 기한이 지나 다른 워커가 넘겨받는다.
- 세션에 묶인 상태가 없어서 PgBouncer transaction pooling 같은 연결 중계를 거쳐도 된다. 다른 세션을 끊는 권한도 필요 없다.
- 남는 위험은 확인을 통과한 뒤 요청 바이트가 커널로 넘어가기 전, 같은 동기 실행 안의 아주 짧은 구간에서 멈춘 경우다. 기한은 기록이라서 그 기록을 읽는 워커만 막을 수 있다. 이미 확인을 통과한 워커는 깨어나면 다시 확인하지 않고 보낸다. 넘겨받은 워커가 넘겨받은 뒤 5초 지나서 조회하므로(ADR-0002) 그 안에 보낸 것은 조회에 잡혀 중복이 되지 않는다. 중복은 그 구간에서 "남은 기한 + 5초"보다 오래 멈춰야 생긴다. 확인은 남은 기한이 응답 한도(10초)보다 길 때만 통과하고, 보통은 꺼낸 직후라 30초 가까이 남아 있다. 이 틈은 실제로 나타난다. 세션 방식(아래)일 때 같은 틈을 재 보니, 초당 100건을 보내는 워커를 아무 때나 멈추고 넘겨받기와 결과 확인 대기보다 오래 멈춰 두면 실행의 1~3%에서 깨어난 직후 요청 하나가 나가 중복이 됐다.
- 이 틈에서 생긴 중복은 탐지한다. 깨어난 워커가 그 요청의 응답을 받아 결과를 기록하려 하면 펜싱에 걸리고, 조회해서 기록이 두 건이면 `alarm_duplicates_detected_total`과 error 로그로 남긴다. 놓치는 경우는 깨어나 요청을 보낸 직후 프로세스가 죽어 응답을 처리하지 못한 경우 하나다.
- 이 틈을 완전히 닫는 방법은 기록이 아니라 **고립**이다. 의심 워커의 프로세스나 네트워크를 밖에서 끊고, 끊긴 것이 확인된 뒤에만 넘겨받는 외부 펜싱(STONITH)이 더 나은 방식임을 안다. 그러나 이 틈에 걸릴 확률은 매우 낮고, 애플리케이션이 직접 고립을 수행하려면 호스트 root에 해당하는 권한(`docker.sock`)과 별도 장치가 필요해 과도한 구현이라고 판단했다. 실제 프로덕션에서는 플랫폼(쿠버네티스 파드 삭제·노드 펜싱, 클라우드 인스턴스 중지 API)이 맡아 해결하는 문제다(ADR-0007).

## 처음 결정과 바꾼 이유

처음에는 워커의 생존을 DB 세션으로 판정했다. 워커마다 전용 연결로 자기 ID의 advisory lock을 쥐고(살아 있는 워커 명단 = `pg_locks`), 2초마다 생존 신호를 보내고, 15초 넘게 조용한 워커가 있으면 다른 워커가 그 워커의 모든 DB 세션을 `pg_terminate_backend`로 끊었다. 잠금을 잃은 워커는 스스로 종료했다. 리스를 고르지 않은 이유는 "판단이 건마다 흩어진다"와 "기한이 지난 워커는 자신이 무효가 된 사실을 알 길이 없다"였다.

구현하고 명세 기준 심사를 세 번 받은 뒤 다시 따져 보니 그 이유가 약했다.

- 리스에서도 워커는 자기 기한을 안다. 자기가 적은 값이다. 보내기 전에 기한을 확인하는 것은 세션 방식의 발송 직전 확인(생존 신호가 최근에 확인됐는가)과 같은 일이다. 멈춰 있는 동안 모르는 것도, 확인 직후에 멈추는 틈도 두 방식이 같다.
- 세션 방식에만 있는 장점은 둘이었다. 크래시 때 기한을 기다리지 않고 바로 넘겨받는 것(동시 발송 한도 50건 이내를 최대 30초 빨리), 그리고 멈춘 워커의 행 잠금을 연결을 끊어 푸는 것이다. 앞의 것은 작고, 뒤의 것은 Postgres 설정(`idle_in_transaction_session_timeout`)이 대신한다.
- 대가는 컸다. TCP 연결이라는 우리 소프트웨어 바깥의 동작을 근거로 삼았고, 남의 세션을 끊는 권한이 필요했고, PgBouncer 같은 중계를 거칠 수 없었고, 워커마다 잠금 연결과 무효 선언 전용 연결이 더 필요했다. 연결에 묶인 잠금으로 크래시를 감지하는 것 자체는 흔하다(Ruby의 Que와 GoodJob이 작업을 advisory lock으로 쥐고, Rails·Flyway가 마이그레이션 잠금에 쓴다). 그러나 멈춘 프로세스는 업계가 거의 다 시간 기한으로 다룬다(ZooKeeper 세션 만료, etcd와 Kubernetes의 Lease, Chubby). 남의 연결을 끊어 무효로 만드는 것은 ZooKeeper가 서버에서 해 주는 세션 만료를 손으로 만든 셈이었고, 설명하고 납득시키기 어려웠다.
- 세션 방식은 잠금을 잃은 워커가 즉시 종료해야 했다. 그래서 위의 틈에서 중복을 낸 워커가 응답을 받아 펜싱에 걸리기 전에 끝나 버려, 처음 약속한 "생기면 탐지한다"가 깨졌다. 리스에서는 깨어난 워커가 계속 돌기 때문에 탐지가 다시 성립한다.

알고 보니 세션 방식도 멈춤 판정은 시간(15초)으로 하는 워커 단위 리스였다. 연결이 따로 하던 일은 크래시를 빨리 알아채는 것뿐이었다.

## 검토한 후보

- **워커 생존을 DB 세션으로 판정 (advisory lock + 생존 신호 + 무효 선언)**: 위의 처음 결정이다.
- **워커 단위 리스 (워커 행 + 만료 시각 + 생존 신호)**: 건마다 기한을 적지 않아도 되지만, 생존 신호와 워커 명단이 다시 필요하다. 발송은 claim 쿼리가 기한을 한 번 적으면 끝나므로 건 단위가 더 단순하다.
- **확실할 때만 넘겨받기 (프로세스가 죽어야만 넘겨받음)**: 중복이 생기는 틈은 더 좁지만, 멈춘 워커의 건은 누군가 그 워커를 죽일 때까지 대기한다. 자동으로 죽이는 주체가 없는 docker compose에서는 "내려간 워커가 쥐고 있던 건도 다른 워커가 이어받는다"는 요구를 지키지 못한다.
- **HTTP 호출 동안 트랜잭션을 열고 행 잠금 유지**: 동시 발송 수만큼 DB 연결을 붙잡아 풀이 고갈되고, 롤백 시 시도 기록이 사라진다.
- **별도 감시 프로세스**: 감시자의 장애를 다시 고려해야 한다. 기한 판단은 살아 있는 워커 누구나 DB를 보고 한다.
- **다수결 합의(etcd 등)**: DB 클러스터가 쓰는 방식이지만 의존 대상이 늘어난다.
- **외부 펜싱을 애플리케이션이 직접 수행(`docker.sock` 마운트)**: 애플리케이션 컨테이너에 호스트 root에 해당하는 권한을 주게 된다.
