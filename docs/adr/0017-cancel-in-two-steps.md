# ADR-0017. 발송 중 알림의 2단계 취소(CANCELING 전이 후 비동기 정리)

## 배경

발송 중인 대량 알림에는 대기(`PENDING`) 상태의 Delivery가 최대 10만 건 존재한다. 취소 시 해당 건들을 모두 `CANCELED`로 변경해야 하며 그사이 신규 발송이 진행되어서는 안 된다. 10만 건을 일괄 갱신하는 데는 약 1초가 소요된다. 취소 API가 이를 동기 처리하면 응답이 지연될 뿐만 아니라, 갱신이 아직 도달하지 않은 행을 워커가 점유(claim)하여 발송할 수 있다.

## 결정

취소 처리를 두 단계로 분리한다.

1. **API 서버**: 알림 상태를 `SENDING`에서 `CANCELING`으로 전이시키고 취소 사유(`REQUESTED`)를 기록한 뒤 즉시 응답한다(ADR-0016의 조건부 `UPDATE`, 수 ms 내 완료). 워커의 점유(claim) 쿼리는 `status = 'SENDING'`인 알림의 Delivery만 조회하므로, 이 트랜잭션이 커밋된 이후 시작되는 점유(claim) 쿼리는 해당 알림의 Delivery를 선택하지 않는다.
2. **워커**: 해당 알림의 대기 건(재시도 대기 중인 건 포함)을 일괄 `CANCELED`로 변경한다. 워커는 작업 폴링 시 대기 건 정리가 완료되지 않은 `CANCELING` 알림도 점유(claim)하며, 수신자 확장(Expansion)과 동일한 리스(lease) 및 만료 시각(`lease_until`) 메커니즘(ADR-0004)으로 소유권을 관리한다. 대기 건 정리가 끝나면 완료 판정(ADR-0018)을 수행하여 처리 중이던 건이 없을 경우 즉시 `CANCELED`로 최종 전이한다.

## 근거

- **단일 트랜잭션 처리 시의 추가 발송 방지**: 두 단계를 단일 트랜잭션으로 묶으면 10만 건을 갱신하는 약 1초 동안 아직 잠기지 않은 행을 워커가 점유(claim)하여 최대 50건가량이 추가 발송될 수 있다. 1단계를 먼저 커밋하면 정리 작업 동안 신규 점유가 즉시 차단된다.
- **중단 복구 보장**: 2단계 정리를 워커가 리스 기반으로 수행하므로 1단계 커밋 직후 API 프로세스가 종료되더라도 워커가 정리를 이어서 완료한다. 누락된 정리를 복구하기 위한 별도 크론이나 보정 루프가 필요 없다.

## 상세

### 취소 시 Delivery 상태별 처리

| 취소 시점의 Delivery 상태                 | 처리 방식                                                                                                           |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 대기 중 (`PENDING`, 재시도 대기 포함)     | `CANCELED`로 일괄 전이                                                                                              |
| 점유 중인 건 (`IN_FLIGHT`, 발송 진행 중)  | 그대로 발송을 완료하고 결과(`SENT`, `FAILED`)를 정상 기록                                                           |
| 결과 미확정(`UNCONFIRMED`) 건 (조회 대기) | 발송 내역 조회(상태 확정, Reconciliation) 수행. 발송 기록이 있으면 `SENT`, 없으면 재발송하지 않고 `CANCELED`로 확정 |
| 수신자 확장(Expansion) 진행 중            | 다음 사용자 페이지 조회 전 리스 갱신 시점에 상태 변경을 감지하고 즉시 중단(ADR-0006)                                |

- **대기(`PENDING`) 복귀 경로의 알림 상태 확인**: 일시 오류 재시도(`500`, `503`), `429` 복귀, 발송 내역 조회 후 재발송, 워커 정상 종료 시 반납 등 Delivery를 `PENDING`으로 되돌리는 모든 경로는 알림 행을 잠근 상태에서 알림의 현재 상태를 확인한다. 알림이 `SENDING`이 아니면 `PENDING` 대신 `CANCELED`로 기록한다. 대기 건 일괄 정리가 끝난 뒤에 `PENDING` 행이 다시 생성되면 점유(claim) 쿼리(`SENDING` 알림만 대상)가 이를 영구히 선택하지 않아 알림이 `CANCELED`에 도달할 수 없기 때문이다. 알림 행을 잠그므로 1단계 상태 변경과 순서가 어긋나지 않는다.
- **기발송 건의 상태 보존**: 이미 전송된 건의 결과 상태는 변경하지 않는다. 결과가 변동될 수 있는 건(`IN_FLIGHT`, `UNCONFIRMED`)이 모두 종결된 후 알림이 `CANCELED`로 전이되며, 그 시점부터 상태별 건수가 고정된다.

### 보장 범위 및 한계: 취소 커밋 직후 소수 건의 추가 발송 가능성

취소가 커밋된 이후 시작된 점유(claim) 쿼리는 해당 알림의 Delivery를 점유하지 않는다. 단, 커밋 시점에 이미 점유 쿼리가 실행 중이었거나 발송 중이던 건은 취소 응답 직후 외부로 전송될 수 있다.

- **발생 원인**: 워커의 한 폴링 주기(사이클)는 토큰 획득 → 점유(claim) 쿼리 → 점유한 건별 HTTP `POST` 순서로 진행된다. 점유 쿼리는 문장 시작 시점의 스냅숏으로 알림 상태를 읽으며 알림 행에 잠금을 걸지 않는다. 따라서 점유 쿼리가 실행되는 수 ms 사이에 취소 트랜잭션이 커밋되면 해당 쿼리는 알림을 `SENDING`으로 인식하여 Delivery를 `IN_FLIGHT`로 전환하고, 이어서 취소 응답 직후 외부 `POST`가 1회 전송될 수 있다. 다음 폴링 주기의 점유 쿼리부터는 `CANCELING` 상태가 반영된다.
- **발생 규모 및 빈도**: 취소 커밋 순간 점유 쿼리를 실행 중이던 워커가 그 주기에서 선택한 건수만큼 발생한다. 평시에는 토큰이 1개씩 보충되므로 1건이며, 토큰이 누적된 직후(발송 시작 직후 또는 정지 해제 직후)에는 최대 10건이다. 점유 쿼리는 전체 워커 합산 초당 약 50회 실행되고 회당 수 ms가 소요되므로 발송 중 취소 10회당 약 1회 빈도로 발생한다(시험에서도 10회 중 1회, 응답 1ms 후 외부 발송 기록이 발생함).
- **데이터 정합성 보장**: 이렇게 전송된 건도 결과 기록이 완료된 후에야 알림이 최종 `CANCELED`로 전이된다. 따라서 `CANCELED` 전이 이후의 집계 건수는 변하지 않으며 실제 수신자 목록이 정확히 보존된다.
- **알림 행 잠금을 생략한 이유**: 점유 쿼리에서 알림 행에 공유 잠금(`FOR SHARE`)을 걸면 취소 커밋 이후 `IN_FLIGHT` 전환을 차단할 수 있다. 그러나 완료 판정을 수반하는 결과 기록 트랜잭션이 동일 알림 행에 배타 잠금(`FOR UPDATE`)을 획득하므로(ADR-0018), 가장 빈번하게 접근하는 행에서 점유 쿼리와 결과 기록이 직렬화된다(순차 대기한다). 또한 잠금을 걸더라도 이미 `IN_FLIGHT`로 전환된 건의 HTTP `POST`는 취소 응답 이후 전송될 수 있어 응답 후 외부 발송 0건을 절대 보장하지도 못한다.
- **운영상 판단**: 대량 일반 알림의 오발송 취소 시 수 건이 추가 발송되는 문제는 정정 알림으로 대응할 수 있다. 실제 수신자(`SENT`)가 정확히 기록되므로 정정 발송 대상을 누락 없이 추출할 수 있다.

### 취소 사유 기록

알림 테이블에 취소 사유(`cancel_reason`) 컬럼을 기록한다.

| 값                 | 의미                                                                                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `REQUESTED`        | 클라이언트 취소 요청에 의한 취소                                                                                          |
| `EXPANSION_FAILED` | 수신자 조회가 영구 오류(비재시도성 오류)로 실패하여 시스템이 자동 중단함(ADR-0006). 마지막 오류 코드와 메시지도 함께 기록 |

취소 사유를 구분하지 않으면 시스템 오류로 인한 자동 중단을 운영자의 수동 취소와 식별할 수 없다. 두 경우 모두 동일한 2단계 취소 절차를 따른다.

### 실수신자 식별 및 정정 알림 연계

오발송된 알림을 취소한 뒤 이미 수신한 사용자에게만 정정 알림을 발송하기 위해 취소된 알림에서도 실수신자를 정확히 조회할 수 있어야 한다.

- 알림 상태는 `CANCELED`로 수렴하지만 개별 Delivery에는 `SENT`, `FAILED`, `CANCELED`가 각각 보존된다. 알림 단건 조회의 상태별 건수와 `GET /v1/alarms/{id}/deliveries?status=SENT`를 통해 실수신자 목록을 조회한다.
- 취소 시 결과 미확정(`UNCONFIRMED`) 건을 일괄 `CANCELED` 처리하지 않고 발송 내역 조회(상태 확정, Reconciliation)를 거쳐 확정하는 이유도 실수신자 누락을 방지하기 위함이다.
- 정정 알림 자동 생성 기능은 현재 범위 밖이다. 추후 도입 시 알림 생성 요청에 수신자 출처(`수신자 = 알림 X의 SENT 수신자`)를 추가하고, 수신자 확장(Expansion, ADR-0006)이 외부 사용자 API 대신 Delivery 테이블을 읽도록 확장할 수 있다.

## 검토한 대안

- **단일 트랜잭션에서 알림 상태 전이와 대기 건 일괄 갱신 수행**: 10만 건 갱신에 소요되는 약 1초 동안 워커의 신규 점유를 차단하지 못해 추가 발송이 발생한다.
- **점유 쿼리에서 알림 상태를 확인하지 않고 대기 건 상태 변경만으로 차단**: 대기 건 일괄 정리가 완료되기 전까지 신규 점유를 막지 못한다.
- **취소 시 결과 미확정(`UNCONFIRMED`) 건도 즉시 `CANCELED`로 처리**: 실제로 알림을 수신한 사용자가 `SENT` 목록에서 누락된다.

## 재검토 조건

단 1건의 추가 발송도 허용되지 않는 알림(법적 고지, 금융 거래 관련 알림 등)을 처리해야 하는 경우 점유(claim) 쿼리에 알림 행 공유 잠금(`FOR SHARE`)을 추가하고 결과 기록 트랜잭션과의 잠금 경합 비용을 감수한다.
