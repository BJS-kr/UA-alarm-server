# 업무 API에는 최소한의 인증(고정 API 키)을 두고, 헬스체크·메트릭은 관리 포트로 분리한다

명세에 인증 요구는 없지만, 이 API는 호출 한 번으로 사용자 10만 명에게 발송할 수 있다. 운영 환경을 가정할 때 이런 경로를 열어 둘 수 없다는 점을 보여 주는 것이 목적이며, 구현은 최소한으로 한다. Bearer 헤더와 고정 API 키가 운영에서 언제나 적절한 방식이라는 뜻은 아니다. 실제 운영에서는 앞단 게이트웨이나 사용자별 인증(OAuth 등)으로 대체한다.

## 방식

- 업무 API(`/v1/...`)는 `Authorization: Bearer <키>`를 요구한다. 키는 환경변수로 받고, compose에는 개발용 키를 둔다.
- 키 비교는 `crypto.timingSafeEqual`로 한다. 응답 시간 차이로 키를 알아내는 공격을 막는다.
- 실패하면 401과 `WWW-Authenticate: Bearer`, Problem Details 본문으로 응답한다.
- Nest Guard 하나와 Node 기본 기능으로 구현해 의존성이 늘지 않는다.

## 포트 분리

| 포트 | 경로 | 인증 |
| --- | --- | --- |
| api 공개 포트 | `/v1/...` | 필요 |
| api 공개 포트 | `/docs` (OpenAPI) | 불필요 |
| api·worker 관리 포트 (비공개) | `/health/*`, `/metrics` | 불필요 |

worker가 관리 포트를 두는 것(ADR-0026)과 같은 구조를 api에도 적용한다. 인증이 필요한 업무 경로와 내부망에서만 닿아야 하는 관리 경로를 포트로 갈라 규칙을 단순하게 한다.

## 한계

키가 하나라 "누가 이 알림을 시작하고 취소했는가"를 구별할 수 없다. 감사 기록은 사용자별 인증이 생길 때의 확장으로 둔다.

## 검토한 후보

- **인증 없이 앞단 게이트웨이가 막는다고 가정**: 실제로 흔한 구성이지만, 과제 환경에는 게이트웨이가 없어 누구나 전체 발송을 할 수 있는 상태가 된다.
- **JWT·OAuth**: 사용자별 권한까지 다룰 수 있지만, 토큰 발급 주체가 필요해 범위를 넘는다.
