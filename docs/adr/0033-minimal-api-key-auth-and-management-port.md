# ADR-0033. 업무 API 고정 키 인증 및 관리 포트 분리

## 배경

과제 명세에는 인증 요구사항이 없다. 그러나 이 API는 단일 호출로 사용자 10만 명에게 알림을 발송할 수 있다. 운영 환경을 가정할 때 이러한 경로를 비인증 상태로 열어 둘 수 없다.

## 결정

핵심 업무 경로를 비인증으로 노출하지 않는다는 원칙을 구현하되, 구현 복잡도는 최소한으로 유지한다. 고정 API 키가 운영 환경의 최종 인증 방식이라는 의미는 아니며, 실제 운영에서는 앞단 게이트웨이나 사용자별 인증(OAuth 등)으로 대체한다.

- 업무 API(`/v1/...`)는 `Authorization: Bearer <키>` 헤더를 요구한다. 키는 환경변수로 주입받으며, `docker-compose.yml`에는 개발용 기본 키를 둔다.
- 키 비교는 `crypto.timingSafeEqual`을 사용하여 응답 시간 차이로 키를 유추하는 타이밍 공격을 방지한다.
- 인증 실패 시 `401` 상태 코드와 `WWW-Authenticate: Bearer` 헤더, Problem Details 본문으로 응답한다.
- NestJS Guard 1개와 Node.js 기본 기능으로 구현하여 외부 의존성을 추가하지 않는다.
- Docker Compose는 `api` 공개 포트를 로컬 호스트(`127.0.0.1`)에만 바인딩하여, 동일 네트워크의 외부 호스트가 개발용 키로 호출하지 못하게 차단한다.

## 상세

### 포트 분리 구조

| 포트                                     | 경로                    | 인증   |
| ---------------------------------------- | ----------------------- | ------ |
| `api` 공개 포트                          | `/v1/...`               | 필요   |
| `api` 공개 포트                          | `/docs` (OpenAPI)       | 불필요 |
| `api` 및 `worker` 관리 포트(외부 미노출) | `/health/*`, `/metrics` | 불필요 |

인증이 필요한 업무 경로와 내부망에서만 접근해야 하는 관리 경로를 포트로 분리하여 접근 제어 규칙을 단순화한다. `worker`도 동일한 관리 포트 구조를 따른다(ADR-0026).

## 한계

단일 고정 키를 사용하므로 어떤 호출자가 알림을 시작하고 취소했는지 구별할 수 없다. 호출자별 감사 기록은 사용자별 인증 도입 시의 확장 과제로 둔다.

## 검토한 대안

- **인증 없이 앞단 게이트웨이가 차단한다고 가정**: 실무에서 흔한 구성이나, 과제 실행 환경에는 게이트웨이가 없어 누구나 전체 발송을 호출할 수 있는 상태가 된다.
- **JWT, OAuth 도입**: 사용자별 권한까지 제어할 수 있으나 토큰 발급 주체(IdP)가 필요하여 과제 범위를 벗어난다.
