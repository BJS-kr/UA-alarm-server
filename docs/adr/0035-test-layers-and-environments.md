# ADR-0035. 테스트는 단위, 통합, 끝단 세 층이고, DB는 늘 실제 PostgreSQL을 쓴다

## 배경

이 시스템이 맞는지는 대부분 SQL과 동시성에서 갈린다. 가짜 DB로는 그 부분을 확인할 수 없다. 반면 실제 mock은 오류를 무작위로 내서, 특정 장애 상황을 골라 재현할 수 없다.

## 결정

| 층 | 확인하는 것 | DB | 외부 API | 비고 |
| --- | --- | --- | --- | --- |
| 단위 | TS 순수 로직(재시도 간격, 응답 분류, 서킷 브레이커, 상태 전이표, 마스킹, 입력 검증, 설정 관계 검사) | 없음 | 없음 | 변이 테스팅 대상(ADR-0034) |
| 통합 | SQL과 동시성(꺼내기, 기한과 넘겨받기, 취소, 완료 판정, 토큰 버킷과 브레이커, 우선순위와 순서, 펼치기 재개) | 실제 PG | 테스트용 가짜 서버 | 고의 결함 목록(ADR-0034)을 이 층에서 돌린다 |
| 끝단 | 전체 시스템이 요구대로 도는가 | 실제 PG | 실제 mock 이미지 | 느리고 무작위성이 있어 별도 스크립트로 실행한다 |

## 세부

- **DB는 실제 PostgreSQL이다.** 정확성의 핵심이 SQL이다. 메모리용 가짜 DB(pg-mem 등)는 `SKIP LOCKED`와 트랜잭션 유휴 한도를 지원하지 않는다. 운영과 같은 postgres 이미지를 쓴다.
- **통합 테스트의 외부 API는 테스트 안에 띄우는 가짜 HTTP 서버다.** mock과 같은 계약(사용자 조회, 발송, 발송 내역 조회)을 따르며, "이 수신자는 20초 뒤 202", "다음 3건은 503" 같은 동작을 미리 정할 수 있다. 받은 요청을 모두 기록해서, "수신자마다 정확히 한 번"을 직접 확인한다.
- **여러 워커와 장애**: 여러 워커는 한 테스트 프로세스 안에서, DB 연결과 워커 ID를 따로 가진 인스턴스로 띄운다. 크래시와 멈춤은 프로세스 단위라야 실제와 같다. 그래서 컴파일된 워커를 자식 프로세스로 띄워 SIGKILL이나 SIGSTOP을 보낸다. 기한이 지난 뒤의 넘겨받기와, 깨어난 뒤의 펜싱을 확인한다.
- **끝단 테스트** (`scripts/e2e.sh`, `scripts/e2e-faults.sh`): 실제 mock 이미지를 사용자 2000명으로 띄운다.
  - 워커 3대로 대량 알림과 긴급 알림을 함께 보내면서, 도중에 워커 하나는 정상 종료하고 하나는 `docker kill`한다. 끝나면 mock의 집계로 수신자마다 정확히 한 번 기록됐는지(중복 0, 누락 0), 429가 이어지지 않았는지, 긴급 알림이 대량 뒤에 줄 서지 않았는지 확인한다. 끝으로 발송 중 취소 뒤 외부 기록이 늘지 않는지 본다.
  - 장애 시나리오: mock 멈춤, 워커 하나 멈춤, PostgreSQL 재시작. 셋 다 끝난 뒤 누락 0, 중복 0을 확인한다.
- **실행은 Docker로 한다.** `docker compose --profile test run --rm test` 하나로 단위와 통합 테스트를 돌린다. 평가자의 PC에 Node가 없어도 된다. 테스트 PG는 compose의 postgres 서비스를 쓰므로, Testcontainers 같은 의존성이 필요 없다.
- 테스트 러너는 NestJS 기본인 Jest다.

## 검토한 후보

- **메모리용 가짜 DB**: 핵심 SQL 기능을 지원하지 않는다.
- **통합 테스트에도 실제 mock 사용**: 무작위성 때문에 특정 장애 상황을 재현할 수 없다.
- **Testcontainers**: 코드에서 컨테이너를 띄울 수 있어 편하지만, compose로 같은 일을 할 수 있어 의존성을 늘리지 않는다.
