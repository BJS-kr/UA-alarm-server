# ADR-0035. 단위·통합·E2E 3계층 테스트 구성 및 실 PostgreSQL 사용

## 배경

본 시스템의 정확성은 대부분 SQL과 동시성 제어에서 결정되므로 가짜(in-memory) DB로는 핵심 동작을 검증할 수 없다. 반면 실제 mock 서버는 오류를 무작위로 발생시키므로 특정 장애 상황을 지정하여 재현할 수 없다.

## 결정

테스트는 단위, 통합, E2E 3계층으로 구성하며, DB는 항상 실제 PostgreSQL을 사용한다.

| 계층 | 검증 대상                                                                                                                               | DB      | 외부 API           | 비고                                                  |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------- | ------- | ------------------ | ----------------------------------------------------- |
| 단위 | TypeScript 순수 로직(재시도 간격, 응답 분류, 서킷 브레이커, 상태 전이표, 마스킹(masking), 입력 검증, 설정 관계 검증)                    | 없음    | 없음               | 변이 테스팅 대상(ADR-0034)                            |
| 통합 | SQL 및 동시성(점유(claim), 리스 및 인계(Takeover), 취소, 완료 판정, 토큰 버킷과 브레이커, 우선순위와 순서, 수신자 확장(Expansion) 재개) | 실제 PG | 테스트용 가짜 서버 | 고의 결함 목록(ADR-0034) 검증 계층                    |
| E2E  | 전체 시스템의 요구사항 충족 여부                                                                                                        | 실제 PG | 실제 mock 이미지   | 실행 시간이 길고 무작위성이 있어 별도 스크립트로 실행 |

## 상세

- **DB는 실제 PostgreSQL을 사용한다.** 시스템 정확성의 핵심이 SQL에 있다. 인메모리 DB(`pg-mem` 등)는 `SKIP LOCKED`와 트랜잭션 유휴 한도를 지원하지 않으므로 운영과 동일한 `postgres` 이미지를 사용한다.
- **통합 테스트의 외부 API는 테스트 프로세스 내부에 띄우는 가짜 HTTP 서버다.** mock 서버와 동일한 계약(사용자 조회, 발송, 발송 내역 조회)을 따르며, 특정 수신자에 대한 지연 응답(예: 20초 뒤 `202`)이나 연속 오류(예: 다음 3건 `503`)를 사전에 지정할 수 있다. 수신한 요청을 모두 기록하여 수신자별 정확히 1회 발송 여부를 직접 검증한다.
- **다중 워커 및 프로세스 장애 테스트**: 복수 워커 경합은 단일 테스트 프로세스 안에서 별도 DB 연결과 워커 ID를 가진 인스턴스들을 생성해 검증한다. 프로세스 강제 종료와 멈춤은 OS 프로세스 단위여야 실제와 동일하므로, 컴파일된 워커를 자식 프로세스로 기동하여 `SIGKILL`이나 `SIGSTOP`을 전송한다. 리스 만료 후의 인계(Takeover)와 프로세스 재개 후의 펜싱(fencing)을 검증한다.
- **E2E 테스트(`scripts/e2e.sh`, `scripts/e2e-faults.sh`)**: 실제 mock 이미지를 사용자 2000명 규모로 기동한다.
  - 워커 3대로 대량 알림과 긴급 알림을 동시에 발송하면서, 도중에 워커 1대는 정상 종료하고 1대는 `docker kill`로 강제 종료한다. 완료 후 mock 서버의 집계 API를 통해 수신자별 정확히 1회 발송(중복 0, 누락 0), `429` 미지속, 긴급 알림이 대량 알림 뒤에 대기하지 않고 우선 처리되었는지를 확인한다. 마지막으로 발송 중 취소 요청 후 외부 발송 기록이 증가하지 않는지 검증한다.
  - 장애 시나리오: mock 서버 일시 정지, 워커 1대 일시 정지, PostgreSQL 재시작 3가지 시나리오를 실행하고 종료 후 누락 0건, 중복 0건을 확인한다.
- **실행은 Docker로 일원화한다.** `docker compose --profile test run --rm test` 명령 하나로 단위 및 통합 테스트를 실행하므로 평가자의 PC에 Node.js가 설치되어 있지 않아도 된다. 테스트용 PG는 Compose의 `postgres` 서비스를 사용하므로 `Testcontainers` 같은 별도 의존성이 필요 없다.
- 테스트 러너는 NestJS 기본 도구인 Jest를 사용한다.

## 검토한 대안

- **인메모리 가짜 DB**: 핵심 SQL 기능을 지원하지 않는다.
- **통합 테스트에도 실제 mock 서버 사용**: 무작위성 때문에 특정 장애 상황을 결정론적으로 재현할 수 없다.
- **Testcontainers 도입**: 코드에서 컨테이너를 제어할 수 있으나 Compose만으로 동일한 실행이 가능하므로 의존성을 늘리지 않는다.
