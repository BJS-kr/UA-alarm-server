# 테스트

테스트 품질은 커버리지가 아니라 "ADR의 보장을 지키는가"로 판정한다(ADR-0034). 층은 단위·통합·끝단 셋이며 DB는 항상 실제 PostgreSQL을 쓴다(ADR-0035).

## 실행

호스트에는 Docker만 있으면 된다.

```bash
docker compose --profile test run --rm test                              # 단위 + 통합
docker compose --profile test run --rm test npm run test:mutation        # 변이 테스팅
docker compose --profile test run --rm test npm run test:sabotage        # 고의 결함 목록
bash scripts/e2e.sh                                                      # 끝단(실제 mock, 워커 3대, 1대 강제 종료)
```

## 층과 대상

| 층 | 대상 | 파일 |
| --- | --- | --- |
| 단위 | 발송·조회 결과 분류, 재시도·브레이커, 전이표, 커서, 설정 관계 검증, 마스킹, 추적 ID, HTTP 클라이언트 분류, 관리 포트 | `test/unit` |
| 통합 | API, 꺼내기 순서와 동시성, 토큰 버킷, 완료 판정, 취소, 펜싱, 워커 전체 흐름(장애 주입), 우선순위, 처리량, 펼치기 재개, 정상 종료, 멈춘 워커의 무효 선언, SIGKILL 크래시 복구, SIGSTOP으로 멈췄다 깨어난 워커의 자기 종료(Linux에서만 실행) | `test/integration` |
| 끝단 | 실제 mock 이미지(사용자 2000명), 워커 3대 중 1대를 발송 도중 `docker kill` | `scripts/e2e.sh`, `test/e2e` |

통합 테스트는 테스트 파일마다 새 DB를 만들고, 외부 API 자리에는 계약은 같고 동작을 미리 정할 수 있는 가짜 서버(`test/integration/support/fake-external-api.ts`)를 둔다.

## 최근 결과

| 항목 | 결과 |
| --- | --- |
| 단위 + 통합 | 140개 통과 (단위 95, 통합 45). 타이밍에 따라 결과가 달라질 수 있는 워커 장애 테스트 파일(`failover.spec.ts`)은 40번 연속 실행해 모두 통과 |
| 변이 점수(Stryker) | 96.6% (기준선 90%). 테스트 컨테이너에서 실행 |
| 고의 결함 목록 | 19/19 검출 |
| 끝단 | 대량 2000건 + 긴급 4건, 워커 3대 중 1대 강제 종료: 중복 0, 누락 0, 429 0, 넘겨받기 13건 |
| 처리량 | 초당 49.1건 (상한 50, 429 0) |
| 긴급 우선 | 대량 알림(2000명)이 1000건 넘게 남은 동안 긴급 알림(수신자 3명) 5개를 차례로 발송(워커 2대, 실제 mock). 15건 중 11건이 발송 시작 요청 후 141ms 안에 SENT. 나머지 4건은 mock 일시 오류 뒤 재시도 2건(약 1.1초), mock 느린 응답 2건(3.5~3.7초) |

## 변이 테스팅으로 드러난 것

첫 점수는 73.8%였다. 살아남은 변이를 보고 두 갈래로 고쳤다.

- **비어 있던 테스트를 채웠다.** 설정 관계의 경계값(같은 값이면 거부되는가), 재시도·브레이커 관계 검증, 추적 미들웨어, 마스킹 규칙별 동작, HTTP 클라이언트의 메서드·경로, keepAlive 재사용, 소켓 상한, 타임아웃 시 요청 끊기, `close()`의 소켓 정리, 200이 아니거나 JSON이 아닌 응답.
- **결과를 바꾸지 않는 코드를 지웠다.** class-transformer 기본값과 같은 옵션, 바로 뒤 조건과 겹치는 커서 검사, 쓰이지 않는 상수, 연결 단계 오류 코드 목록(ADR-0037의 "안 보냄" 판정을 하나로 줄였다), 이름 목록에 묶여 있던 URL 비밀번호 마스킹(모든 문자열로 넓혔다).

남은 생존 변이는 결과가 같은 변이로 판정해 받아들였다.

| 위치 | 변이 | 판정 |
| --- | --- | --- |
| HTTP 클라이언트 | 메서드 `'GET'`을 빈 문자열로 | Node가 빈 메서드를 GET으로 보낸다 |
| HTTP 클라이언트 | `status >= 200` 조건 제거 | 최종 응답으로 1xx가 오지 않는다 |
| HTTP 클라이언트 | 내부 결과의 `kind: 'response'`를 빈 문자열로 | 호출하는 쪽은 `kind === 'error'`인지만 본다 |
| HTTP 클라이언트 | 중복 완료 가드, 타이머 해제 제거 | Promise는 한 번만 끝나고, 끝난 요청의 destroy는 아무 일도 하지 않는다 |
| HTTP 클라이언트 | 응답 스트림 `error` 분기 | 응답 도중 스트림 오류를 결정적으로 재현할 수 없다. 재현되지 않으면 타임아웃 경로(같은 `unknown`)로 끝난다 |
| HTTP 클라이언트·커서 | `catch`의 `return undefined` 제거 | 함수가 어차피 undefined를 돌려준다 |
| 마스킹 | 깊이 제한 `> 6`을 `>= 6`으로 | 제한의 목적(순환 참조 차단)은 같다 |

## 고의 결함 목록으로 드러난 것

`test/sabotage/sabotages.mjs`에 ADR별로 깨뜨릴 SQL·로직과 실패해야 할 테스트를 둔다. 처음 실행에서 S01(꺼내기 정렬에서 우선순위 제거)을 놓쳤다. 테스트가 10건을 한 번에 꺼낸 뒤 순서를 봤는데, `claim()`이 반환 전에 JS에서 다시 정렬해 SQL 정렬이 깨져도 가려졌다. 우선순위의 의미는 "토큰 수(LIMIT)만큼 꺼낼 때 무엇을 고르는가"이므로 한 건씩 꺼내 고른 순서를 보도록 고쳤다. S12(정지 중에도 토큰을 준다)도 같은 종류였다. 통이 비어 있으면 결함이 있어도 0개를 주므로, 통이 찬 뒤에 정지하도록 테스트를 고쳤다. S17~S19는 아래 실제 프로세스 테스트에서 나온 문제를 막기 위해 더했다.

## 실제 워커 프로세스 테스트로 드러난 것

멈춘 워커 테스트는 처음에 잠금만 쥔 가짜 세션을 썼다. 컴파일된 워커를 발송 도중 SIGSTOP으로 멈추고, 다른 워커가 무효로 선언해 넘겨받아 끝낸 뒤 SIGCONT로 깨우는 테스트를 더해 수십 번 반복하자 세 문제가 나왔다. 한 번 통과한 테스트도 반복해서 돌려야 드러나는 종류였다.

| 증상 | 원인 | 조치 | 고의 결함 |
| --- | --- | --- | --- |
| 한 수신자에게 외부 기록 두 건 (반복 중 한 번) | 발송 직전 확인이 HTTP 요청을 만들기 전에만 있어, 소켓 연결을 기다리던 요청이 깨어난 뒤 그대로 나갔다고 판단 | 확인을 소켓에 쓰기 직전으로 옮김(ADR-0004). 단위 테스트가 "연결된 뒤에 확인하는가"를 따로 본다 | 단위 테스트 |
| 깨어난 워커가 처리되지 않은 `'error'`로 죽음 | pg 풀은 쉬는 연결의 오류만 받아 준다. 트랜잭션 도중이던 연결의 오류는 받을 곳이 없었다 | 모든 연결에 오류 리스너 | S18 |
| 다른 워커의 발송이 통째로 멈춤 | 알림 행 잠금을 쥔 채 멈춘 워커 때문에 결과 기록이 연결 풀을 모두 붙잡아, 무효 선언이 연결을 얻지 못했다 | 무효 선언과 넘겨받기에 전용 연결(ADR-0004, 0013) | S19 |

테스트는 종료 코드만이 아니라 종료 사유("잠금을 잃었다" fatal 로그)도 본다. 종료 코드만 보면 위의 처리되지 않은 오류로 죽은 경우도 통과하고, 그러면 S17(잠금을 잃어도 종료하지 않음)을 놓친다. SIGSTOP은 Windows에 없어 이 테스트는 Linux(테스트 컨테이너)에서만 돈다.
