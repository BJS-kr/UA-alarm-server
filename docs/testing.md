# 테스트

테스트 품질은 커버리지가 아니라 "ADR의 보장을 지키는가"로 판정한다(ADR-0034). 층은 단위·통합·끝단 셋이며 DB는 항상 실제 PostgreSQL을 쓴다(ADR-0035).

## 실행

호스트에는 Docker만 있으면 된다.

```bash
docker compose --profile test run --rm test                              # 린트 + 포맷 확인 + 단위 + 통합
docker compose --profile test run --rm test npm run test:mutation        # 변이 테스팅
docker compose --profile test run --rm test npm run test:sabotage        # 고의 결함 목록
bash scripts/e2e.sh                                                      # 끝단: 실제 mock, 워커 3대, 1대 정상 종료 + 1대 강제 종료, 긴급 우선, 발송 중 취소
bash scripts/e2e-faults.sh                                               # 끝단 장애: mock 멈춤, 워커 멈춤, DB 재시작
```

## 층과 대상

| 층 | 대상 | 파일 |
| --- | --- | --- |
| 단위 | 발송·조회 결과 분류, 재시도·브레이커, 전이표, 커서, 설정 관계 검증, 마스킹, 추적 ID, HTTP 클라이언트 분류와 쓰기 직전 확인, 관리 포트, 발송 시작·취소의 응답 판정, 405·415 판정 | `test/unit` |
| 통합 | API, 꺼내기 순서와 동시성, 토큰 버킷, 완료 판정, 취소, 펜싱, 워커 전체 흐름(장애 주입), 우선순위, 처리량, 펼치기 재개, 정상 종료, 결과 확인 대기, 서킷 브레이커, 워커 장애(아래 표) | `test/integration` |
| 끝단 | 실제 mock 이미지(사용자 2000명, 평가용 집계 켬). 정상 종료·강제 종료·긴급 우선·발송 중 취소·장애 시나리오 | `scripts/e2e*.sh`, `test/e2e` |

통합 테스트는 테스트 파일마다 새 DB를 만들고, 외부 API 자리에는 계약은 같고 동작을 미리 정할 수 있는 가짜 서버(`test/integration/support/fake-external-api.ts`)를 둔다. 끝단 테스트는 우리 DB만 보지 않고 mock의 평가용 집계(`/_admin/stats`)로 누락·중복을 다시 센다.

## 장애 대비 장치는 "있으면 막고, 빼면 깨진다"를 둘 다 확인한다

설계한 장치가 실제로 값을 하는지 보려면, 장치가 있을 때 그 장애를 막는 테스트와, 장치를 뺐을 때 그 테스트가 실제로 실패하는 것을 함께 확인해야 한다. 뒤쪽은 고의 결함 목록(`test/sabotage/sabotages.mjs`)이 장치를 하나씩 빼고 지정한 테스트를 돌려 확인한다.

| 장치 | 막는 장애 | 있을 때 막는 테스트 | 뺐을 때 |
| --- | --- | --- | --- |
| 꺼내기의 행 잠금(`SKIP LOCKED`) | 워커 여럿이 같은 건을 집음 | 여러 워커가 동시에 꺼내도 같은 건을 두 번 집지 않는다 | S02 |
| 결과 기록 펜싱(owner, 시도 번호) | 넘겨받힌 뒤 늦게 온 결과가 덮어씀 | 넘겨받힌 뒤 늦게 도착한 기록은 반영되지 않는다 | S04 |
| 넘겨받은 건은 조회한 뒤에만 재발송 | 죽기 직전에 보낸 건의 중복 | 기한이 지난 건은 넘겨받고, 그중 이미 보낸 건은 다시 보내지 않는다 | S07, S15 |

| 펼치기 담당의 기한 | 남의 펼치기를 빼앗거나, 죽은 담당의 펼치기가 멈춤 | 기한이 남은 펼치기 작업은 다른 워커가 맡지 않는다 / 펼치기는 저장된 커서부터 이어 간다 | S43, S44 |

| 브레이커가 열린 동안 세지 않음 | 긴 장애에 일부가 재시도를 다 써서 누락 | 외부 장애가 브레이커 정지보다 훨씬 길게 이어져도 … / 장애 동안의 응답 없음은 결과 미확정으로 두되 시도 횟수를 되돌린다 | S45, S51 |

| 완료 판정의 알림 행 잠금 | 마지막 두 건이 동시에 끝나면 완료되지 않음 | 마지막 두 건을 두 워커가 동시에 기록해도 COMPLETED | S05 |

| 토큰 버킷 용량 상한 | 몰아서 보내 429 | 한 번에 통 크기 이상은 받지 못한다 | S11 |
| 토큰 버킷 정지 | 429·장애 중에도 계속 보냄 | 정지 중에는 토큰을 주지 않는다 | S12 |
| 429는 시도 횟수에 세지 않음 | 처리량 제한 때문에 실패 확정 | 429는 시도 횟수를 되돌린다 | S16 |
| 발송 시작의 조건부 전이 | 취소된 알림이 다시 시작됨 | 취소된 알림의 시작은 409 | S13 |
| 발송 시작은 전이 결과로 응답 | 실제로 시작한 요청이 409를 받음 | 이 요청이 발송을 시작했으면 직후 취소가 와도 202 | S27 |
| DB 오류를 cause까지 보고 503 | DB 장애가 500으로 보임 | DB 연결을 얻지 못하면 정해 둔 시간 안에 503으로 답한다 | S28 |
| 오류 로그의 글 마스킹 | DB 오류 메시지에 담긴 본문(인증번호)·전화번호가 로그로 나감 | 오류를 넘긴 로그는 message, stack, detail과 cause의 숫자를 가린다 / 구조화 필드 안의 오류도 가린다 | S31, S30 |
| 입력의 NUL 거절 | DB가 저장을 거절해 500 | NUL이 든 제목 / NUL이 든 수신자 / NUL이 든 수신자 커서는 400이다 | S32 |
| 글자 수를 코드 포인트로 | 검증은 통과한 이모지 제목이 DB에서 거절되어 500 | 코드 포인트로 100자를 넘는 제목 / 정확히 한도인 제목과 본문은 받는다 | S33 |
| body-parser 오류의 상태 유지 | 너무 큰 본문이 413이 아니라 500 | 본문이 너무 큰 요청은 413 Problem Details로 답한다 | S34 |
| 조회 재시도 간격을 늘림 | 외부 장애 동안 결과 미확정 건마다 1초 간격 조회가 몰림 | 조회가 연달아 실패하면 간격을 늘리고, 다시 결과 미확정이 되면 처음부터 센다 | S35, S36 |

ID가 비어 있는 번호(S08, S09, S17, S19, S20, S21, S23, S29)는 점유를 DB 세션 판정에서 기한 방식으로 바꾸며 지킬 장치가 없어져 뺀 항목이다(ADR-0004).

### 검증하지 않은 것

- worker 생존 확인의 기준(작업 루프가 30초 동안 돌지 않음)으로 실제 재시작이 일어나는지. 작업 루프를 끝없이 막는 장애를 결정적으로 만들기 어려워 단위 테스트(관리 포트가 503을 내는가)까지만 확인했다.
- DB와의 네트워크만 끊긴 워커. compose에서 DB만 골라 끊기 어렵다. 새 건을 꺼내지 못하고, 쥔 건은 기한이 지나 넘겨받히며, 작업 루프가 멈추면 생존 확인이 unhealthy로 표시하도록 했지만 그 경로를 재현한 테스트는 없다.
- 끝단 장애 시나리오는 중복과 누락만 보고, 브레이커가 잘못 열리지 않았는지는 보지 않는다. 워커 멈춤 뒤의 브레이커는 위 실측과 단위 테스트(S59)로, 알림 막바지의 브레이커는 통합 테스트(S60)로 확인했다.
- 페이지 커밋의 응답만 유실된 뒤 같은 워커가 펼치기를 다시 집는 경로. 커밋은 됐는데 응답만 잃는 상황을 결정적으로 만들기 어렵다.

## 변이 테스팅으로 드러난 것

첫 점수는 73.8%였다. 살아남은 변이를 보고 두 갈래로 고쳤다.

- **비어 있던 테스트를 채웠다.** 설정 관계의 경계값(같은 값이면 거부되는가), 재시도·브레이커 관계 검증, 추적 미들웨어, 마스킹 규칙별 동작, HTTP 클라이언트의 메서드·경로, keepAlive 재사용, 소켓 상한, 타임아웃 시 요청 끊기, `close()`의 소켓 정리, 200이 아니거나 JSON이 아닌 응답.
- **결과를 바꾸지 않는 코드를 지웠다.** class-transformer 기본값과 같은 옵션, 바로 뒤 조건과 겹치는 커서 검사, 쓰이지 않는 상수, 연결 단계 오류 코드 목록(ADR-0037의 "안 보냄" 판정을 하나로 줄였다), 이름 목록에 묶여 있던 URL 비밀번호 마스킹(모든 문자열로 넓혔다).

남은 생존 변이는 결과가 같은 변이로 판정해 받아들였다.

| 위치 | 변이 | 판정 |
| --- | --- | --- |
| HTTP 클라이언트 | 메서드 `'GET'`을 빈 문자열로 | Node가 빈 메서드를 GET으로 보낸다 |
| HTTP 클라이언트 | `status >= 200` 조건 제거 | 최종 응답으로 1xx가 오지 않는다 |
| HTTP 클라이언트 | 내부 결과의 `kind: 'response'`를 빈 문자열로 | 호출하는 쪽은 `kind === 'error'`인지만 본다 |
| HTTP 클라이언트 | 중복 완료 가드, 타이머 해제 제거 | Promise는 한 번만 끝나고, 끝난 요청의 destroy는 아무 일도 하지 않는다 |
| HTTP 클라이언트 | 응답 스트림 `error` 분기 | 응답 도중 스트림 오류를 결정적으로 재현할 수 없다. 재현되지 않으면 타임아웃 경로(같은 `unknown`)로 끝난다 |
| HTTP 클라이언트·커서 | `catch`의 `return undefined` 제거 | 함수가 어차피 undefined를 돌려준다 |
| 마스킹 | 깊이 제한 `> 6`을 `>= 6`으로 | 제한의 목적(순환 참조 차단)은 같다 |
| 사용자 조회 실패 분류 | `status !== undefined` 조건 제거 | `Set.has(undefined)`가 어차피 false다. 조건은 타입 검사를 위해 둔다 |
| 브레이커 판단 창 | 시작 시각 비교 `>`를 `>=`로 | 시작 시각이 똑같은 결과끼리의 순서만 바뀐다. 시작 시각은 소수점 아래까지 재는 단조 시계라 같은 값이 사실상 없다 |
| HTTP 클라이언트 | 쓰기 직전 확인의 오류 코드 상수와 메시지를 빈 문자열로 | 코드는 같은 상수끼리만 비교하고, 메시지는 결과(`withheld`)에 담기지 않는다 |

## 고의 결함 목록으로 드러난 것

- 처음 실행에서 S01(꺼내기 정렬에서 우선순위 제거)을 놓쳤다. 테스트가 10건을 한 번에 꺼낸 뒤 순서를 봤는데, `claim()`이 반환 전에 JS에서 다시 정렬해 SQL 정렬이 깨져도 가려졌다. 우선순위의 의미는 "토큰 수(LIMIT)만큼 꺼낼 때 무엇을 고르는가"이므로 한 건씩 꺼내 고른 순서를 보도록 고쳤다.
- S12(정지 중에도 토큰을 준다)도 같은 종류였다. 통이 비어 있으면 결함이 있어도 0개를 주므로, 통이 찬 뒤에 정지하도록 테스트를 고쳤다.
- S27(발송 시작 응답을 다시 읽은 상태로 정함)은 실제 동시 요청 테스트로는 20번 중 한 번 꼴로만 드러났다. 경합 순서를 정해서 만드는 단위 테스트를 더해 결정적으로 잡는다. 동시 요청 테스트는 실제 경합을 보는 용도로 남겼다.
- 실행기 자체의 버그도 나왔다. "테스트가 실행되지 않음"을 `0 total`로 판단했는데, 테스트가 20개인 파일의 `20 total`에도 걸렸다.

## 실제 워커 프로세스 테스트로 드러난 것

아래는 점유를 DB 세션으로 판정하던 때의 일이다. 멈춘 워커 테스트는 처음에 잠금만 쥔 가짜 세션을 썼다. 컴파일된 워커를 발송 도중 SIGSTOP으로 멈추고, 다른 워커가 무효로 선언해 넘겨받아 끝낸 뒤 SIGCONT로 깨우는 테스트를 더해 수십 번 반복하자 아래 문제가 차례로 나왔다. 한 번 통과한 테스트도 반복해서 돌려야 드러나는 종류였다.

| 증상 | 원인 | 조치 | 고의 결함 |
| --- | --- | --- | --- |
| 한 수신자에게 외부 기록 두 건 (반복 중 한 번) | 발송 직전 확인이 HTTP 요청을 만들기 전에만 있어, 소켓 연결을 기다리던 요청이 깨어난 뒤 그대로 나갔다고 판단 | 확인을 소켓에 쓰기 직전으로 옮김(ADR-0004) | S22 |
| 깨어난 워커가 처리되지 않은 `'error'`로 죽음 | pg 풀은 쉬는 연결의 오류만 받아 준다. 트랜잭션 도중이던 연결의 오류는 받을 곳이 없었다 | 모든 연결에 오류 리스너 | S18 |
| 다른 워커의 발송이 통째로 멈춤 | 알림 행 잠금을 쥔 채 멈춘 워커 때문에 결과 기록이 연결 풀을 모두 붙잡아, 무효 선언이 연결을 얻지 못했다 | 무효 선언과 넘겨받기에 전용 연결(ADR-0004, 0013) | S19 |
| 리팩토링 뒤 40번 반복 중 37번째에 다시 중복 한 건 | 생존 신호를 보낸 직후 멈추면 응답은 깨어난 뒤 처리된다. 그 처리 시각을 확인 시각으로 써서, 무효가 된 워커가 잠깐 발송할 수 있었다. 리팩토링 전부터 있던 문제다 | 확인 시각을 신호를 보낸 시각으로(ADR-0004) | S29 |
| 위를 고친 뒤에도 60번 중 한 번 중복 | 진단해 보니 깨어난 직후 1ms 안에 요청이 나갔다. 확인을 통과하고 소켓에 쓰는 같은 동기 실행 도중에 멈춘 경우로, 문서에 남긴 남은 틈이다(ADR-0004). 테스트가 넘겨받기와 결과 확인 대기보다 오래 멈춰 두어서 드러났다 | 테스트를 설계가 약속하는 범위로 맞췄다. 무효 선언 직후, 결과 확인 대기 안에 깨운다. 더 오래 멈추는 경우는 외부 펜싱 없이는 닫을 수 없는 틈으로 남긴다 | (남은 틈) |

세션 방식일 때 이 테스트는 종료 코드와 종료 사유를 함께 봤다. 기한 방식으로 바꾼 지금은 반대로, 깨어난 워커가 종료하지 않고(fatal 로그 없음) 늦은 결과가 펜싱에 걸린 로그를 남기는지 본다. SIGSTOP은 Windows에 없어 이 테스트는 Linux(테스트 컨테이너)에서만 돈다.

심사 중 직접 구현을 고치며 하나가 더 나왔다. Drizzle은 드라이버 오류를 감싸 `cause`에 두는데, DB 장애를 503으로 판단하는 코드가 겉 오류만 봐서 DB가 죽어도 500을 냈다. `cause`를 따라가 보도록 고쳤다(ADR-0039, S28).
