# 심사 기준

구현 에이전트가 1차 구현을 마친 뒤 띄우는 심사 에이전트용 문서다. 심사 에이전트는 매 회차 새 컨텍스트로 시작한다.

## 심사 에이전트가 받는 것

- 원본 명세 `.local/assignment.md`
- `docs/requirements.md`, `docs/adr/*`, `CONTEXT.md`, `docs/schema.md`, `docs/structure.md`
- 저장소의 코드 전체

구현 과정의 대화나 설명은 받지 않는다. 코드와 문서, 실행 결과만으로 판단한다.

## 심사 순서

### 1. 실행으로 확인한다

실행하지 않은 것은 통과로 보지 않는다. 명령과 출력을 증거로 남긴다.

- 빌드가 된다.
- `docker compose --profile test run --rm test`로 단위·통합 테스트가 통과한다.
- `docker compose up` 한 번으로 모든 서비스가 뜨고 헬스체크가 healthy가 된다.
- 끝단 스크립트에서 수신자마다 외부 기록이 정확히 한 번(중복 0, 누락 0)이고, 429가 지속되지 않는다. 워커 한 대를 도중에 죽이는 경우를 포함한다.
- 변이 테스팅 점수와 살아남은 변이 목록을 확인한다.
- 고의 결함 스크립트에서 모든 결함이 지정된 테스트를 실패시킨다.

### 2. 명세에서 출발해 따라간다

`docs/requirements.md`의 요구사항(R·O·S)마다 구현이 있는지, 연결된 ADR대로인지, 테스트가 연결되어 있는지 본다.

- 구현이 없거나 테스트가 연결되지 않은 요구사항
- 어떤 요구사항에도 연결되지 않는 구현(범위 초과)

### 3. ADR을 지키는지 본다

각 ADR의 결정대로 구현됐는지, 그리고 "검토한 후보"에서 기각한 방식이 쓰이지 않았는지 본다. 특히 다음이 끼어들지 않았는지 확인한다: 시간 기반 리스로 넘겨받기, Redis·큐 라이브러리, 엔티티를 통째로 저장하는 쓰기, LISTEN/NOTIFY, 외부 health로 장애 판단.

### 4. 정확성 핵심 점검 (SQL과 동시성)

| 점검 | ADR |
| --- | --- |
| 모든 상태 전이가 조건부 UPDATE 한 문장이다 | 0016, 0032 |
| 꺼내기는 토큰을 먼저 받고, `priority, start_seq, id` 순서로, `SKIP LOCKED`로, SENDING 알림의 건만 집는다 | 0009, 0011, 0012, 0017 |
| IN_FLIGHT에서 나가는 쓰기에 owner와 시도 번호 조건이 있다 | 0004 |
| 발송 직전 확인이 있고, 잠금을 잃으면 종료하며, 무효 선언은 그 워커의 모든 세션을 끊는다 | 0004 |
| 재발송은 조회가 성공해 "기록 없음"을 답했을 때만 한다 | 0002 |
| 완료 판정은 알림 행 잠금 + `NOT EXISTS`이고, Delivery를 최종 상태로 바꾸는 모든 경로가 같은 함수를 거친다 | 0018 |
| 취소는 두 단계이며, 결과 미확정 건은 조회 후 CANCELED가 된다 | 0017 |
| 펼치기는 페이지 삽입과 커서 저장이 한 트랜잭션이고, 알림 상태를 확인하고 진행한다 | 0006, 0017 |
| 토큰 버킷은 요청 시 계산하며 `clock_timestamp()`를 쓰고, 429와 서킷 브레이커는 `paused_until`로 전체를 멈춘다 | 0009, 0014 |
| 시간 설정값의 관계를 기동 시 검증한다 | 0030 |

### 5. 테스트 품질

ADR-0034의 기준으로 본다: 보장 하나를 지키는가, 그 보장을 깨면 실패하는가, 관찰 가능한 결과로 검증하는가, 결정적인가. 살아남은 변이가 정당한지, 고의 결함이 모두 검출되는지 판정한다.

### 6. 운영 항목

헬스체크(0026), 메트릭(0027), 로그 수준과 마스킹(0028), 설정 검증(0030), 정상 종료와 신호 전달(0007), 관리 포트와 인증(0033).

### 7. 용어·의존성·비공개

- 용어가 `CONTEXT.md`와 같다.
- 승인 목록 밖의 의존성이 없다(`CLAUDE.md`).
- 원본 명세의 문장이 커밋되는 파일에 옮겨져 있지 않다(ADR-0038).

### 8. README

S1~S4(`docs/requirements.md`)를 모두 담고 있다.

## 지적 형식

각 지적은 다음을 담는다.

- **심각도**: 차단(명세·ADR 위반, 중복·누락 가능성, 실행 실패) / 개선(품질) / 참고
- **근거**: 요구사항 ID 또는 ADR 번호
- **위치**: `파일:줄`
- **증거**: 재현 명령과 출력, 또는 코드 인용

추측은 "확인 필요"로 표시하고 차단으로 올리지 않는다.

**ADR 자체의 문제**(모순, 약점, 구현 불가)를 발견하면 구현을 고치라고 하지 않는다. "ADR 문제"로 따로 분류해 보고한다. 구현 에이전트는 이를 받으면 작업을 멈추고 사용자에게 보고한다.
