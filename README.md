# 대량 알림 발송 서버

관리자가 만든 알림을 외부 발송 API로 수신자마다 한 건씩 보내는 NestJS 서버입니다. `api`는 알림을 받고 상태를 바꾸며, 실제 발송은 별도 프로세스인 `worker`가 합니다. 발송 상태, 작업 대기열, 처리량 제한은 모두 PostgreSQL 하나에 둡니다.

이 서버가 지키는 것은 세 가지입니다.

- **같은 사람에게 두 번 보내지 않습니다.** 외부 API가 중복을 막아 주지 않아도, 응답이 오지 않아도 마찬가지입니다.
- **워커가 죽거나 멈춰도 빠지는 사람이 없습니다.** 그 워커가 쥐고 있던 건은 다른 워커가 이어서 보냅니다.
- **워커를 몇 대로 늘려도 외부 API의 처리량 제한을 함께 지킵니다.** 긴급 알림은 대량 발송 중에도 먼저 나갑니다.

결정마다 배경, 검토한 대안, 이유를 ADR 39개로 남겼습니다. [ADR 목차](docs/adr/README.md)에 읽는 순서와 용어 풀이가 있습니다.

## 실행

필요한 것은 Docker(Compose v2)뿐입니다.

```bash
docker compose up
```

postgres, mock(외부 발송 API), migrate(마이그레이션 후 종료), api, worker 2대가 순서대로 뜹니다. 처음 실행할 때 이미지를 빌드합니다.

| 항목 | 값 |
| --- | --- |
| API | http://localhost:3000 |
| 인증 | `Authorization: Bearer dev-api-key` (개발용 기본값. `API_KEY` 환경변수로 바꿉니다) |
| API 문서 (Swagger UI) | http://localhost:3000/docs |
| OpenAPI 3.0 문서 | http://localhost:3000/docs/openapi.json, 서버 없이 보려면 [docs/openapi.json](docs/openapi.json) |

워커 수를 바꾸거나, 메트릭 수집(Prometheus, http://localhost:9090)까지 함께 띄우려면:

```bash
docker compose up --scale worker=3
```

```bash
docker compose --profile monitoring up
```

헬스체크와 메트릭은 관리 포트(9100)에 있고, compose 네트워크 밖으로는 열지 않습니다. 설정 항목과 기본값은 [app-config.ts](src/shared/config/app-config.ts)에 있습니다.

## API

업무 API는 모두 `Authorization: Bearer <API 키>`가 필요합니다.

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| POST | `/v1/alarms` | 알림 생성. 생성만으로는 보내지 않습니다 |
| GET | `/v1/alarms` | 목록. 최신순, 커서 페이지네이션, `status`·`type` 필터 |
| GET | `/v1/alarms/{id}` | 단건. 상태별 발송 건수를 함께 줍니다 |
| POST | `/v1/alarms/{id}/send` | 발송 시작 |
| POST | `/v1/alarms/{id}/cancel` | 발송 취소 |
| GET | `/v1/alarms/{id}/deliveries` | 수신자별 결과. `status` 필터, 커서 페이지네이션 |

```
CREATED ──발송 시작──▶ SENDING ──모든 건 종료──▶ COMPLETED
   │                      │
   │ 취소                  │ 취소
   ▼                      ▼
CANCELED ◀──남은 건 정리── CANCELING
```

- 일부 수신자가 실패해도 알림은 COMPLETED이고, 결과는 건수로 봅니다.
- 발송 중 취소하면 먼저 CANCELING이 되어 새 발송이 바로 멈춥니다. 이미 나가던 요청의 결과까지 확정된 뒤 CANCELED가 되고, 그때부터 건수가 바뀌지 않습니다.
- 수신자별 상태는 PENDING(대기), IN_FLIGHT(보내는 중), UNCONFIRMED(보냈는지 모름, 조회로 확정), SENT, FAILED, CANCELED입니다.

| 상황 | 상태 코드 |
| --- | --- |
| 생성 | 201 + `Location` |
| 발송 시작·취소 뒤 아직 진행 중(SENDING, CANCELING) | 202 |
| 발송 시작·취소 뒤 이미 끝난 상태, 조회 | 200 |
| 입력 오류(필드 검증, 잘못된 ID나 커서) | 400 |
| 인증 실패 | 401 |
| 알림 없음, 없는 경로 | 404 |
| 경로는 있는데 메서드가 틀림 | 405 + `Allow` |
| 지금 상태로 할 수 없음(취소된 알림 시작, 완료된 알림 취소) | 409 |
| 본문이 너무 큼, JSON이 아님 | 413, 415 |
| DB에 연결할 수 없음 | 503 |

같은 요청을 다시 보내도 결과가 같습니다. 응답을 못 받은 클라이언트는 그냥 다시 보내면 됩니다. 오류는 모두 RFC 9457 Problem Details(`application/problem+json`)이고, 응답의 `traceId`가 서버 로그에도 같은 값으로 남습니다.

### 예시

아래 응답은 이 저장소의 compose 스택(사용자 2000명)에서 실제로 받은 값입니다. 길이를 줄이려고 일부 필드를 생략했습니다.

긴급 알림 생성. 대량 알림은 `"type": "BULK"`이고 `recipientIds`를 넣지 않습니다.

```bash
curl -i -X POST http://localhost:3000/v1/alarms \
  -H 'Authorization: Bearer dev-api-key' -H 'Content-Type: application/json' \
  -d '{"type":"URGENT","title":"서버 점검 안내","body":"오늘 23시부터 30분간 점검합니다","recipientIds":["u_000001","u_000002"]}'
```

```http
HTTP/1.1 201 Created
Location: /v1/alarms/01a14146-58cc-726c-84e1-d6dbcbe9ff46

{ "id": "01a14146-58cc-726c-84e1-d6dbcbe9ff46", "type": "URGENT", "status": "CREATED", ... }
```

발송 시작:

```bash
curl -i -X POST http://localhost:3000/v1/alarms/01a14146-58cc-726c-84e1-d6dbcbe9ff46/send \
  -H 'Authorization: Bearer dev-api-key'
```

```http
HTTP/1.1 202 Accepted

{ "id": "01a14146-58cc-726c-84e1-d6dbcbe9ff46", "status": "SENDING", "startedAt": "2026-10-15T20:34:51.734Z", ... }
```

대량 알림(2000명)을 보내는 도중 취소한 뒤의 단건 조회입니다. 실제로 받은 사람은 `/deliveries?status=SENT`로 뽑습니다.

```json
{
  "id": "01a14146-62b1-7db9-b08c-138594538f03",
  "type": "BULK",
  "status": "CANCELED",
  "counts": {
    "total": 2000,
    "pending": 0,
    "inFlight": 0,
    "unconfirmed": 0,
    "sent": 355,
    "failed": 3,
    "canceled": 1642
  }
}
```

완료된 알림을 취소하면:

```json
{
  "type": "/problems/invalid-state",
  "title": "Not allowed in the current state",
  "status": 409,
  "detail": "An alarm in COMPLETED cannot be canceled",
  "instance": "/v1/alarms/01a14146-58cc-726c-84e1-d6dbcbe9ff46/cancel",
  "currentStatus": "COMPLETED",
  "traceId": "8b586a77afa5b4f6c9864b9dd9e718e9"
}
```

## 설계

```
관리자 ──HTTP──▶ api ──▶ ┌──────────────── PostgreSQL ────────────────┐ ◀── worker × N ──▶ 외부 발송 API
                         │ alarms           알림과 상태                  │        │
                         │ alarm_recipients 긴급 알림의 지정 수신자       │        └──▶ 사용자 API
                         │ deliveries       수신자별 발송 건 (= 작업 큐)  │
                         │ rate_limiter     모든 워커가 함께 쓰는 토큰 버킷 │
                         └────────────────────────────────────────────┘
```

api와 worker는 서로를 부르지 않고 DB로만 이어집니다. 대량 알림 하나는 이렇게 흘러갑니다.

1. 발송 시작 요청이 알림을 CREATED에서 SENDING으로 바꿉니다. "지금 CREATED일 때만 바꾼다"는 조건부 UPDATE 한 문장이라, 동시에 여러 번 와도 한 번만 바뀝니다(ADR-0016).
2. 워커 하나가 그 알림의 수신자 펼치기를 맡습니다. 사용자 API를 1000명씩 읽고, 페이지마다 Delivery 삽입과 다음 커서 저장을 한 트랜잭션으로 커밋합니다. 커밋된 건은 바로 발송 대상이 됩니다(ADR-0006).
3. 모든 워커가 같은 루프를 돕니다. 토큰을 받고, 받은 개수만큼 Delivery를 꺼내(`FOR UPDATE SKIP LOCKED`) 보내고, 결과를 적습니다.
4. 결과를 적는 트랜잭션이 알림 행을 잠그고, 끝나지 않은 건이 더 없으면 그 자리에서 알림을 COMPLETED로 바꿉니다(ADR-0018).

### 중복과 누락을 막는 장치

외부 API는 같은 요청을 두 번 받으면 두 번 보냅니다. 그래서 핵심은 "보냈는지 모르는 건을 그냥 다시 보내지 않는 것"입니다.

1. **보냈는지 모르는 건은 외부 기록을 조회한 뒤에만 다시 보냅니다.** 타임아웃이나 보낸 뒤 끊긴 건은 결과 미확정(UNCONFIRMED)으로 두고, 5초 뒤 `GET /v1/messages?clientRef=`로 조회합니다. clientRef는 `{alarmId}:{recipientId}`로 고정이라, 조회 한 번으로 이전 시도가 모두 보입니다. 기록이 있으면 완료이고, "기록 없음"을 확인했을 때만 다시 보냅니다(ADR-0002).
2. **꺼낸 건에는 30초 기한을 적습니다.** 기한 안에 결과가 적히지 않으면 다른 워커가 넘겨받아, 1번의 조회 경로로 처리합니다. 워커가 죽든 멈추든 같은 길입니다(ADR-0004, 0007).
3. **늦게 깨어난 워커의 쓰기는 DB가 거부합니다.** 결과는 "담당이 아직 나이고 시도 번호도 같을 때만" 적습니다. 넘겨받기가 담당을 비우므로, 멈췄다 깨어난 워커의 쓰기는 0건 갱신이 됩니다(펜싱).

**남는 틈이 하나 있습니다.** 발송 직전 확인을 통과한 바로 그 순간 워커가 멈추고, 15초 넘게 있다가 깨어나면 같은 요청이 한 번 더 나갈 수 있습니다. 생기면 탐지해 `alarm_duplicates_detected_total`과 error 로그로 남깁니다. 완전히 막으려면 의심 워커를 밖에서 끊는 외부 펜싱이 필요한데, 호스트 root 권한이 필요해 이 범위에서는 두지 않았습니다(ADR-0004).

### 처리량 제한 공유

- 모든 워커가 PG의 토큰 버킷 행 하나를 함께 씁니다. 보내기 전에 토큰을 받아야 하고, 토큰은 초당 50개씩 찹니다. 충전 타이머 없이, 요청할 때 흐른 시간만큼 계산해 지급합니다(ADR-0009).
- 우리 버킷 용량은 10입니다. mock의 버킷(용량 50)보다 작게 두어, 네트워크 때문에 요청이 몰려 도착해도 mock 쪽에 여유가 남습니다.
- 429를 받으면 버킷 행에 정지 시각을 적어 모든 워커가 함께 멈춥니다. 워커는 서로가 몇 대인지 알 필요가 없습니다.

### 긴급 알림 우선

- 워커는 토큰을 먼저 받고, 받은 개수만큼 우선순위 순으로 꺼냅니다. 토큰이 생기는 순간 꺼낼 수 있는 긴급 건이 있으면 그것부터 나갑니다(ADR-0011).
- 긴급이 대량 때문에 기다리는 시간은, 이미 대량 건에 나간 토큰이 쓰이는 동안뿐입니다. 평소에는 다음 토큰까지(수십 ms)입니다.
- 대량 발송을 멈추지는 않습니다. 긴급 건이 응답을 기다리는 동안에는 토큰을 쓸 곳이 없으므로, 멈추면 처리량만 버립니다.
- 같은 우선순위 안에서는 먼저 시작한 알림부터 끝냅니다(ADR-0012).

### 워커 다중화와 종료

- 작업 분배는 `FOR UPDATE SKIP LOCKED`, 처리량은 공유 버킷, 장애 복구는 건마다 적은 기한이 맡습니다. 워커끼리 직접 통신하지 않습니다.
- 정상 종료(SIGTERM)는 새 건을 꺼내지 않고, 보낸 요청의 응답을 기다려 적고, 보내지 않은 건은 바로 돌려놓습니다. 그 밖의 모든 경우(크래시, OOM, `docker kill`, 멈춤)에는 기한이 지나 다른 워커가 넘겨받습니다(ADR-0007).
- 기본 워커 수는 2대입니다. 1대로도 처리량은 되지만, 그 1대가 죽으면 재시작될 때까지 발송이 멈춥니다(ADR-0010).

### 외부 장애

- 일시 오류(500, 503)는 건마다 간격을 두 배씩 늘려 재시도하고, 8번 시도한 뒤 실패로 확정합니다. 429는 시도 횟수에 세지 않습니다(ADR-0014).
- 워커가 최근에 보낸 20건 중 절반 이상이 실패하면, 서킷 브레이커가 모든 워커를 멈춥니다. 정지가 풀리면 모든 워커를 합쳐 시험 발송 한 건만 보내고, 성공해야 다시 평소처럼 보냅니다.
- 브레이커가 열린 동안의 실패는 시도 횟수에 세지 않습니다. 그래서 장애가 길어져도 재시도를 다 써서 빠지는 건이 없습니다.
- mock의 `GET /health`는 기동 순서에만 쓰고, 장애 판단에는 쓰지 않습니다. health는 프로세스가 살아 있다는 것만 보여 주므로, 발송 API만 실패하는 장애를 놓칩니다.

### 운영

- **오류 처리**: 예상하지 못한 오류는 꼭대기(프로세스 안전망, HTTP 예외 필터, 워커 루프)에서 받아 로그와 메트릭으로 남기고 계속 돕니다. api는 DB 대기에 한도를 두어, 요청이 응답 없이 멈추지 않고 503으로 끝납니다(ADR-0039).
- **헬스체크**: api의 생존 확인에는 DB를 넣지 않아, DB가 잠깐 죽어도 api가 연달아 재시작하지 않습니다. worker의 생존은 HTTP 응답이 아니라 작업 루프가 최근 30초 안에 돌았는지로 봅니다(ADR-0026).
- **로그**: 표준 출력 JSON이고 모든 줄에 traceId, alarmId 등이 붙습니다. 본문의 네 자리 이상 숫자, 전화번호, 비밀 키, 접속 주소의 비밀번호는 로거 한 곳에서 가립니다(ADR-0028).
- **설정**: 모두 환경변수이고, 값 사이의 관계(응답 한도 < 발송 기한 등)가 어긋나면 시작하지 않습니다(ADR-0030).
- **DB 권한**: 마이그레이션은 DDL 권한 계정으로 별도 서비스가 실행합니다. api와 worker는 읽기·쓰기 권한만 있는 계정을 씁니다(ADR-0025).
- **인증**: 호출 한 번으로 10만 명에게 보낼 수 있는 API를 열어 둘 수 없어서, 고정 API 키를 둡니다. 운영에서는 게이트웨이나 사용자별 인증으로 바꿀 자리입니다(ADR-0033).
- **메트릭**: api와 worker가 Prometheus 형식으로 냅니다. 중복 탐지, 429 정지, 브레이커 발동, 넘겨받기, 긴급 대기의 경보 기준은 ADR-0027에 있습니다.

## 기술 선택

| 항목 | 선택 | 이유 |
| --- | --- | --- |
| 언어·프레임워크 | TypeScript, NestJS 12, Node 24 LTS | api와 worker가 같은 코드베이스와 이미지를 씁니다 |
| 저장소·대기열·처리량 제한 | PostgreSQL 18 하나 | 아래 표 참고 |
| DB 접근 | Drizzle (`pg` 드라이버 위) | `SKIP LOCKED`, 조건부 UPDATE, `NOT EXISTS` 같은 핵심 쿼리를 빌더로 쓸 수 있고, 읽은 엔티티를 통째로 덮어쓰는 동작이 없어 동시성에서 lost update가 생기지 않습니다(ADR-0036) |
| 외부 HTTP | `node:http` | 소켓 수를 표준 라이브러리로 정하고, "요청 바이트를 다 넘겼는가"로 보냈는지를 직접 가립니다(ADR-0037) |
| 설정·검증·문서 | @nestjs/config, class-validator, @nestjs/swagger | NestJS 표준 조합입니다 |
| 메트릭 | prom-client | Node에 Prometheus 형식 기능이 없습니다 |
| 테스트 | Jest, Stryker | 단위·통합 테스트와 변이 테스팅 |

흔히 쓰는 도구를 몰라서 뺀 것이 아닙니다. 그 도구가 주는 기능을 하나씩 확인하고, 이미 가진 것으로 대신할 수 있을 때 뺐습니다(ADR-0005). 시스템이 하나 늘 때마다 두 시스템의 상태가 어긋날 수 있고, 그러면 중복·누락 방지가 동기화 문제로 바뀝니다.

| 흔한 선택 | 대신 쓴 것 | 이유 |
| --- | --- | --- |
| BullMQ + Redis 큐 | `deliveries` 행 + `FOR UPDATE SKIP LOCKED` | 큐와 DB에 상태를 나누면 시작·완료·취소마다 둘을 맞춰야 합니다. 중복을 막는 것은 큐가 아니라 "조회한 뒤에만 다시 보내기"와 펜싱이라, 그 장치를 DB 위에 두면 큐는 겹치는 정보가 됩니다(ADR-0003) |
| Redis 기반 rate limiter | PG 토큰 버킷 행 하나 | 갱신이 초당 100회 안쪽이고 처리량에 영향이 없습니다(ADR-0009) |
| 워커 명단, 감시 프로세스, etcd | 건마다 적은 기한 | 넘겨받기는 건의 기한만 보면 됩니다. 판단은 살아 있는 워커 누구나 DB 시계로 합니다(ADR-0004) |
| OpenTelemetry | W3C `traceparent` + AsyncLocalStorage | 지금 필요한 것은 요청 하나의 로그를 찾는 traceId입니다. 형식이 표준이라 나중에 OTel을 붙여도 이어집니다(ADR-0019) |
| pino | NestJS 기본 로거의 JSON 모드 | NestJS 11부터 기본으로 됩니다(ADR-0028) |

## 명세 해석

| 모호한 점 | 해석 |
| --- | --- |
| 외부 발송 API에 제목 필드가 없다 | 본문만 보냅니다. 제목은 알림을 구별하는 관리용 이름이고, 겹쳐도 됩니다 |
| "발송 완료"의 기준 | 외부 API가 202로 접수했거나, 발송 내역 조회로 기록이 확인된 것 |
| "중복 없음"의 기준 | 한 알림에서 수신자마다 외부 발송 기록이 정확히 한 건 |
| "전체 사용자"를 정하는 시점 | 발송을 시작한 뒤 사용자 API를 끝까지 읽은 결과 |
| 일부 수신자만 실패한 알림 | COMPLETED. 실패는 건수와 `/deliveries`로 봅니다 |
| 발송 중 취소 | 취소가 커밋된 뒤에 시작한 꺼내기는 그 알림의 건을 집지 않습니다. 그 순간 이미 꺼내진 건(워커당 평소 1건)은 나갈 수 있고, 결과를 그대로 적습니다. CANCELED가 된 뒤에는 건수가 바뀌지 않습니다(ADR-0017) |
| "긴급이 먼저" | 토큰이 생기는 순간 보낼 수 있는 긴급 건이 있으면 긴급부터 보냅니다. 긴급 알림이 끝날 때까지 대량을 멈추는 것은 아닙니다 |

요구사항별로 대응하는 ADR과 테스트는 [docs/requirements.md](docs/requirements.md)에 표로 정리했습니다.

## 바꾼 결정

- **워커 장애 판정을 DB 세션에서 건마다 적는 기한으로 바꿨습니다.** 처음에는 워커마다 DB 연결에 묶인 잠금을 쥐고, 조용해진 워커의 DB 세션을 다른 워커가 끊는 방식이었습니다. 크래시를 바로 알아채는 장점은 작았고, TCP 연결이라는 소프트웨어 바깥의 동작에 기대며 남의 세션을 끊는 권한까지 필요했습니다. 멈춘 프로세스를 시간 기한으로 다루는 것이 업계에서 흔한 방식이고(SQS의 visibility timeout, Kubernetes의 Lease), 설명하기도 쉽습니다(ADR-0004).
- **서킷 브레이커에 시험 발송을 두었습니다.** 외부를 300초 끊는 시험을 해 보니, 정지가 풀릴 때마다 모든 워커가 한꺼번에 다시 보내는 방식은 긴 장애를 버티지 못했습니다. 지금은 풀릴 때 한 건만 보내 보고, 장애 동안의 실패는 시도 횟수에 세지 않습니다(ADR-0014).
- **값은 실측으로 정했습니다.** mock은 응답이 늦은 요청도 접수 즉시 기록해서, 결과 확인 대기를 30초에서 5초로 줄였습니다(ADR-0002). 처리량을 재다가 결과 기록이 DB 연결을 붙잡아 토큰이 버려지는 것을 보고, 작업 루프 전용 연결 풀을 따로 두었습니다. 초당 46.9건이 49.1건이 됐습니다(ADR-0013).

## 작업 방식

설계는 AI 에이전트와 대화하며 하나씩 정했고, 정한 것은 모두 ADR로 남겼습니다. 구현은 에이전트가 했습니다. 구현을 마칠 때마다, 대화 맥락이 없는 새 심사 에이전트가 원본 과제 명세를 기준으로 코드와 문서를 검증했고, 그 지적을 반영하는 일을 되풀이했습니다(ADR-0038, [심사 기준](docs/review-criteria.md), [에이전트 지침](CLAUDE.md)).

## 구현하지 않은 것

- **데이터 보존**: 대량 알림 하나에 Delivery가 10만 행 생깁니다. 끝나지 않은 건만 담은 부분 인덱스 덕분에 쌓여도 발송은 느려지지 않아 그대로 둡니다. 쌓이면 Delivery를 월 단위 파티션으로 나눠 오래된 달을 통째로 떼어 내고, 지우기 전에 끝난 알림의 건수를 알림 행에 남깁니다(ADR-0031).
- **외부 펜싱**: 위의 "남는 틈"을 완전히 막으려면 의심 워커를 밖에서 끊어야 합니다. 운영에서는 플랫폼(쿠버네티스의 파드 삭제, 클라우드 인스턴스 중지)이 맡는 일입니다(ADR-0004).
- **정정 알림**: 취소된 알림에서도 실제로 받은 사람을 정확히 뽑을 수 있게 했습니다. 보내는 기능은 "알림 X의 SENT 수신자"라는 수신자 출처를 더하면 됩니다(ADR-0017).
- **템플릿**: 알림이 보낸 내용을 그대로 가지므로, 템플릿은 생성할 때 내용을 복사해 오는 층으로 위에 얹으면 됩니다(ADR-0023).
- **사용자별 인증과 감사 기록**: 지금은 키가 하나라 누가 시작하고 취소했는지 구별하지 않습니다(ADR-0033).
- **대시보드와 경보**: 메트릭과 경보 기준은 정했고, Prometheus 수집까지 붙였습니다. Grafana 대시보드와 경보 규칙은 넣지 않았습니다(ADR-0027).
