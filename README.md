# 대량 알림 발송 서버

관리자가 만든 알림을 외부 발송 API로 수신자마다 한 건씩 보내는 NestJS 서버입니다. `api`는 알림을 받고 상태를 바꾸며, 실제 발송은 별도 프로세스인 `worker`가 합니다. 발송 상태, 작업 큐, 처리량 제한은 모두 PostgreSQL 하나에 둡니다.

설계에서 가장 무겁게 본 것은 다음 세 가지입니다. 같은 사람에게 두 번 보내지 않습니다. 워커가 죽거나 멈춰도 받지 못하는 사람이 생기지 않습니다. 워커를 몇 대로 늘려도 외부 API의 처리량 제한을 함께 지킵니다.

결정 하나하나의 배경과 검토한 대안은 39개의 ADR로 남겼습니다. 이 README는 그 요약이고, ADR은 [목차](docs/adr/README.md)에서 읽는 순서와 한 줄 요약, 구현하면서 바꾼 결정을 함께 볼 수 있습니다.

## 실행

필요한 것은 Docker(Compose v2)뿐입니다. Node나 PostgreSQL을 따로 설치하지 않아도 됩니다.

```bash
docker compose up
```

postgres, mock(외부 발송 API), migrate(마이그레이션 후 종료), api, worker 2대가 순서대로 뜹니다. 처음 실행할 때 이미지를 빌드합니다.

| 항목 | 값 |
| --- | --- |
| API | http://localhost:3000 |
| 인증 | `Authorization: Bearer dev-api-key` (개발용 기본값. `API_KEY` 환경변수로 바꿉니다. 포트는 이 머신에서만 받습니다) |
| API 문서 (Swagger UI) | http://localhost:3000/docs |
| OpenAPI 3.0 문서 | http://localhost:3000/docs/openapi.json, 서버 없이 보려면 [docs/openapi.json](docs/openapi.json) |

워커 수를 바꿀 때:

```bash
docker compose up --scale worker=3
```

메트릭 수집(Prometheus)까지 함께 띄울 때. Prometheus 화면은 http://localhost:9090 입니다.

```bash
docker compose --profile monitoring up
```

헬스체크와 메트릭은 관리 포트(9100: `/health/live`, `/health/ready`, `/metrics`)에 있고, 이 포트는 compose 네트워크 안에만 열려 있습니다. compose 파일의 비밀번호와 API 키는 개발용 값입니다. 운영에서는 같은 이미지에 환경변수만 바꿔 배포합니다. 설정 항목과 기본값은 [app-config.ts](src/shared/config/app-config.ts)에 있습니다.

## 테스트

테스트도 모두 컨테이너에서 돕니다.

린트(ESLint), 포맷 확인(Prettier), 단위·통합 테스트 200개(단위 131, 통합 69)를 차례로 돌립니다. 실제 워커 프로세스를 `SIGSTOP`으로 멈추는 테스트는 Linux에서만 돌기 때문에, 테스트 컨테이너에서 실행합니다.

```bash
docker compose --profile test run --rm test
```

변이 테스팅(Stryker). 도메인 로직, 설정 검증, 마스킹, HTTP 응답 분류 코드를 일부러 바꿔 보고 테스트가 그 변화를 잡는지 확인합니다. 최근 점수는 97.2%이고, 90% 아래면 실패합니다.

```bash
docker compose --profile test run --rm test npm run test:mutation
```

고의 결함 목록. 장애 대비 장치(펜싱, 기한과 넘겨받기, 발송 직전 확인, 서킷 브레이커 등)와 꺼내기·완료 판정의 SQL을 하나씩 빼고, 그 장치가 막던 장애를 재현하는 테스트가 실제로 실패하는지 확인합니다. 장치가 있을 때 막는 테스트와 짝을 이뤄 "있으면 막고, 빼면 깨진다"를 둘 다 보여 줍니다. 최근 결과는 51개 중 51개 검출입니다. 장치별 표는 [docs/testing.md](docs/testing.md)에 있습니다.

```bash
docker compose --profile test run --rm test npm run test:sabotage
```

끝단 테스트. 실제 mock 이미지(사용자 2000명)에 워커 3대를 띄웁니다. 이 스크립트는 기존 compose 스택과 볼륨을 지우고 새로 띄웁니다.

- 대량·긴급 알림을 보내는 도중 워커 1대는 `docker stop`으로 정상 종료하고(종료 로그까지 확인), 다른 1대는 `docker kill`로 죽입니다.
- 끝난 뒤 우리 DB와 mock의 평가용 집계(`/_admin/stats`) 양쪽으로 확인합니다. 수신자마다 외부 기록이 정확히 한 건인지, 사용자 수만큼 Delivery가 만들어졌는지, 긴급 알림이 대량 알림 뒤에 줄 서지 않았는지 봅니다.
- 끝으로 남은 워커로 대량 알림을 보내다 취소하고, CANCELED 뒤에 외부 기록이 늘지 않는지 봅니다.
- `docker stop`이나 `docker kill`로 멈춘 컨테이너는 Docker가 사람이 멈춘 것으로 보아 `restart: unless-stopped`로도 다시 띄우지 않습니다. 그래서 이 테스트는 남은 워커가 넘겨받는 경로를 봅니다. 크래시나 OOM처럼 프로세스가 비정상 종료하면 다시 띄웁니다.

```bash
bash scripts/e2e.sh
```

장애 시나리오. 같은 구성에서 대량 알림을 보내는 도중 mock을 25초 멈추고, 워커 하나를 25초 멈추고, PostgreSQL을 재시작합니다. 설정은 기본값 그대로이고, 매번 mock 집계로 누락 0·중복 0을 확인합니다.

```bash
bash scripts/e2e-faults.sh
```

통합 테스트는 실제 PostgreSQL에 테스트 파일마다 새 DB를 만들고, 외부 API 자리에는 응답을 미리 정할 수 있는 가짜 서버를 둡니다. 결과의 자세한 내용과 변이 테스팅·고의 결함으로 드러난 것은 [docs/testing.md](docs/testing.md)에 있습니다.

## API

업무 API는 모두 `Authorization: Bearer <API 키>`가 필요합니다.

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| POST | `/v1/alarms` | 알림 생성. 생성만으로는 보내지 않습니다 |
| GET | `/v1/alarms` | 목록. 최신순, 커서 페이지네이션, `status`·`type` 필터 |
| GET | `/v1/alarms/{id}` | 단건. 상태별 발송 건수를 함께 줍니다 |
| POST | `/v1/alarms/{id}/send` | 발송 시작 |
| POST | `/v1/alarms/{id}/cancel` | 발송 취소 |
| GET | `/v1/alarms/{id}/deliveries` | 수신자별 결과. `status` 필터, 커서 페이지네이션 |

### 알림 상태

```
CREATED ──발송 시작──▶ SENDING ──모든 건 종료──▶ COMPLETED
   │                      │
   │ 취소                  │ 취소
   ▼                      ▼
CANCELED ◀──남은 건 정리── CANCELING
```

일부 수신자가 실패해도 알림은 COMPLETED이고, 결과는 건수로 봅니다. 발송 중 취소하면 먼저 CANCELING이 되어 새 발송이 즉시 멈추고, 이미 나가던 요청의 결과까지 확정된 뒤 CANCELED가 됩니다. 그때부터 건수가 바뀌지 않습니다.

수신자별 상태(Delivery)는 여섯 가지입니다.

| 상태 | 뜻 |
| --- | --- |
| PENDING | 보낼 차례를 기다림 (재시도 시각을 기다리는 건 포함) |
| IN_FLIGHT | 워커가 쥐고 외부로 보내는 중 |
| UNCONFIRMED | 보냈는지 모름. 외부 발송 내역을 조회해 확정합니다 |
| SENT | 외부 API가 접수함(202를 받았거나 발송 내역 조회로 확인) |
| FAILED | 수신 거부(400) 또는 재시도 횟수 소진 |
| CANCELED | 알림 취소로 보내지 않음 |

### 상태 코드

| 요청 | 결과 |
| --- | --- |
| 생성 | 201 + `Location` |
| 발송 시작 | CREATED·SENDING이면 202, COMPLETED면 200, 취소된 알림이면 409 |
| 취소 | CREATED면 200(바로 CANCELED), SENDING이면 202(CANCELING), CANCELING이면 202, CANCELED면 200, COMPLETED면 409 |
| 입력 오류(필드 검증, ID가 UUID가 아님, 틀린 커서) | 400 |
| 인증 실패 | 401 |
| 알림 없음 | 404 |
| 요청 본문이 너무 큼 | 413 |
| DB에 연결할 수 없음 | 503. 잠시 뒤 다시 시도하면 됩니다 |
| 예상하지 못한 서버 오류 | 500. 내부 정보 없이 `traceId`만 줍니다 |

202와 200은 응답 시점에 일이 아직 진행 중인지로만 가릅니다. 같은 요청을 다시 보내도 결과가 같으므로, 응답을 못 받은 클라이언트는 그냥 다시 보내면 됩니다.

에러는 모두 RFC 9457 Problem Details(`application/problem+json`)입니다. 클라이언트는 `type`으로 분기하고, 응답의 `traceId`는 서버 로그에도 같은 값으로 남습니다.

## 동작 방식

```
관리자 ──HTTP──▶ api ──▶ ┌──────────────── PostgreSQL ────────────────┐ ◀── worker × N ──▶ 외부 발송 API
                         │ alarms           알림과 상태                  │        │
                         │ alarm_recipients 긴급 알림의 지정 수신자       │        └──▶ 사용자 API
                         │ deliveries       수신자별 발송 건 (= 작업 큐)  │
                         │ rate_limiter     모든 워커가 함께 쓰는 토큰 버킷 │
                         └────────────────────────────────────────────┘
```

api와 worker는 서로를 호출하지 않고 DB로만 이어집니다. 대량 알림 하나는 이렇게 흘러갑니다.

1. 발송 시작 요청이 알림을 CREATED에서 SENDING으로 바꿉니다. 조건부 UPDATE 한 문장이라 동시에 여러 번 요청해도 한 번만 바뀝니다.
2. 워커 하나가 그 알림의 펼치기를 맡아 사용자 API를 1000명씩 읽고, 페이지마다 Delivery 삽입과 다음 커서 저장을 한 트랜잭션으로 커밋합니다. 커밋된 건은 펼치기가 끝나기 전에도 바로 발송 대상이 됩니다.
3. 모든 워커가 같은 루프를 돕니다. 토큰 버킷에서 토큰을 받고, 받은 개수만큼 Delivery를 꺼내(`FOR UPDATE SKIP LOCKED`) 보내고, 결과를 기록합니다.
4. 결과를 기록하는 트랜잭션은 알림 행을 잠그고, 끝나지 않은 건이 더는 없으면(`NOT EXISTS`) 그 자리에서 알림을 COMPLETED로 바꿉니다.

긴급 알림은 수신자가 최대 100명이라 펼치기가 없습니다. 발송 시작 요청의 트랜잭션에서 Delivery를 바로 만듭니다.

## 구현 코멘트

### API 설계

- 리소스는 알림 하나이고, 발송 시작과 취소는 상태 필드를 쓰는 `PATCH` 대신 동작 경로(`/send`, `/cancel`)로 두었습니다. 허용되지 않는 상태로 바꾸는 요청이 애초에 생기지 않고, 취소 결과가 CANCELING인지 CANCELED인지 응답으로 드러납니다(ADR-0015).
- `/deliveries`는 요구받지 않았지만 추가했습니다. 수신 거부만으로도 대량 알림마다 1% 가까이 실패하므로, 누가 왜 실패했는지 볼 수단이 운영에 필요합니다.
- 모든 상태 전이는 "지금 상태가 X일 때만 Y로" 바꾸는 조건부 UPDATE 한 문장입니다. 0건이 바뀌면 현재 상태를 다시 읽어 응답을 정합니다(ADR-0016).
- 알림 생성에는 멱등 키를 두지 않았습니다. 생성만으로는 아무것도 발송되지 않으므로 중복 생성의 피해는 보내지 않은 초안 하나이고, 키 저장·만료 규칙을 둘 만큼의 이득이 없습니다(ADR-0022).
- 목록은 offset 대신 keyset 커서입니다. 알림 ID가 UUIDv7이라 ID 순서가 생성 순서이므로 커서가 ID 하나로 됩니다(ADR-0024).
- 알림 종류(`type`)는 필수이고 기본값이 없습니다. 빠뜨리기만 해도 전체 발송이 되는 사고를 막기 위해서입니다(ADR-0021).

### 데이터 처리

- 테이블은 `alarms`, `alarm_recipients`, `deliveries`, `rate_limiter` 넷입니다([docs/schema.md](docs/schema.md)). 수신자별 상태를 담는 `deliveries` 행이 곧 작업 큐입니다. 남은 일이 DB 한 곳에만 있으므로 큐와 DB가 어긋날 일이 없습니다(ADR-0003).
- 상태별 건수는 저장하지 않고 조회할 때 `GROUP BY`로 셉니다. 저장하면 상태를 바꾸는 경로 하나만 갱신을 빠뜨려도 영원히 어긋납니다(ADR-0018).
- 꺼내기와 완료 판정은 끝나지 않은 건만 담은 부분 인덱스를 씁니다. 끝난 건이 쌓여도 발송 경로는 느려지지 않습니다.
- 알림은 발송 한 번의 단위이고, 보낸 시점의 제목과 본문을 그대로 가집니다. 같은 내용을 다시 보내려면 알림을 새로 만듭니다(ADR-0023).

### 중복과 누락을 막는 방법

외부 API는 같은 요청을 두 번 받으면 두 번 기록합니다. 그래서 "보냈는지 모르는 건을 다시 보내지 않는 것"이 핵심입니다.

- 한 건은 한 워커만 쥡니다. `FOR UPDATE SKIP LOCKED`로 꺼내면서 행에 워커 ID(owner)와 시도 번호를 씁니다.
- 결과 기록은 owner와 시도 번호가 그대로일 때만 반영됩니다. 다른 워커가 넘겨받은 뒤 늦게 도착한 결과는 0건 갱신으로 버려집니다(펜싱).
- 안 나간 것이 확실할 때만 바로 재시도합니다. 요청 바이트가 커널로 다 넘어가기 전에 실패했거나(연결 거부 등), 429·500·503을 받은 경우입니다. mock을 실측해 보니 이 응답들은 기록을 남기지 않았습니다([docs/mock-observations.md](docs/mock-observations.md)).
- 그 밖의 경우(타임아웃, 보낸 뒤 연결 끊김, 앞단 게이트웨이의 502·504, 기한이 지나 넘겨받은 건)는 UNCONFIRMED로 두고, 5초 뒤 `GET /v1/messages?clientRef=`로 조회합니다. clientRef는 `{alarmId}:{recipientId}`로 시도마다 같아서 조회 한 번으로 이전 시도가 모두 확인됩니다. 기록이 있으면 SENT로 확정하고, 조회가 성공했는데 기록이 없을 때만 다시 보냅니다. 조회 자체가 실패하면 보내지 않고 조회를 다시 하며, 간격은 발송 재시도처럼 1초에서 두 배씩 늘립니다(ADR-0002, 0014).
- 꺼낸 건에는 기한(30초)을 적습니다. AWS SQS의 visibility timeout과 같은 개념입니다. 기한 안에 결과가 기록되지 않으면 정리 루프(2초 주기)가 그 건을 결과 미확정으로 바꾸고 owner를 비운 뒤, 위의 조회 경로로 처리합니다. 기한은 응답 한도(10초)와 결과 기록을 넉넉히 덮으므로 정상이면 넘겨받기가 일어나지 않습니다. 기한 판단은 DB 시계 하나로 합니다(ADR-0004).
- 워커가 죽거나 멈추면(크래시, 이벤트 루프 막힘, 긴 GC, `docker pause`) 그 워커가 보내던 건은 기한이 지난 뒤 다른 워커가 넘겨받습니다. 깨어난 워커는 기한이 지난 건을 보내지 않고, 이미 보낸 건의 결과 기록은 펜싱에 걸립니다. 펜싱에 걸리면 조회로 중복 여부를 확인해 남기고, 프로세스는 종료하지 않고 계속 일합니다. 통합 테스트에서 실제 워커 프로세스를 `SIGSTOP`으로 멈췄다가 깨워 이 흐름을 확인합니다. 워커 ID는 프로세스마다 새로 뽑습니다.
- 트랜잭션 도중 멈춘 워커가 쥔 알림 행 잠금은 Postgres가 풉니다. 워커의 DB 연결에 `idle_in_transaction_session_timeout`(5초)을 걸어, 트랜잭션 도중 응답하지 않는 세션을 끝내게 합니다.
- 발송 직전 확인은 남은 기한이 응답 한도보다 길 때만 통과하고, 요청 바이트를 소켓에 쓰기 바로 앞에서 합니다. 그보다 앞에서 확인하면, 소켓 배정이나 TCP 연결을 기다리는 사이에 멈췄다 깨어난 워커가 이미 넘겨받힌 건을 보낼 수 있습니다. 확인에 걸린 건은 보내지 않고 반납하며, 시도 횟수와 서킷 브레이커에 세지 않습니다.
- 남는 틈도 기록해 두었습니다. 확인을 통과한 뒤 요청 바이트가 커널로 넘어가기 전(같은 동기 실행 안의 아주 짧은 구간)에 멈추고, 남은 기한과 결과 확인 대기(5초)를 합친 것보다 오래(적어도 15초, 보통은 30초 넘게) 있다가 깨어나면 중복이 생길 수 있습니다. 이 틈은 실제로 재현됩니다. 세션 방식일 때 같은 틈을 재 보니, 초당 100건을 보내는 워커를 아무 때나 멈추고 넘겨받기와 결과 확인 대기보다 오래 멈춰 두면 실행의 1~3%에 한 건씩 중복이 났습니다. 생기면 탐지합니다. 깨어난 워커가 그 요청의 응답을 받아 펜싱에 걸리면 조회로 중복을 확인해 `alarm_duplicates_detected_total`과 error 로그로 남깁니다. 놓치는 경우는 깨어나 요청을 보낸 직후 프로세스가 죽는 경우 하나입니다. 이 틈을 완전히 닫는 방법은 아래 "구현하지 않은 것"에 적었습니다.

### 선택 구현

#### 긴급 알림 우선

- 생성할 때 `type: "URGENT"`와 수신자(1~100명, 중복 불가)를 함께 지정합니다.
- 워커는 토큰을 먼저 받고, 받은 개수만큼 `ORDER BY priority, start_seq, id`로 꺼냅니다. 긴급 건이 있으면 토큰이 생기는 순간 긴급부터 나갑니다. 긴급이 기다리는 시간은 이미 대량 건에 나간 토큰이 쓰이는 동안뿐입니다. 평소에는 토큰이 한 개 남짓씩 나가므로 다음 토큰까지(수십 ms)이고, 토큰이 쌓여 있던 직후에도 최대 10개(약 0.2초 분량)입니다(ADR-0011).
- 대량 발송을 멈추지는 않습니다. 긴급 건이 응답을 기다리는 동안에는 토큰을 쓸 곳이 없으므로, 멈추면 처리량만 버립니다.
- 같은 우선순위 안에서는 먼저 시작한 알림부터 끝냅니다. 같은 크기의 대량 알림 두 개를 번갈아 보내면 둘 다 66분쯤에 끝나지만, 차례로 보내면 33분과 66분에 끝납니다(ADR-0012).
- 측정: 대량 알림(2000명)이 1000건 넘게 남은 동안 긴급 알림(수신자 3명) 5개를 차례로 보냈습니다. 15건 중 11건이 발송 시작 요청 후 141ms 안에 SENT가 됐습니다. 나머지 4건은 mock의 일시 오류 뒤 재시도(약 1.1초) 2건과 mock의 느린 응답(3.5~3.7초) 2건이었습니다.

#### 처리량 제한 공유

- 모든 워커가 PG의 토큰 버킷 행 하나를 함께 씁니다. 충전 타이머 없이, 토큰을 요청할 때 UPDATE 한 문장 안에서 흐른 시간만큼 채운 뒤 지급합니다. 시각은 DB 시계(`clock_timestamp()`) 하나로 잽니다(ADR-0009).
- 충전 속도는 초당 50, 용량은 10입니다. mock도 토큰 버킷(용량 50)으로 동작하는 것을 실측으로 확인했습니다. 우리 용량을 작게 두면 mock 쪽 통에 약 40개의 여유가 늘 남아, 네트워크 때문에 요청이 몰려 도착해도 429가 나지 않습니다. 충전 속도를 낮춰 여유를 만들면 처리량이 줄어들기 때문에 용량 쪽을 줄였습니다.
- 429를 받으면 버킷 행의 `paused_until`을 `Retry-After`만큼 미뤄 모든 워커가 함께 멈춥니다. 워커는 서로의 수를 알 필요가 없습니다.

#### 워커 확장과 작업 분배

- `--scale worker=N`으로 늘립니다. 분배는 `SKIP LOCKED`, 처리량은 공유 버킷, 넘겨받기는 건마다 적은 기한이 맡으므로 워커끼리 직접 통신하지 않고 서로의 수도 알 필요가 없습니다.
- 기본은 2대입니다. 처리량은 외부 상한(초당 50건)에 묶여 있어 1대로도 되지만, 1대가 죽으면 재시작될 때까지 발송이 멈춥니다. 2대면 남은 워커가 대기 건을 계속 보내고 죽은 워커가 쥐던 건은 기한(30초)이 지나면 넘겨받으며, 다중 워커에서만 생기는 경로가 평소에도 늘 실행됩니다(ADR-0010).
- 워커 한 대가 동시에 응답을 기다리는 요청은 최대 50개이고, HTTP 연결 풀의 소켓도 50개로 같게 둡니다. 워커가 한 대만 남아도 혼자 초당 50건을 낼 수 있는 값입니다(ADR-0013).
- 워커 하나는 DB 연결을 최대 12개 씁니다(결과 기록 10, 꺼내기 2). PostgreSQL 기본 `max_connections`(100)에서는 api 몫(10)을 빼면 워커 7대 정도가 상한이므로, 그 이상 늘리려면 `max_connections`를 함께 올립니다. 세션에 묶인 상태가 없어 PgBouncer 같은 연결 중계를 거쳐도 됩니다.

#### 워커가 종료될 때

워커가 내려가는 이유는 여러 가지지만, 쥐고 있던 건이 처리되는 출구는 둘뿐입니다(ADR-0007).

- 정상 종료(SIGTERM, 배포·축소): 새 건을 꺼내지 않고, 이미 보낸 요청의 응답을 기다려 기록한 뒤, 꺼냈지만 보내지 않은 건을 대기로 되돌리고, 펼치기 담당도 내려놓고 종료합니다. 다른 워커가 기한을 기다리지 않고 바로 이어 갑니다. 신호가 Node까지 닿도록 exec 형식 `CMD`와 `init: true`를 쓰고, 마무리 시간을 위해 `stop_grace_period: 30s`를 둡니다.
- 그 밖의 모든 경우(크래시, OOM, `docker kill`, 멈춤, DB와 갈라짐): 쥐고 있던 건은 기한이 지난 뒤 다른 워커가 넘겨받습니다. 펼치기 도중이었다면 기한이 지난 뒤 저장된 커서부터 이어 갑니다.

### 실패 처리

- 응답 타임아웃은 10초입니다. mock의 느린 응답(실측 3.0~4.5초)은 받고, 30초 지연은 끊어서 조회 경로로 보냅니다.
- 일시 오류(500·503)는 건별로 지수 백오프(1초에서 시작해 최대 60초, ±20% 지터)로 재시도하고, 8번 시도한 뒤 실패로 확정합니다. 429는 시도 횟수에 세지 않습니다. 그 건이 아니라 우리 속도의 문제이기 때문입니다(ADR-0014).
- 서킷 브레이커는 발송 결과로 판단합니다. 최근 20건 중 절반 이상이 5xx, 연결 오류, 응답 없음(타임아웃, 보낸 뒤 끊김)이면 브레이커를 열고 버킷을 멈춰 모든 워커가 5초(연달아 발동하면 최대 60초) 기다립니다. 대체 채널이 없으므로 장애 동안의 대응은 기다렸다가 보내는 것입니다(ADR-0014).
- 정지가 풀려도 브레이커가 열려 있으면 모든 워커를 합쳐 시험 발송 한 건만 나갑니다. 성공하면 닫고 평소처럼 보내고, 실패하면 정지를 두 배로 늘려 다시 엽니다. 시험 발송을 맡은 워커가 죽으면 기한 뒤 다른 워커가 다시 시험합니다.
- 브레이커가 열린 동안의 실패는 시도 횟수에 세지 않습니다. 그 건이 아니라 외부 장애 탓이기 때문입니다. 그래서 장애가 길어져도 재시도를 다 써서 빠지는 건이 없습니다. 브레이커가 열리기 전에 시작한 요청이 늦게 실패해 돌아와도 판단에 쓰지 않아, 정지가 풀리자마자 다시 발동하지 않습니다.
- 워커 한 대가 응답 한도보다 오래 멈췄다 깨어나도 브레이커가 열리지 않습니다. 깨어난 프로세스는 만료된 타이머를 소켓보다 먼저 실행하므로, 타임아웃 타이머가 끝나면 한 번 양보해 그사이 도착한 응답을 먼저 읽습니다. 심사에서 워커를 45초 멈추자, 외부가 멀쩡한데 브레이커가 열려 전체 발송이 10초 넘게 거의 멈춘 것을 보고 고쳤습니다. 고친 뒤 같은 시험 세 번에서 브레이커 발동은 0이었습니다.
- 통합 테스트에서 외부가 4초 동안 전부 503을 내도(정지 0.1~0.4초가 여러 번 풀림) 실패 확정은 0건이고, 장애 동안 나간 요청은 80건 미만입니다. 시도 횟수를 세게 되돌리면 앞쪽 건이 재시도를 다 써서 실패합니다(S45). 처음 구현은 정지가 풀릴 때마다 동시 한도만큼 다시 보내고 그 실패를 셌기 때문에, 심사에서 외부를 300초 끊었을 때 3000명 중 1~12명이 누락됐습니다.
- 수신자 조회(펼치기)가 실패하면, 다시 하면 될 수 있는 실패(5xx, 429, 타임아웃)는 같은 간격으로 재시도합니다. 다시 해도 같은 실패(400, 401, 403, 404)는 펼치기를 멈추고 알림을 취소 처리하며, 취소 이유(`EXPANSION_FAILED`)와 마지막 오류를 알림에 남깁니다. 일부만 만들어진 채 COMPLETED로 끝나지 않게 하기 위해서입니다(ADR-0006).
- mock이 제공하는 `GET /health`는 compose 기동 순서에만 쓰고, 장애 판단에는 일부러 쓰지 않습니다. health는 프로세스가 응답한다는 것만 보여 주므로 발송 API만 실패하는 부분 장애를 놓치고, 실제 발송 서비스(FCM 등)는 클라이언트용 health를 주지 않습니다.

### 성능

- 처리량의 상한은 외부 API의 초당 50건입니다. 실측(사용자 2000명, 워커 2대)에서 초당 49.1건이 나갔고 429는 0건이었습니다. 사용자 10만 명이면 상한 기준으로 약 33분이 걸립니다.
- 처음 측정에서는 초당 46.9건이었습니다. 결과 기록 트랜잭션이 알림 행 잠금을 기다리며 DB 연결을 붙잡는 동안 작업 루프가 연결을 얻지 못해, 그 사이 토큰이 버려지고 있었습니다. 작업 루프 전용 연결 풀(2개)을 따로 두어 49.1건이 됐습니다(ADR-0013).
- DB 부하는 실측했습니다(사용자 2000명, 초당 49건 발송, `pg_stat` 20초 표본). 워커 2대에서 토큰 버킷 행 갱신이 초당 72회, Delivery 행 갱신이 99회(건마다 꺼내기와 결과 기록), 커밋이 185회입니다. 워커 3대에서는 토큰 버킷 갱신이 94회, 커밋이 221회입니다. 처음 측정(워커 2대 159회·280회, 3대 212회·340회)에서 토큰 요청의 대부분이 0개를 받는 헛된 갱신임을 보고 줄였습니다(아래).
- 토큰은 초당 50개씩만 생겨 평소에는 한 번에 한 개 남짓을 받습니다. 0개를 받으면 연달아 0개일수록 두 배씩 물러나고(상한 100ms), 받아서 통을 비웠으면 다음 토큰이 생길 때까지 묻지 않습니다. 같은 행 하나를 HOT 갱신하는 가벼운 쿼리라(갱신 전부가 HOT, 테이블 56kB) 처리량에는 영향이 없습니다. 묶어서 받으려면 토큰이 쌓일 때까지 기다려야 하고, 그만큼 긴급 알림이 늦어집니다(ADR-0009).
- 사용자 10만 명 조회는 실측 31~33초입니다. 펼치기는 한 워커가 맡지만 발송과 동시에 진행되므로 병목이 아닙니다(ADR-0006).

### 운영

- 예상하지 못한 오류(ADR-0039): 서버가 기록 없이 죽지 않게, 오류가 올라오는 꼭대기에서 한 번씩 받습니다. 프로세스 안전망(`unhandledRejection`, `uncaughtException`), HTTP 전역 예외 필터, worker의 공통 작업 루프(`PollingLoop`)가 로그와 메트릭(`alarm_unhandled_errors_total`, `alarm_loop_errors_total`)을 남기고 계속 돕니다. api는 DB 연결 대기(5초)와 쿼리(30초)에 한도를 두어, 요청이 응답 없이 멈추지 않고 503으로 끝납니다. 일부러 끝내는 경우는 시작하지 못했을 때(설정 오류 등)뿐입니다. 결과를 DB에 기록하지 못해도 끝내지 않습니다. 그 건은 기한이 지나 다른 워커가 넘겨받습니다.
- 헬스체크(ADR-0026): api의 `/health/ready`는 DB 확인을 포함하고, `/health/live`는 포함하지 않습니다. DB가 잠깐 죽었을 때 모든 api가 재시작되는 것을 막기 위해서입니다. worker의 `/health/live`는 HTTP 응답이 아니라 작업 루프가 최근 30초 안에 돌았는지를 봅니다.
- 로그(ADR-0028): 표준 출력 JSON이고, 모든 줄에 traceId(요청에 `traceparent`가 있으면 그 값)와 alarmId 등이 붙습니다. info에는 성공 건을 남기지 않고, `LOG_LEVEL=debug`로 켜면 발송 시도마다 한 줄씩 생략 없이 남깁니다. 본문의 네 자리 이상 숫자, 전화번호, 비밀 키, 접속 주소의 비밀번호는 로거 한 곳에서 마스킹합니다.
- 설정(ADR-0030): 모두 환경변수이고 기동할 때 검증합니다. 값 하나뿐 아니라 값 사이의 관계(응답 한도 10초 < 발송 기한 30초 등)가 어긋나도 시작하지 않습니다.
- 마이그레이션(ADR-0025): 별도 `migrate` 서비스가 DDL 권한 계정으로 실행하고 끝납니다. api와 worker는 데이터 읽기·쓰기 권한만 있는 계정을 씁니다. 앱에 구멍이 있어도 테이블을 지우거나 바꿀 수 없습니다.
- 인증(ADR-0033): 호출 한 번으로 10만 명에게 보낼 수 있는 API를 열어 둘 수 없다는 점을 보이기 위한 최소 구현입니다. 고정 API 키를 `timingSafeEqual`로 비교합니다. 실제 운영에서는 앞단 게이트웨이나 사용자별 인증으로 대체합니다.
- 메트릭(ADR-0027): api와 worker가 `/metrics`를 Prometheus 형식으로 냅니다. 경보 규칙을 둔다면 이렇게 잡습니다.

| 조건 | 의미 |
| --- | --- |
| `alarm_duplicates_detected_total` 증가 | 같은 수신자에게 두 번 나간 것이 확인됐다. 즉시 확인 |
| `alarm_rate_limit_pauses_total`가 5분 넘게 계속 증가 | 처리량 제한 설정이 외부 서비스와 맞지 않는다 |
| `alarm_breaker_trips_total`가 5분 넘게 계속 증가 | 외부 발송 서비스 장애 |
| `alarm_oldest_in_flight_seconds` > 60 | 넘겨받기가 돌지 않는다(살아 있는 워커가 없거나 모두 멈췄다) |
| `alarm_pending_oldest_due_seconds{priority="0"}` > 10 | 긴급 알림이 밀리고 있다 |

## 기술 선택

| 항목 | 선택 | 이유 |
| --- | --- | --- |
| 언어·프레임워크 | TypeScript, NestJS 12, Node 24 LTS | 과제 조건. api와 worker가 같은 코드베이스와 이미지를 씁니다 |
| 저장소·큐·처리량 제한 | PostgreSQL 18 하나 | 아래 참고. `uuidv7()`이 내장돼 확장이 필요 없습니다 |
| DB 접근 | Drizzle (`pg` 드라이버 위) | `FOR UPDATE SKIP LOCKED`, `FOR NO KEY UPDATE`, CTE를 쓴 `UPDATE ... FROM`, `NOT EXISTS` 같은 핵심 쿼리를 빌더로 쓸 수 있고, 읽은 엔티티를 통째로 덮어쓰는 동작이 없어 동시성에서 lost update 함정이 없습니다. SQL은 저장소(`*.repository.ts`)에만 두고, 빌더로 표현할 수 없는 한 문장(계산과 지급이 한 문장이어야 하는 토큰 버킷)과 값 자리의 작은 식(`clock_timestamp()` 등)만 `sql` 템플릿으로 씁니다(ADR-0036) |
| 외부 HTTP | `node:http` | keepAlive 소켓 수를 표준 라이브러리로 정할 수 있고, "요청 바이트를 커널에 다 넘겼는가"를 직접 판정할 수 있습니다(ADR-0037) |
| 설정·검증·문서 | @nestjs/config, class-validator, @nestjs/swagger | NestJS 표준 조합 |
| 메트릭 | prom-client | Node에 Prometheus 형식 기능이 없고, 히스토그램을 직접 만들면 실수하기 쉽습니다 |
| 테스트 | Jest, Stryker | 단위·통합, 변이 테스팅 |
| 린트·포맷 | ESLint(typescript-eslint), Prettier, @stylistic | ESLint와 Prettier는 NestJS 새 프로젝트가 기본으로 쓰는 도구입니다. 문장 사이 빈 줄 규칙(`padding-line-between-statements`)은 ESLint 본체에서 폐기 예정(8.53)이라 그 규칙을 옮겨 간 @stylistic을 더했습니다 |

### 의존성은 의도적으로 최소화했습니다

흔히 쓰는 도구를 몰라서 뺀 것이 아닙니다. 그 도구가 주는 기능을 하나씩 확인하고, 이미 의존하는 것(PostgreSQL, Node 표준 기능, NestJS)으로 대체할 수 있을 때 뺐습니다(ADR-0005). 구성 요소가 하나 늘 때마다 장애 지점과 운영 대상이 늘고, 시스템끼리 상태가 엇갈릴 가능성이 생깁니다. 이 과제의 핵심인 중복·누락 방지가 시스템 사이의 동기화 문제로 바뀌는 것을 피하고 싶었습니다.

| 흔한 선택 | 대신 쓴 것 | 근거 |
| --- | --- | --- |
| BullMQ + Redis 큐 | `deliveries` 행 + `FOR UPDATE SKIP LOCKED` | 큐와 DB에 상태를 나눠 두면 시작·완료·취소마다 둘을 맞추는 코드가 필요합니다. BullMQ도 멈춘 작업을 시간 기반 잠금으로 넘기지만, 넘겨받은 쪽은 그 작업을 그대로 다시 실행합니다. 중복을 막는 것은 큐가 아니라 "넘겨받은 건은 조회한 뒤에만 다시 보내고, 늦은 쓰기는 펜싱으로 막는다"는 장치라서, 그 장치를 DB 위에 두면 큐는 중복 정보가 됩니다(ADR-0003) |
| Redis 기반 rate limiter | PG 토큰 버킷 행 하나 | 실측 초당 72~94회 갱신(워커 2~3대)이고 처리량에 영향이 없으며, 잃어도 잠깐의 429로 끝나는 가벼운 상태입니다(ADR-0009) |
| 워커 등록 테이블, 감시 프로세스, etcd | 건마다 적은 기한(`lease_until`) | 넘겨받기는 건의 기한만 보면 되므로 워커 명단이 필요 없습니다. 기한 판단은 살아 있는 워커 누구나 DB 시계로 합니다. 감시 프로세스를 두면 감시자의 장애를 다시 고려해야 합니다(ADR-0004) |
| pgmq | 위와 같음 | 메시지가 확장의 자체 테이블에 있어 상태가 다시 두 곳에 나뉘고, 공식 postgres 이미지에 없습니다 |
| OpenTelemetry | W3C `traceparent` + AsyncLocalStorage | 지금 필요한 것은 요청 하나의 로그를 찾는 traceId입니다. 형식은 표준을 따르므로 나중에 OTel을 붙여도 그대로 이어집니다(ADR-0019) |
| pino | NestJS 기본 로거의 JSON 모드 | NestJS 11부터 기본 지원합니다(ADR-0028) |
| 별도 HTTP 클라이언트 | `node:http` | 내장 `fetch`는 연결 수를 정하려면 `undici` 패키지가 필요합니다(ADR-0037) |

각 결정에는 다시 볼 조건도 적었습니다. 예를 들어 외부 처리량이 초당 수천 건으로 커지면 처리량 제한부터 Redis로 분리합니다.

## 명세 해석

| 모호한 점 | 해석 |
| --- | --- |
| 외부 발송 API에 제목 필드가 없다 | 본문만 보냅니다. 제목은 알림을 구별하는 관리용 이름이고, 유일하지 않아도 됩니다 |
| "발송 완료"의 기준 | 외부 API가 202로 접수했거나, 발송 내역 조회로 기록이 확인된 것 |
| "중복 없음"의 기준 | 한 알림에서 수신자마다 외부 발송 기록이 정확히 한 건 |
| "전체 사용자"를 정하는 시점 | 발송을 시작한 뒤 사용자 API를 끝까지 읽은 결과 |
| 일부 수신자만 실패한 알림 | COMPLETED. 실패는 건수와 `/deliveries`로 봅니다 |
| 발송 중 취소 | 취소가 커밋된 뒤에 시작한 꺼내기는 그 알림의 건을 집지 않습니다. 취소와 같은 순간에 돌던 꺼내기가 집은 건(워커당 평소 1건, 토큰이 쌓여 있던 직후에는 최대 10건)은 응답 직후에 나갈 수 있습니다. 이미 나가던 건은 되돌릴 수 없고, 결과를 그대로 기록합니다. CANCELED가 된 뒤에는 건수가 바뀌지 않습니다(ADR-0017) |
| "긴급이 먼저" | 토큰이 생기는 순간 보낼 수 있는 긴급 건이 있으면 긴급부터 보냅니다. 긴급 알림이 끝날 때까지 대량을 멈추는 것은 아닙니다 |
| 같은 내용을 다시 보내는 경우 | 알림을 새로 만듭니다. 알림 하나는 발송 한 번입니다 |

요구사항별로 어떤 ADR과 테스트가 대응하는지는 [docs/requirements.md](docs/requirements.md)에 표로 정리했습니다.

## 고민한 것과 바꾼 결정

- 처음 구현에서는 모든 쿼리를 `sql` 템플릿과 `execute`로 썼습니다. Drizzle을 고른 이유(빌더와 타입)를 살리지 못한 것이라, ADR-0036대로 빌더로 옮기고 SQL을 저장소 계층에 모았습니다. 서비스와 워커 루프에는 흐름만 남았습니다. 옮긴 뒤 같은 테스트와 고의 결함 목록을 다시 돌려 동작이 같음을 확인했고, 그사이 Drizzle이 드라이버 오류를 `cause`로 감싸는 탓에 DB 장애가 503이 아니라 500으로 나가던 버그가 드러나 고쳤습니다.
- 심사 기준을 "계획대로 만들었는가"에서 "명세를 낸 사람이 이 구현을 보고 납득하는가"로 바꿨습니다. 우리 ADR을 기준으로 삼으면 우리 계획을 다시 확인할 뿐이기 때문입니다. 새 기준의 심사에서 발송 시작과 취소가 동시에 오면 실제로 시작한 요청이 409를 받는 문제가 나와, 전이한 요청은 그 결과로 답하도록 고쳤습니다(ADR-0016).
- 결과 확인 대기를 30초에서 5초로 줄였습니다. 처음에는 외부 서비스가 기록을 늦게 남길 수 있다고 보고 30초로 잡았습니다. mock을 실측해 보니 30초 지연 요청도 0.35초 시점에 이미 기록이 있었습니다. 남긴 5초는 끊기 직전에 보낸 요청이 도착하는 여유입니다.
- 워커 장애 처리를 DB 세션 판정에서 건마다 기한을 두는 리스로 바꿨습니다. 처음에는 워커마다 advisory lock을 쥐고, 생존 신호가 끊긴 워커의 DB 세션을 다른 워커가 `pg_terminate_backend`로 끊는 방식이었습니다. 리스를 버린 이유("기한이 지난 워커는 자신이 무효가 된 것을 알 길이 없다")는 다시 보니 약했습니다. 워커도 자기 기한을 알고, 멈춘 동안 모르는 것은 두 방식이 같습니다. 세션 방식만의 장점(크래시 때 즉시 넘겨받기)은 작은 반면, 연결 상태라는 소프트웨어 바깥의 동작에 기대고 남의 세션을 끊어야 해서 설명하고 납득시키기 어려웠습니다. 잠금을 잃은 워커가 바로 종료해야 해서 중복 탐지가 깨지는 문제도 있었습니다. 경위는 ADR-0004에 적었습니다.
- 서킷 브레이커를 바꿨습니다. 정지가 풀리면 시험 발송 한 건만 내보내고, 열린 동안의 실패는 시도 횟수에 세지 않으며, 열리기 전에 시작한 요청의 늦은 결과는 판단에 쓰지 않습니다. 심사에서 긴 외부 장애에 일부가 재시도를 다 써서 누락되는 것과, 느린 외부 서비스 앞에서 정지가 되풀이되는 것이 드러났기 때문입니다(ADR-0014).
- 토큰을 연달아 0개 받으면 두 배씩 물러나게 했습니다. 0개는 다른 워커가 먼저 가져간 충돌이라, 다음 토큰까지만 쉬면 워커 수에 비례해 헛된 갱신이 늘었습니다(워커 3대 테스트에서 빈 요청 약 730건 → 약 350건, ADR-0009). 또 토큰을 받아 통을 비웠으면 다음 토큰이 생길 때까지 묻지 않게 했습니다. 바로 다시 물으면 거의 늘 0개이기 때문입니다(약 350건 → 약 270건, 초당 49건 발송에서 토큰 버킷 갱신이 워커 2대 초당 155회 → 72회).
- 처리량을 재다가 DB 연결 풀을 둘로 나눴습니다(초당 46.9건에서 49.1건). 설계 단계에서는 보지 못한 문제였고, 측정으로 드러났습니다.
- "보냈는지 모르는" 오류의 기준을 하나로 줄였습니다. 처음에는 연결 오류 코드 목록(ECONNREFUSED 등)도 함께 봤는데, 변이 테스팅에서 그 조건을 지워도 결과가 같다는 것이 드러났습니다. 지금은 "요청 바이트를 커널에 다 넘겼는가" 하나만 봅니다.
- 고의 결함 목록의 첫 실행에서 꺼내기 정렬의 우선순위를 지운 결함을 테스트가 놓쳤습니다. 10건을 한 번에 꺼낸 뒤 순서를 봤는데, 코드가 반환 전에 다시 정렬해 SQL 결함을 가렸습니다. 우선순위의 의미는 "토큰 수만큼 꺼낼 때 무엇을 고르는가"이므로, 한 건씩 꺼내 고른 순서를 보도록 테스트를 고쳤습니다.
- 멈춘 워커 테스트를 실제 프로세스로 바꾸면서 문제를 여럿 찾았습니다. 처음 테스트는 워커처럼 잠금만 쥔 가짜 세션을 썼습니다. 컴파일된 워커를 발송 도중 `SIGSTOP`으로 멈추고, 다른 워커가 넘겨받아 끝낸 뒤 `SIGCONT`로 깨우는 테스트를 더해 수십 번 반복했더니 아래 문제가 나왔습니다. 모두 재현 테스트와 고의 결함 항목을 함께 남겼습니다.
  - 반복 실행 중 한 번, 한 수신자에게 기록이 두 건 남았습니다. 발송 직전 확인이 HTTP 요청을 만들기 전에만 있어서, 소켓 연결을 기다리던 요청이 깨어난 뒤 그대로 나간 것으로 판단했습니다. 확인을 소켓에 쓰기 직전으로 옮겼습니다.
  - 트랜잭션 도중이던 DB 연결이 끊기자 처리되지 않은 `'error'` 이벤트로 프로세스가 죽었습니다. 풀은 쉬고 있는 연결의 오류만 받아 주기 때문입니다. 같은 일은 DB 재시작 때 api에서도 생길 수 있어서, 모든 연결에 오류 리스너를 달았습니다.
  - 나머지 둘은 세션 방식(위의 리스 전환 전)에만 있던 문제라, 리스로 바꾸며 사라졌습니다. 경위는 [docs/testing.md](docs/testing.md)에 있습니다.
- 취소 정리가 끝난 뒤 재시도 건이 PENDING으로 돌아오면 그 건이 영원히 남는다는 것을 구현 중에 발견했습니다. 건을 대기로 되돌리는 모든 경로가 알림 행을 잠그고 상태를 확인해, 알림이 SENDING이 아니면 CANCELED로 두도록 했습니다(ADR-0017).

## 구현하지 않은 것 (설계만)

- 데이터 보존: 대량 알림 하나에 Delivery가 10만 행 생깁니다. 지금은 부분 인덱스 덕에 발송 경로가 느려지지 않아 그대로 둡니다. 쌓이면 Delivery를 월 단위 파티션으로 나눠 오래된 달을 통째로 떼어 내고, 지우기 전에 끝난 알림의 건수를 알림 행에 스냅숏으로 남깁니다. 끝난 알림의 건수는 더 바뀌지 않으므로 원본과 어긋나지 않습니다(ADR-0031).
- 외부 펜싱: 위에 적은 "발송 직전 확인 직후 기한을 넘겨 멈춤" 틈을 완전히 닫으려면, 의심 워커의 프로세스나 네트워크를 밖에서 끊고 끊긴 것을 확인한 뒤에만 넘겨받아야 합니다(STONITH). 이 방식이 더 낫다는 것은 알지만, 애플리케이션이 직접 하려면 `docker.sock` 같은 호스트 root 수준 권한이 필요해 이 범위에서는 과하다고 판단했습니다. 실제 운영에서는 플랫폼(쿠버네티스의 파드 삭제·노드 펜싱, 클라우드 인스턴스 중지)이 맡는 문제입니다(ADR-0004).
- 정정 알림: 잘못 보낸 알림을 취소하고 이미 받은 사람에게 정정 알림을 보내는 흐름을 위해, 취소된 알림에서도 실제로 받은 사람을 정확히 뽑을 수 있게 했습니다. 보내는 기능을 만든다면 "알림 X의 SENT 수신자"라는 수신자 출처를 추가하고, 펼치기가 사용자 API 대신 Delivery 테이블을 읽게 하면 됩니다(ADR-0017).
- 템플릿: 같은 문구를 반복해서 보낸다면 템플릿을 두고, 알림을 만들 때 내용을 복사해 오는 층을 위에 얹으면 됩니다. 알림이 이미 내용 스냅숏을 가지므로 지금 구조는 바뀌지 않습니다(ADR-0023).
- 사용자별 인증과 감사 기록: 지금은 키가 하나라 누가 시작하고 취소했는지 구별할 수 없습니다(ADR-0033).
- 대체 채널: 푸시가 막히면 SMS로 돌리는 경로가 생기면, 서킷 브레이커가 열린 동안 기다리는 대신 그 채널로 보냅니다(ADR-0014).

## 시간이 더 있다면

- 사용자 10만 명으로 도는 끝단 테스트를 저장소 스크립트로 두겠습니다. 지금 스크립트는 2000명까지입니다. 10만 명은 심사 과정에서 한 번 돌려 봤고(워커 3대, 완료 기준 초당 44~48건, mock 쪽 토큰 사용 초당 약 50건, 429 0, 대량 발송 중 긴급 100건의 외부 접수 p95 1.9초), 상한 기준으로 약 33분이 걸립니다.
- monitoring 프로필에 Grafana 대시보드와 위의 경보 규칙을 실제로 넣겠습니다. 지금은 Prometheus 수집까지만 있습니다.
